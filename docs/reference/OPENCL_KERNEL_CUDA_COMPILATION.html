一份 .cl 内核，如何走 OpenCL 和 CUDA 两条编译路线

核心是“受约束的源码转换＋设备兼容头＋主机运行时适配”。CUDA 路线将 OpenCL 风格源码转成 CUDA C++，由 NVRTC 编译，再通过 CUDA Driver API 加载和运行。

共享设备算法源码NVRTC 运行时编译有限 OpenCL 子集
三个名称对应的对象：本地 .refactor/gpuowl/ README 自称 PRPLL；PrMers 的 Marin／内部 NTT 路线仍使用原生 OpenCL；PrMers 的 CUDA 路线来自 third_party/aevum/ 的 PRPLL 派生引擎。它们不能合称为“PrMers 的所有 OpenCL 内核都自动支持 CUDA”。

NVIDIA 官方将 NVRTC 定义为 CUDA C++ 运行时编译库；因此这里的“编译 OpenCL 内核”依靠项目自己先适配源语言。NVRTC 的输出可以是 PTX 或 CUBIN，再交给 Driver API 加载。见 NVIDIA NVRTC 说明。

  1. 构建主机程序：PRPLL 的 Makefile 用普通 C++ 编译器构建主机。make CUDA=1 选择 CUDA 兼容实现并链接 NVRTC、CUDA Driver；CUDA=0 使用 OpenCL。这里没有要求用 nvcc 逐个离线编译 .cl。
  2. 打包资源：genbundle.sh 将 .cl 与兼容头变为字符串。兼容头在 bundle 中必须排第一：CUDA 编译传入它，原生 OpenCL 编译跳过它。
  3. 组装一次具体编译：KernelCompiler::build 创建包含目标 .cl 的程序，连同虚拟头和形状宏调用名为 clCompileProgram 的入口。CUDA 构建中这个名字指向本地适配函数。
  4. 转换语言：主源码和各虚拟 .cl 头经过 preprocessOpenCL，注入 opencl_compat.cuh。转换后源码作为 prpll_kernel.cu 等 CUDA C++ 编译单元提交。
  5. NVRTC 编译：nvrtcCreateProgram → nvrtcCompileProgram → nvrtcGetPTX；当前本地 PRPLL 还尝试获取匹配 sm 的 CUBIN。
  6. 加载与启动：cuModuleLoadDataEx → cuModuleGetFunction → cuLaunchKernel。缓存命中时跳过源码编译，但依然需要加载设备模块。

PRPLL：Makefile:22–43、111；src/KernelCompiler.cpp:340–365；src/cuda/clwrap_cuda.cpp:362–479；src/cuda/cudawrap.cpp:448–503。模块和启动语义分别见 Driver Module API、Driver Execution API。

2. 源码转换：预处理器与兼容头各做一半

preprocessOpenCL 是按已知源码写法扫描和改写的转换器；兼容头负责类型、函数和宏。两者配合很重要，例如不能把 OpenCL 的 __global 直接宏定义为空，否则容易误伤 CUDA 的 __global__。

OpenCL 写法或行为CUDA 路线注意点
kernel / __kernelextern "C" __global__保留可按原名字查询的导出内核，避免 C++ 名字改编。
普通助手函数NVRTC 的 -default-device不必给每个原 OpenCL 函数补写 __device__。
global / __global 指针扫描器移除地址空间限定这是 OpenCL 指针限定符，与 CUDA 内核函数限定符不是同一语义。
local 固定数组改写为 __shared__ 数组local 函数参数则移除限定；处理依赖源码模式，动态 local 参数需单独实现。
constant 指针const 指针不等同于把数据放入 CUDA __constant__ 符号；缓存策略取决于实际生成代码。
KERNEL(WG)／reqd_work_group_sizeextern "C"、__global__ 与 __launch_bounds__CUDA launch bounds 主要描述上限／资源约束；精确工作组要求仍须由启动端保证。
overloadable 属性移除，使用 C++ 重载只处理转换器认识的属性。
ulong、long2、ulong2显式 64 位标量／CUDA longlong 向量类型Windows 的 C++ long 通常为 32 位。代码使用 i64 避免直接映射裸 long。
向量构造、算术和位重解释make_type2、运算符重载及 as_type 助手覆盖项目用到的类型和形态，不是全部 OpenCL 向量语言。
get_*_id／sizethreadIdx、blockIdx、blockDim、gridDim本地实现存在一维或部分二维假设，详见适用范围。
mul_hi(ulong, ulong)__umul64hi按整数高半乘法接入 CUDA 指令；不涉及浮点近似。
barrier／sub_group_broadcast__syncthreads／__shfl_sync工作组与 warp 范围不同，调用者必须满足各自参与条件。
OPENCL pragma、部分 PTX 约束删除 pragma；针对已知写法调整 asm 操作数约束属于源码适配规则，不能据此保证任意 OpenCL／汇编都可转换。

为什么转换后仍可高效

设备端最终是编译器可见的 CUDA C++，类型助手与数学函数能够内联。内核执行时没有“逐个 OpenCL 指令解释”的过程；额外编译与主机适配成本主要在启动和提交侧。生成代码可能与原生 CUDA 接近，也可能因写法、资源与计划不同而更慢，不能只凭这种架构推导加速比例。

同一份 .cl 还可以通过 HAS_PTX、CUDA_BACKEND、厂商能力分支使用特定优化。本地 PRPLL 的 math.cl 本身已有 PTX 分支，兼容头选择 NVIDIA 路径；“共享源码”并不要求所有厂商执行完全相同的机器指令。

PRPLL：cudawrap.cpp:221–437；opencl_compat.cuh:16–103、121–247、269–317；cl/math.cl:312–350。

3. 主机侧仍需要适配：只改内核语法不够

PRPLL 用 tinycuda.h 定义 cl_mem、cl_kernel 等不透明句柄包装，再由 clwrap_cuda.cpp 实现它实际使用的 cl* 子集。上层 Queue、Kernel、Gpu 保留既有调用形式；CUDA 运行时真正管理的是 CUdeviceptr、CUfunction、CUstream 和 CUevent。

上层职责CUDA 适配关键语义
clCreateBuffercuMemAlloc＋句柄包装cl_mem 主机句柄本身不是设备地址。
clSetKernelArg将已登记 cl_mem 转换为 CUdeviceptr，保存其他标量参数本地使用“大小＋对象登记表”判断缓冲参数；新项目可直接使用显式类型，避免隐式猜测。
command queue非阻塞 CUDA stream同一 stream 内保持顺序；non-blocking 不代表主机等待自动低 CPU。
NDRange kernelglobal/local size 换算 grid/block，cuLaunchKernel维度、偏移、等待列表和尾组语义必须按支持范围核对。
读写、复制同一 stream 的异步 memcpy；阻塞要求时同步不能混入默认流复制并假定会等待非阻塞 stream。主机缓冲寿命仍需保证。
marker／finish／eventcuEventRecord、cuStreamWaitEvent、cuStreamSynchronize 等设备依赖、完成查询、错误传播和最终排空都是主机适配的一部分。

CUDA 路线中名为 clLinkProgram 的适配主要加载已经由 NVRTC 形成的模块，并不等于实现了所有 OpenCL 分离编译和多程序链接语义。

PRPLL：tinycuda.h:21–61；clwrap_cuda.cpp:507、648、759、799、853、898、985、1061。这些是本地应用子集，不是完整或经过认证的 OpenCL 实现。

4. PrMers：Aevum 插件复用同一路线

Marin／内部 NTT

由 PrMers 的 OpenCL 路径组装、创建和编译 program，内核包含 Marin 等来源。已确认的入口仍为真实 clCreateProgramWithSource／clBuildProgram。

include/marin/ocl.h:484–522；include/marin/engine_gpu.h:1336；src/opencl/NttEngine.cpp:20。

Aevum OpenCL／CUDA

同一引擎源码分别构建 OpenCL 插件与 CUDA 插件。CUDA 插件内部使用 .cl 转换器、兼容头、NVRTC 和 Driver API；PrMers 通过 aevum_engine_* C 接口访问它。

third_party/aevum/Makefile:43、94–107；src/EngineApi.h:12–58；scripts/build_aevum_cuda.sh:84–103。

构建与运行选择分开

  • PrMers Makefile 的普通 make 先保证 OpenCL 构建，再按 SDK 检测决定是否构建 CUDA 插件；make aevum-dual 是要求 CUDA 构建成功的入口。
  • 两个插件使用不同对象输出目录。Linux 共享库使用隐藏可见性和本地符号绑定等措施，减少同名兼容函数与真实 OpenCL 符号互相干扰。
  • 运行时 EngineAevum 用 LoadLibrary／dlopen 加载插件，通过 C ABI 获取构造、乘法、平方、读写和同步入口。PrMers 主程序仍能使用原生 OpenCL；CUDA 插件并不意味着主程序完全移除了 OpenCL 依赖。
  • 先把用户所选 OpenCL 设备映射到同一物理 NVIDIA CUDA 设备，不能假定两个设备序号一致。
  • 当前 choose_api 对两个后端运行相同 workload 探针，核对 residue；auto 模式需要 CUDA 探针每操作时间小于 OpenCL 的 97% 才选 CUDA。显式 cuda 模式可以跳过 3% 收益门槛，但仍要求探针对照一致；不可用或失败时回退。

这里的 3% 是该适配器的选择门槛，不是 CUDA 比 OpenCL 固定快 3%；探针相同也不构成完整 ECM 任务已经逐项验收的证据。

PrMers：Makefile:126–153；scripts/build_aevum_cuda.sh:87–103；src/aevum/EngineAevum.cpp:72、102、328–348、357、536–603。SDK 与宿主平台的具体构建条件以这些本地文件为准。

5. 两份本地副本并非完全相同

项目本地 GPUOWL／PRPLL本地 PrMers/Aevum
设备编译NVRTC，可取 PTX 和匹配 sm 的 CUBIN；优先加载 CUBIN，拒绝后尝试 PTX。所查 compile 路径返回 PTX，由 Driver 加载／JIT。
目标架构查询 NVRTC 支持列表；匹配时选 sm，否则尝试不高于设备的 compute 目标。所查编译入口直接按设备 major/minor 生成 sm 目标，需核对所带 NVRTC 是否支持。
资源参数寄存器限制可以从编译参数中分离，在 PTX 加载路径处理。可传 maxrregcount；转换 KERNEL 宏支持 CUDA_MIN_BLOCKS，部分加载限制另有实现。
厂商变体兼容头选择 NVIDIA／PTX 分支。编译选项额外将 FFT_VARIANT 的某些 AMD W/H 变体改为 NVIDIA 通用变体。
NDRange／内建维度启动处理 x/y；get_group_id 和 get_local_size 部分处理第二维，其他函数仍有一维写法。所查启动主路径及多数 get_* 宏以第一维为主，Graph 子路径还显式拒绝部分维度／依赖情况。
事件查询失败所查 clGetEventInfo 只把 NOT_READY 改为运行，其他查询错误在该分支可能继续报告完成。通过 cuda_error_map::eventStatusFromCu 把查询失败映射为负执行状态，避免当作完成。
选择方式常规 Makefile 用 CUDA=0/1 选择构建后端。PrMers 可以在同一宿主进程中加载两个引擎插件并按探针选用。

PRPLL：clwrap_cuda.cpp:268–291、340、362、898、1099；KernelCompiler.cpp:479–506。Aevum：clwrap_cuda.cpp:242、284–310、713、922；cudawrap.cpp:222、447；EngineAevum.cpp:536。它们的不同实现不在本轮修改范围内。

6. 对“任意 OpenCL 内核都能编译为 CUDA”的限制

  1. 语法转换不是通用编译器。扫描规则识别特定类型、属性、数组声明和向量构造；它没有完整 OpenCL AST／类型系统。新增内核写法可能需要扩展规则，纯字符串替换也要防止误改注释、字面量或不相关语句。
  2. 维度和索引并未完整覆盖。例如 get_global_id(d) 在所查头中仍以 x 计算，部分索引被转为 32 位。不能原样承载我们 Stage2 的 batch 第二维和大偏移。
  3. 等待列表不是每个入口都实现。PRPLL 的 clEnqueueNDRangeKernel 参数明确忽略 globalOffset、nWaits、waits；marker 入口却实现了 stream wait。上层必须使用它实际支持的依赖表达，不能把函数名当作完整 OpenCL 合同。
  4. 原子与内存模型特化。兼容头将若干 C11 atomic 操作简化为 volatile load/store 与调用者 fence；这是为特定 carry 发布协议设计的实现，不是通用 acquire/release／scope 的完整仿真。新增跨 block 协议必须重新证明可见性与进展。
  5. local、constant、subgroup 各有范围。固定 shared 数组与动态 local 参数不同；const 指针不等于 CUDA constant storage；全 mask shuffle 要求对应线程参与，不能替代任意 subgroup collective。
  6. 计时不是完整时间轴。两个兼容实现的部分 profiling 时间戳采用相对起点和 CUDA elapsed time 构造，不能直接用于跨事件绝对时间重建。
  7. 编译器、驱动和设备架构仍需匹配。本地 PRPLL 另有 PTX_VERSION 重标号入口；修改 PTX 文本版本号并不能一般性证明旧驱动支持其指令和语义，不应照搬为通用发行兼容方案。

PRPLL：opencl_compat.cuh:35–40、285–317；clwrap_cuda.cpp:250–265、898、1118。Aevum：opencl_compat.cuh:35–40、273–302；clwrap_cuda.cpp:713、944。以上属于源码合同审查，没有通过运行实验宣称这些局限已造成某个用户故障。

7. 对 ECM-ELF OpenCL Stage2 规划的启示

值得采用的是“共享受约束的设备源码”。精确域算术、NTT 索引、pack/carry 和归约主体尽量共用；CUDA PTX／shuffle 与 OpenCL local／subgroup 差异集中在明确原语和少数内核变体。主机侧继续使用自己拥有的设备资源与队列。

这比维护两套独立 NTT 数学实现更容易核对一致性。它也不要求把 ECM-ELF 的所有 CUDA API 全部伪装成 OpenCL：PRPLL 的 cl* 适配服务于其已有上层调用，ECM-ELF 可以直接在自己的批量运算入口调用 CUDA 或 OpenCL，实现显式的缓冲类型和依赖。

  • 共享层：固定宽度类型、Goldilocks 公式、槽与 carry 合同、索引、数学请求。第一版采用能被两种编译器接受的受限 C 风格表达。
  • 设备原语层：高半乘法、加减进位、工作组存储、同步、subgroup、可选 PTX。接口描述范围与参与条件，避免暗含 warp32。
  • 编译层：OpenCL 用设备驱动编译；CUDA 可选 NVRTC，或由构建期生成等价 CUDA C++ 再离线编译。共享源码与是否运行时编译是两个独立选择。
  • 保留 CUDA 性能控制：现有已验证 PTX 和特化 tile 可以作为 CUDA 专属变体保留；共享化逐算子推进，先固定 D 对照，不能因“统一”就替换已验证的最快路径。
  • 缓存身份：至少包括主体源码、适配头／转换器版本、编译选项、编译器、目标架构及设备／驱动信息；OpenCL binary、CUDA PTX/CUBIN 与性能数据分别标明来源。
  • 首个探针：同一数学主体分别形成 OpenCL kernel 和 CUDA kernel，比较 Goldilocks 边界、正逆 NTT、卷积与 S4 结果，再对比完整吞吐。不能只验证“编译成功”。

具体实施建议属于 OpenCL Stage2 规划草稿，本固定资料不声明 ECM-ELF 已实现双后端共享内核。本轮没有编译或运行这些第三方工程，也没有修改生产程序。
