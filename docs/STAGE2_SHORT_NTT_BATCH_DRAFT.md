# 短 NTT 批处理开发草稿

## 范围与状态

本草稿覆盖 NTT 表排序修复、实际执行的长度计数及实验性短 NTT 分块选择。正式语义见 [NTT](architecture/NTT.md) 与 [Auto B2 / tune](architecture/AUTO_B2.md)。新策略默认关闭；编译不代替 GPU 算术和完整曲线性能验证。

## 已有数据与研究边界

输入为用户指定的 `build_cuda_cmake/production_stage2/stage2_tune.toml`；原始副本保存在忽略目录 `data/experiments/short_ntt_batch_20261010/stage2_tune_before_sort.toml`。condition.0 记录 sm89、CUDA driver/runtime 数值13030、PTX3、add_sub_mask=1，repeats=19。表未记录功耗、频率、设备名称或生成二进制身份，不能将这些数据声明为某个固定功耗下的完整生产测试。

计时边界为两个正向变换加点乘/缩放融合逆向的 GPU 事件时间，排除打包、carry、系数归约及传输。保留数据示例：

- k=10：batch=1/4/16，单批26.624/27.648/26.624 μs；Conv/s分别约37,560/144,676/600,962。
- k=16：batch=1/4/16，Conv/s约8,798/23,532/32,826。
- k=18：batch=1/4/16，Conv/s约4,883/6,938/5,475；batch=4对batch=16的吞吐优势约26.7%。
- k=19：batch=1/4/16，Conv/s约2,782/3,488/2,578；batch=4对batch=16的吞吐优势约35.3%。
- k=20：batch=1/4/16，Conv/s约1,588/1,392/1,187，多 batch 已不占优势。

这支持按长度区分策略，并证明“统一使用最大 batch”不足以表达现有测量。生产底层原来已经批量执行，原批量可能远大于16；不能把上述单批比值直接当作本次改动的 Stage2 收益。

## 排序问题

原因：发布器定义了 columns 的顺序，却按插入顺序输出 rows。修复在发布器执行数值元组排序 `(log2_length,length,batch,tile)`，并将这四个字段保留为行列。现有文件通过可复用重排工具修复，移动1个NTT表的行，不更改测量值或冻结证据。

## 运算量计数

计数在多项式乘法成功返回后累计；按单条 L 统计卷积数，并以3倍输出数学 NTT 数。另汇总逻辑元素和 radix2 蝶形数量、S4分块数及改变分块的请求数。输出位于曲线结束；普通独立 worker 覆盖初始化和主流程。自检内部不经过该多项式层的变换另属算术验证，不重复计入。

## 实验性实现

- `stage2_short_ntt_batch_tune=false`；CLI覆盖为 `--short-ntt-batch-tune 1`，读取已有 `stage2_tune_profile`。
- 仅 k≤19、同长度至少两个实测 batch 的记录参与。条件复用遵守 tune-ignore；S4分块开关及数据hash不改变独立NTT计时，因此匹配NTT摘要时排除这两个调度字段。
- 按整批加尾批的预计卷积总时间比较，收益必须超过10%；候选不超过原准入分块，依赖关系不变。
- 同长度 batch 轴用分段线性插值；上界外按末点单位卷积时间外推，下界外保留首点的启动时间。模型值标记为估算。
- 运行、请求签名、NTT生命周期、S4生命周期与组件估算共用分块选择。数据hash用于条件记录，不能替代二进制身份。
- 完整ECM tune及启动短校准保持原分块，避免结果依赖正在更新的NTT表；实际条件记录该策略。

## 构建与定位

受限执行环境的两次 CUDA 编译均在 ptxas 报 INVALID_HANDLE。相同源码、工具链和 split_compile=8 在常规执行环境完成完整编译与链接，完整构建约121.6 s。工具链为 CUDA13.3/MSVC14.51.36231、sm89、PTX3/addsub1。队列身份和条件兼容修正后进行主机端重编译，复用脚本核验过的 CUDA 对象；最终二进制身份由独立构建目录的 manifest 给出。该现象支持环境句柄问题的判断，不是代码性能验证。

最终EXE SHA256：`bc54b75309730890ec76caf4451cb2b5c368582d48ad8c537cfe4233e2525ad2`；主机端增量构建完成约34.7 s，CUDA对象由构建脚本核验并复用。

输出目录：`build_cuda_cmake/short_ntt_batch_20261010/`。编译日志在该目录 `_objects/`。没有覆盖运行中的生产文件或改变 GPU 设置。本轮未运行新的 GPU 算术门禁或性能 A/B。

## 待验证与后续

- 原排序场景、序列化/加载后排序与测量值保留。
- 新分块下的GMP检查、摘要计数守恒、请求签名及NTT/S4内存规划与实际分配一致。
- 固定 D/P 完整曲线 A/B，分别记录 engine total、进程墙钟、准备/归约/传输成本；覆盖尾批、host/resident与显存边界。
- 纯NTT选型增加分块时可能增加准备和同步成本。若完整曲线退化，补齐整条S4流水线的 batch 成本校准，不能放宽算术验证或把纯NTT收益冒充生产收益。
- 大 batch 样本目前有限；后续应针对生产实际请求补测，不能从batch=16推定batch=数千的真实性能。

## 完整曲线验证

使用上述冻结二进制，GPU1 RTX4060 Laptop，不修改设置；4070Ti/GPU0有独立任务。输入为521/2203/4423-bit完整梅森及M8011的7995-bit余因子，sigma26、B1=20；固定D/P、B2、预算。八组分别预热一次，off/on各三次正式采样，共64次运行。性能结果、设备频率/功率采样和算术边界的当前说明已提炼到[性能页](performance/STAGE2.md#短-ntt-分块选择)，本草稿不作为业务规则。

64MiB三组未改变分块，时间波动不代表优化。256MiB驻留4423/7995、小B2均慢约2.1%；host回退组约持平。以本机重新校准k17～19、batch1/4/8/16/32/64、19次采样后，B2放大至2.6×10¹⁰，4423约持平、7995仍慢2.1%。纯NTT吞吐拐点仍存在，完整S4分块代价未包含在当前选型模型内，默认继续关闭。

64次运行的GMP抽查/必需自检无错误，数学NTT数、因子及G根摘要A/B一致。四次最终独立诊断通过全叶子指纹、稠密拓扑、五阶段分块/请求容量、请求/S4顺序签名和NTT模型上界。CPUportable门禁及真实48条NTT记录的native/formatter排序、值保留、幂等检查通过。

诊断工具初版未启用leaf hash而退出，第二版将有意开启的fixture `clean=0`误判为失败；这两次日志保留。源码的clean标志表示额外fixture，而非算术正确性；门禁据此分别检查性能clean=1、leaf诊断clean=0，GMP和计数/指纹门限保持不变。GPU实现未因测试调整。

证据在`data/experiments/short_ntt_ab_20261010/`；统计在`data/benchmarks/short_ntt_ab_20261010_final/`，图在`data/figures/short_ntt_ab_20261010_final.png`。复用工具见[说明](../tools/bench/README_STAGE2_SHORT_NTT.md)。原始失败及预热均保留，没有改写既有证据。

后续应先校准完整S4请求的batch成本，尤其检查7995-bit通用归约在小chunk下的并行度，以及准备/检查/同步成本；尚需显存边界、其他GPU和真实生产B1验证。当前临时草稿保留，开发完成后由用户决定处理，不自动删除。
