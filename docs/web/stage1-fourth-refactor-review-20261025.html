默认、覆盖和错误的处理顺序

  1. 先解释来源。每个 CLI 值、每个 TOML 显式计算值都要做单值合法性检查，包括非当前 worker 和稍后会被覆盖的配置。记录原始值、位置、scope，不通过反复解析来保留诊断。
  2. 再合并有效设置。生成默认值 → 全局/对应 stage 配置 → 当前 worker → 显式 CLI；队列模式拒绝 curve、param、数量、save 等任务字段 CLI。别名按 argv 顺序，最后一次显式有效值优先。
  3. 再应用任务。每条 worktodo 复制基础设置，任务非零 sigma → CLI → 配置非零 sigma → 现有随机策略；save 前缀决定该任务的 curve/param。ECM/ECM2 缺 curves 补 100，缺 B2 补 0。
  4. 最后检查组合与计算限制。检查实际 curve/param/target、NAF、sigma 范围和后端资格，再冻结计算输入。非法任务仍标错跳过；配置/CLI 错误仍终止启动。

显式禁用：cache 空值表示现有默认，off/none/0/- 表示禁用，不得下一步再补默认。ckpt_seconds≤0 仍按既有规则禁用定期保存，不取消停止保存；不能只看 schema 展示文字就把负值改成非法。

静态缺口，待复现：ckpt_backups 的定义为 0..16，但当前生成绑定只转 int，normalize 再 clamp，-1/99 可能被静默接纳。重复 sigma 从有 param 前缀切到无前缀时，旧 param claim 也可能残留。两者应列入输入验收，先复现再按已确认规则修复，不以“兼容重构”掩盖缺陷。

能否“仅在读取时生成，用完删除”

  • 按需取得已经存在。短 publish/edit 锁不是从启动持有到退出；首次使用时创建载体，每次事务结束释放 OS 锁。长期 owner/批次 lease 则必须覆盖消费责任，不只保护最初读取。
  • 锁必须包住读改写。A、B 都读到旧文件，分别合并再替换，即使只在读取时加锁，后写者仍会覆盖先写者。原子替换保证单次文件不撕裂，不保证两次更新都保留。
  • 纯读可以细分。若全部 writer 原子替换、单文件旧/新任一完整快照均可接受，可评估无锁读。需要 fresh save 范围、多文件一致性、读后写或账本迁移时，应保留相应事务 gate。先在锁内取得字节快照，再锁外解析，是缩短部分读锁的候选。
  • Windows 独占 gate 可评估自动删除。现有 checkpoint/ledger 已示范 DELETE_ON_CLOSE；FileLock/QueueEditLock 的 share=0 独占实现可研究采用同策略。OwnerLease 是多个 worker 共用载体的字节范围锁，不能直接套“当前 worker 释放就删文件”。Microsoft CreateFileW 文档说明关闭时删除及共享限制。
  • POSIX 不宜释放后直接 unlink。已打开旧文件的等待者仍指向旧对象；删名重建后，新进程可能锁住另一个对象，两边同时进入。这个风险由 flock 的打开文件描述语义与 unlink 对已打开文件的语义推导而来。稳定载体有实际作用，不能按年龄清理。

程序自身退出，不代表其他 worker、GUI、feeder 或等待者都退出。全停机维护可以清理无用载体；运行时自动清理需要更强协调。将锁放进统一子目录能减少视觉干扰，却不减少逻辑锁数量，且所有参与程序必须采用同一资源映射，适合作为后续可选方案。

优先候选：目前有比残留文件更值得处理的问题

  1. P95 存在标志锁的回收协议。仅凭 mtime>60s 删除，无法区分崩溃与暂停/慢 I/O 的活跃 owner；旧 owner 退出时又无条件删除同名文件，可能误删后来者的标志。删除失败会立即 continue，绕过等待超时与 sleep，存在忙等风险。建议先做无 GPU 夹具，再以可靠 OS gate 替换内部 writer 资格。已确认相关程序成组升级，不支持新旧协议同时写同一资源。
  2. P95 feeder 未加入共同 writer gate。Stage1 在 sync/p95 外层取得 marker；feeder:538 直接调用无内部锁的 p95_write_worktodo_add，后者 prime95.cpp:216–268 是读、合并、替换。不同 .feeder.tmp / .ecm.tmp 只避免临时文件重名，仍存在最终 worktodo.add 丢更新窗口。应把共同互斥放到真实共享写入口，同时保留 save 先就绪、add 后发布及同步账本责任。Prime95 自身不参加此 gate 的限制仍须保留。
  3. 显式共用 internal results 路径的锁域不一致。Stage1 用 .ecm-ledger.lock；CPU Stage2 append_text_record 用 .publish.lock；CUDA Stage2 input.cpp:217 的 append 仅靠目标本体写句柄排斥同时打开写者。默认输出不同；显式共用时存在读旧内容、另一方更新、再覆盖的窗口，以及 Windows rename 共享冲突。已确认继续允许显式共用，先用无 GPU 双 writer 复现，再统一同一输出 gate；不以拒绝此配置代替修复，不改变 Stage2 完成一条 append 一条的发布规则。
  4. GUI 队列写入缺少共同 edit gate。gui_v2/views/pages.cpp:125 仅租用选中 worker；gui/worktodo_gen.cpp:850–928 校验 stamp 后替换，不取 .edit.lock。外部其他 worker 可在最后校验与替换之间推进同一队列。建议共享 worktodo 写入口使用短 edit gate，预览 stamp 继续表达用户确认的版本，不能互相替代。
  5. Stage2 的旧 worker gate 可列退役候选。在全部采用 OwnerLease 的新消费者之间重复，但仍拦截只用旧 gate 的旧版 Stage2。只有明确兼容并行范围后才删除；单任务 progress lock 与 GUI control lease 不属于重复项。

以上竞态是已定位源码路径和触发条件的候选，尚未做并发复现；不代表默认配置必然发生。锁的重复/残留本身也不是 30 秒收尾延迟的证据。验证应分别记录 acquire 等待时间、持有时间、重试次数、操作和资源路径，再决定性能优化范围。

推荐方案与约束

推荐：在已有 io/files 内收敛重复 OS 锁 Implementation；高层 Module 选择资源身份、短事务或长期 lease、等待/立即失败以及清理政策。先让同一资源的全部 writer 共用一个真实 Seam，再缩短允许缩短的临界区。Interface 提供明确错误，Locality 集中平台细节，Leverage 覆盖各真实 Adapter，不新增锁目录层级或转发类。

必须保留：共享队列支持不同 worker 并行；计算期间不持有队列 edit gate；outbox→queue edit 的锁序；P95 源与目标不同时交叉持锁；保存/结果/队列责任的提交顺序。统一 Implementation 不能偷偷把 .edit.lock 改成 .publish.lock，或把 fail-fast 改为等待。切换 lock 路径、协议或目录必须处理旧二进制及 feeder/GUI 的实际参与方式。

验收：双进程同 worker 拒绝、不同 worker 可并行；编辑与追加不丢行；park/flush 不丢责任；活跃 P95 超 60 秒不被偷锁、删除失败有界退出；feeder 与 handoff 两条任务均保留；条件性共用结果与 GUI 编辑竞态；终止后可重新取得 OS 锁。无 GPU 夹具优先，平台分别验证，避免用运行时批量删 lock 掩盖问题。

二、锁协议必须补齐的设计细节

  • 资源身份与完整参与者：列出每个共享文件的 Stage1、两种 Stage2、feeder 和 GUI 写入入口；同一资源使用同一身份和 gate。核对相对路径、大小写、符号链接及硬链接的现有处理；无法建立稳定身份时明确报错，不能静默分裂成两把锁。别名处理如需改变原有支持范围，单列说明。
  • 唯一取得点与重入：共享写入口覆盖完整读改写。上层已有 ledger/交接锁时，明确内部调用的持锁关系，避免外层锁住同一资源、内层再次获取导致自我等待。Module 内部隐藏需要已持锁的 Implementation，不向所有调用者暴露可绕过互斥的开关。
  • 锁顺序：列出 owner、checkpoint、outbox、queue edit、save、result 的实际嵌套。保留 outbox→queue edit、源 save 释放后再取目标 save；多结果路径按稳定顺序取得，避免重复取得同一身份。internal/submission 等不同用途指向同一资源的既有拒绝规则保持。计算期间不持有 queue edit/publish 短 gate。
  • 等待与错误：保留已有立即失败/有界等待政策，只有共享 writer 合同确有需要时再调整。用单调时钟预算，任何失败分支都受超时约束；区分被占用、权限、路径不存在与系统 I/O 错误，报告操作、资源、等待时长及系统原因。不能靠无限重试或吞错宣称成功。
  • 释放与残留：禁止按年龄清理活跃 OS 锁。Windows 独占 gate 的关闭删除、POSIX 稳定载体、共享 owner 的字节锁分别处理。锁清理和锁实现合并排在正确性之后；旧 Stage2 worker gate 的退役不是本轮通过的前提。
  • 升级与恢复：停止旧写入者后成组升级；旧纯 marker 的处理与业务 pending/intent 分开，不能删除后者。保留发送模糊状态的确认规则和旧档恢复能力；不要求用户手工迁移业务文件，不创建新的磁盘 schema。

共同 gate 只协调参加本项目协议的程序。Prime95 自身不取得该 gate；仍按现有 worktodo.add 交接方式及确认限制运行，本轮不宣称实现跨外部程序的完整事务。

三、明确失败后保留什么

锁获取失败不得使受保护操作假装成功或绕过必要提交点；必要写入失败保留原任务、checkpoint、完成记录或交接 intent 中相应的恢复材料。save 先就绪、任务后可见，结果持久化、完成责任记录、finished/源行推进和交接确认保持既定顺序。已持久化交接责任之后，源队列可以按现有合同推进；随后 flush 占锁失败保留 intent 待重试，不能一律回滚或重复计算。模糊发送不能盲重试；cache、备份等可选失败仍按已有政策报告，不能伪装成交接成功。锁统一不改变 Stage1 批内 sigma 排序，也不改变 Stage2 逐条 append。

四、输入重构中的缺陷与兼容清单

  • 允许修复的输入缺陷：先复现 ckpt_backups 越界被 clamp、重复 sigma 前缀残留。前者按已定义的 0..16 范围报错，附位置/键/值/范围；后者按最后一次 sigma 选项完整替换该选项携带的值与 param 声明，显式 --gpu-param 的独立冲突检查仍保留。每一次非法显式值都要报错。
  • 保留合法转换：负 ckpt_seconds 按零、cache 的空值与禁用标记、ECM/ECM2 缺省、任务字段冲突、sigma 优先级、路径基准与配置缺失策略均保持；不顺便收紧 gpu-info 显式缺失配置等行为。
  • 冻结与实时性：TOML 用一次启动快照，worker 基础设置冻结；worktodo 每轮重新读，当前任务计算字段冻结，后续任务仍可新增、删除、重排，完成按当前 worker 第一条同文匹配。claim/save 行数修复仍在有副作用的队列流程。
  • 实现收敛：沿用现有文件和真实 Adapter，不新增中转 manager；默认/范围只在现有配置定义维护，生成物随生成器同步。代码调整后核对文档、测试和来源诊断，不用放宽测试掩盖变化。

五、正式门禁与耗时记录

  1. 确定性交错：用 barrier/事件在真实读、写、替换和确认点制造竞争，不依赖大量随机运行。基线失败、候选通过；跨进程用例覆盖正常退出、强制结束、占锁超时与重新取得。60 秒过期场景可控制时间/mtime，不必让每个用例实际等待一分钟。
  2. 并发结果：同 worker 拒绝、不同 worker 可并行；feeder/handoff 两条任务均保留；GUI 编辑与 worker 完成不丢行、不复活旧行；Stage1 与两种 Stage2 共用 internal 时所有记录完整，单阶段排序/追加规则不变。
  3. 故障恢复：覆盖权限/替换失败、进程在关键提交点结束、park/flush 交错及模糊确认，核对恢复后既不漏已完成工作，也不重复推进任务。测试不通过就不进入下一段输入迁移。
  4. 复用现有合同：优先扩展 tools/test 的 storage_concurrency、stage1_host_io、worktodo/GUI ownership 和输入矩阵，测试代码仍在 src 外。锁关键用例不能只用同进程线程替代跨进程 OS 验证。
  5. 构建范围：先做无 GPU host 验证；阶段性构建所有受共享 IO 改动影响的 Stage1 CUDA/OpenCL、CPU/CUDA Stage2、GUI 与 feeder；输入迁移后跑真实 direct/queue/gpu-info，再做少量必要 GPU/恢复冒烟。Windows 为当前可用正式门禁；POSIX/Android 无运行环境时明确列为未验证，不据源码编译推断运行通过。
  6. 性能：记录构建/测试耗时、lock acquire 等待/持有与重试、约 1000 曲线小 B1 的 save→result→queue done 及独立进程峰值；有无长历史/同步配置分别测。同设备、输入、配置及二进制身份对照，不把组件峰值或嵌套计时相加，不预设提升比例。

构建目录先生成内部 .gitignore；冻结样本、失败日志、二进制身份和计时证据放在 data/experiments，原始证据不改写。现有合同证明的规则继续保留，新增测试命中真实 Interface，提升 Locality 与 Leverage，避免建立另一套测试执行链。
