形状、队列与资源

S 是当前算术模数位宽，P 是任一输入的系数容量，B 是 batch，b 是 digit 位数，s 是一个槽的 digit 数，n 是 NTT 长度，g 是 carry 工作组。形状入口 integer_shape 用精确整数除法替代 GMP 依赖，但遵循现有 CUDA ntt_shape_query 的相同公式。当前保留两份实现，以独立 GMP 夹具检查一致；共享纯规划模块仍待提取。

K = 2S + max(1, ceil(log₂P)); s = ceil(K/b); L = Ps
L(2ᵇ−1)² < q ⇔ L ≤ floor(floor((q−1)/(2ᵇ−1))/(2ᵇ−1))
选择最大的合格 b；n = 最小二次幂 ≥ 2Ps+1，n ≤ 2²⁹

整数检查支持2≤S≤16384，实际 digit 最大32位。carry 的 R=⌈64/b⌉ 轮 cone 把每个位置缩到0≤x≤2ᵇ；x=2ᵇ产生进位，x=2ᵇ−1传播，其余终止。工作组用 local memory 做前缀扫描，再由每个 batch 的一个工作项扫描组摘要。末端额外检查 R+1 个零扩展位置，避免 cone 预传播掩盖越界高位；有效输出之后的非零 digit 也拒绝。此实现不要求 warp、subgroup 或64位原子。

B频谱在卷积之后借作carry scratch，不新增第三份全长数组。两份模数数组、根表和调用方输入/输出另计；请求临时payload为 8B[2n+3n/g+(a+c)+(a+c−1)] bytes，a、c分别为两输入的实际系数数。预算限制由共同Runtime账本和单对象上限执行，没有生产arena或自动缩小D/batch。

所有步骤同队列有序提交，步骤间不插入主机等待。当前 multiply 末尾阻塞下载逐系数 verdict／carry 摘要，再返回成功；输出数值留在设备。输入位宽、槽高位、carry尾部、归约修复失败、结果不在[0,N)均拒绝；异常时该次输出无效。它尚不是跨树层延迟排空的生产接口。

普通模式输出模N的普通整数表示；梅森模式要求模数自身等于2ˢ−1，输出模M的普通表示。真实任务的N整除M判断、余因子承载选择与最终投影仍属于待接入的任务流程，不能据此宣布生产OpenCL已支持自动承载。

F=∏(X−bᵢ)，Gₖ=∏(X−gⱼ)，H初值为1，每块H←HGₖ mod F。逆级数常数项固定为1，使用Newton更新g(2−ag)，复合模数下不对任意非单位系数求逆。下降使用现有CUDA的scaled recurrence；没有替换为逐点Horner或每个节点重新除多项式。Horner和学校式多项式仅存在于独立GMP oracle。

补齐叶子是常数1，次数为0；非二次幂叶数不会引入额外零根。分组只合并同层同形状的独立请求；F树保留下降节点，G树结构只保留根。规则切片用buffer/offset/stride借用同一层allocation，不规则切片才复制。低层pack分别写A/B digit数组，允许只读同源输入，输出仍禁止与源owner相同。

预算边界

多个计划共用一份PolynomialWorkspace。发生明确的owned-payload预算不足时，只回收已空闲scratch，按同一形状、batch和精确性条件重试一次；不吞掉其他OpenCL错误，不降低数学工作量。系数输出分配同样可回收空闲scratch；F树、H、结果和pending lease不被驱逐。仍无自动减小D/P或batch的生产预算规划。

计算量与流量合同

令S为实际目标位数，w=⌈S/64⌉，C为点数，s为归一化段长，L=⌈C/s⌉，b为块积长度，K=⌈C/b⌉。以下是当前普通模数基线的操作计数，不是硬件周期估计；GPU时钟、整数指令调度和private spill会改变时间。

一次SOS Montgomery = 2w² 次64×64 MAC；另有进位传播（最坏O(w²)）及O(w)比较／校正
k>0、ℓ=bitlength(k)：ladder = 5 + 11(ℓ−1) 次模乘；OpenCL另有3次输入转换、2次输出转换
全部点：MAC主项 ≈ 2w² Σ[10+11(ℓᵢ−1)]；k=0只需5次转换模乘
正常分段归一化：L次扩展二进制GCD／求逆 + (8C+2L) 次Montgomery
块积：2C+K次Montgomery；GCD：每项O(Sw) limb级移位／比较／减法

归一化段积不可逆时，以独立kernel逐点恢复该段，额外最多C次逆元／GCD；零Z和互补因子仍可区分。当前每次归一化提交热路径和恢复kernel，各自等待完成，再下载检查状态；尚未合并事件等待。二进制GCD不是CPU/GMP的高性能多精度GCD算法，不能仅按操作数预测GPU更快。

3. 算术与 NTT：功能可行，性能的首要风险

3.1 保留 Goldilocks64 与当前精确打包

q = 264 − 232 + 1
264 ≡ 232 − 1 (mod q)
nterms · (2b − 1)2 < q

继续使用同一个 q、根约定、digit 宽 b、槽宽和精确性判定。nterms 是一个整数卷积系数的累加项上界，不是随意代入的多项式次数；执行形状必须由共享 shape query 给出。

OpenCL 的 ulong 低半乘积与 mul_hi 可组成完整 128 位乘积，也可以显式拆成 32 位部分积和进位。先实现可移植、规范范围为 [0,q) 的加减乘，再比较两种写法；不要依赖设备 C 编译器提供 __int128，也不要把 ulong2 当成自动处理进位的 128 位整数。类型与整数函数依据 Khronos OpenCL C 规范。

不要求 FP64。本方案是精确整数 NTT。AMD／Intel 的 64 位整数乘法实际生成与吞吐需要实测，支持 ulong 并不意味着与 32 位乘法同速。若原生高半乘法生成较差，优先比较显式 32 位拆分；只有测出结构性瓶颈后，才另立多素数 NTT＋CRT 方案并重新证明容量、重构和误差合同。

3.2 通用 NTT 先按工作组实现

设备源码维护建议：Goldilocks 公式、NTT 索引、pack/carry 与 S4 主体尽量共享，工作项索引、local/shared、同步和高半乘法通过明确原语接入。CUDA 已验证的 PTX／warp 优化保留为专属变体。可按 PRPLL 的思路用 NVRTC 编译共享源码，也可在构建期生成 CUDA C++；两种方式都需要证明适配语义与完整性能，尚未选定为正式实现。

  • 功能探针先用简单 radix2；完整性能路径采用 local memory 内融合 tile、全局 outer passes 与根表缓存。
  • 首版不要求 subgroup。CUDA warp32 shuffle、__syncwarp 及 launch bounds 需要重新组织；work-group barrier 必须由整组一致到达，不能机械替换位于部分线程分支中的 warp 同步。
  • 现有 outer_coop 是一个 CUDA block 内协作，不是整张 grid 的同步。可按工作组映射其索引与 radix 结构；跨工作组依赖仍以独立 kernel 和队列次序表达。
  • 工作组和 tile 根据设备及具体 kernel 的资源上限选择。不能照搬 CUDA 的 512-thread tile；建议先比较工作组 64／128／256、多个合法 tile 和 batch。
  • subgroup 版本后置，按实际支持的 subgroup 大小与操作选择，保留通用回退。不把 AMD、Intel 的执行宽度写成固定厂商常量。

依据：goldilocks_ptx.cuh:6、40；stage2_scalar.cuh:3、25、49；tile.cuh:209；outer_coop.cuh:1、15；parameters.h:7。同步范围见 OpenCL C 同步规范。

3.3 carry、S4 与点算术

carry 保留精确收敛、残余检查和越槽检测；通用 S4 保留 reciprocal 长除法和商校正；梅森路径保留折叠归约。诊断计数可以先用“每工作组输出＋后续归并”，避免把 64 位原子扩展设为准入条件；部分和范围与最终计数仍需证明，不能因兼容性降低检查强度。

Stage1 OpenCL 主路径使用 uint limbs，Stage2 当前使用 64 位 words。第一版 Stage2 建议维持 64 位规范数据布局，减少 pack／slot／树之间的转换；点内核先移植标量参考算术。若后续复用 Stage1 的 32 位点算术，应显式转换 limb、容器与 Montgomery R，先核对普通域值再接回 Stage2，不能仅强制转换缓冲指针。

4. 显存与低 CPU 队列必须同时设计

4.1 容量预算包含单对象限制

CUDA 版使用 cudaMemGetInfo；OpenCL 核心设备查询没有等价的通用“当前可用显存”承诺。建议使用显式 arena／fold／reserve 预算、本进程实际拥有量、可用的厂商查询以及真实分配结果联合准入。集显共享内存、其他进程和驱动保留空间都使“总内存−本进程占用”不等于可分配空间。

每个 Goldilocks 向量：8 · L · B bytes
A/B 两份工作区：16 · L · B bytes
L=227、B=1：每份 1024 MiB，A/B 合计 2048 MiB
tile 原始 local 数组约 8 · 2t bytes，另加 padding 与临时量

这里 B 是同一请求并行处理的卷积数量；公式仅描述对应工作区，不是全进程峰值。carry 是否借用 B、根表、raw、S4 输出、fold、frontier 与暂存都要按寿命分别入账。

除总预算，还需检查每次分配是否超过 CL_DEVICE_MAX_MEM_ALLOC_SIZE。即使总显存足够，单个 NTT 向量也可能放不下；sub-buffer 不能绕过父对象大小。优先减 batch 或选更小 P/D；batch=1 仍放不下时降低变换规模。跨多个内存对象分片访问属于另一个内核方案，首版不隐式启用。限制依据 Khronos 设备查询规范。

4.2 队列与等待

  1. 默认一条有序队列。pack、NTT、carry、S4 与下一层设备请求连续提交，依赖层间不插主机 clFinish。
  2. 按有限提交窗口或待回收事件节流；准备纯查询／休眠前明确 clFlush。仅等待最早必须回收的资源，不把所有后续工作一起排空。
  3. 非阻塞上传和读回的主机缓冲必须活到事件完成；GPU owner、根表、常量和 oracle 快照同样按事件寿命复用。第一版可用简单稳定暂存，之后才测 map／unmap 与主机分配选项。
  4. 计时、完成与错误事件分别处理；负执行状态为失败终态。最终 native wait／读回完成及所有 oracle 排空成功后才能发布。
  5. 不要假设 clWaitForEvents 或 clFinish 在所有驱动都低 CPU。比较原生等待和有界退避，记录进程 CPU 时间与墙钟；先复用已验证的等待原则，再做两个 GPU 时间窗口。

clFlush 保证提交而不保证完成，跨队列事件还需保证生产队列已提交；见 Flush / Finish 规范。本地 GPUOWL／PRPLL 的队列可作组织参考，不能复制其固定计数阈值当作 ECM 的时间预算。

不把 Graph 作为首版依赖。cl_khr_command_buffer 是可选扩展，能力与参数更新需查询；先跑通普通提交路径，再评估固定形状重放。Khronos command buffer 规范。

6. 分阶段交付与进入下一步的条件

P0 · 最小主机解耦与设备能力

完成条件：CUDA 行为保持；OpenCL 探针不链接 CUDA runtime；不支持的能力明确拒绝。构建文件夹先建立内部 .gitignore。只补必要入口，不进行全仓库 GPU 框架重写。

P1 · Goldilocks 与批量 NTT 小闭环

完成规范加减乘、根与正逆变换；先 radix2 正确性，再 local tile／outer；比较 ulong 高半乘法与显式 32 位拆分。覆盖小长度、生产长度、batch 与尾批，记录完整卷积吞吐。

P2 · S4 精确乘法与首条完整曲线

P5 · OpenCL tune、GUI 和发布资格
