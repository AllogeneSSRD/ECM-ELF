交接提交点与故障恢复

核心性质：Prime95 能看到任务行时，该行引用的 save 已完整发布并经校验。普通文件系统没有跨独立文件的一次 rename 事务。以 worktodo.add 发布为最后提交点，允许“文件已就绪、任务尚未可见”的可恢复状态，禁止“任务可见、文件缺失或半写”。

  1. 本地结果完成后，持久保存交接意图：源文件版本/曲线范围、目标路径、任务文本与目标 worker。
  2. 固定本批所需 save 内容，在目标目录写临时文件；完成写入、关闭与所需持久化检查，验证内容和范围，再原子发布目标文件。
  3. 目标文件就绪后才提交引用它的 worktodo.add 任务，保留已有队列内容；投递路径来自同一交接记录。
  4. 记录交接完成。文件失败不投递；队列失败保留就绪文件与待投递记录，重启续投，不重算 Stage1。

本地 worktodo 推进前，至少须有足够的持久完成/交接意图可供恢复；持久记录写入失败停止推进。普通备份失败独立报告，不作为 P95 文件就绪证明。

P95 的 skip/count 可定位累计 save 中的本批范围，允许稳定文件名继续增长；已经交付的记录前缀必须保持不变，不能截断、重排或用旧版本回退。目标文件发布时要保留历史前缀，并确认本次范围已全部就绪，再投递任务。需要验证 Prime95 并发读取、恢复去重和 add 已发布但完成回执未写的窗口；当前不能宣称跨程序恰好一次已解决。

ECMSTAGE1 的 skip 初始化与收尾校正

用户建议启动检测保存文件，并在 save 发布后强制复核，改写后的任务才进入 finished 与 P95 交接。当前 parse_save_line 不保存 B2/skip，ECMSTAGE1 的 skip 未参与 Stage1 点乘；新结构须保留并验证该字段，用于本批结果范围及后续交接，不改变 Stage1 数学工作量。

  1. 启动预处理：在本 worker 的 ECMSTAGE1 行中，对 skip=0 且指定 save 已存在的任务读取记录数，重写 skip。未找到文件和空文件均为0；读取失败须报告，不能当成0。按归一化后实际输出路径检查，兼容前缀与历史来源。相同文件在一次扫描中可复用计数，避免重复读取。
  2. 实际领取：再次确定当前文件中的批次起点。启动时校正不能冻结未来任务的起点：多个任务可能使用同一 save，前一任务会使其增长。运行/恢复使用稳定的本批范围事实；重启后不能把已写的本批记录误算成全部历史记录。
  3. 收尾强制复核：只有在 save 和结果发布成功后，重新读取总记录数，并验证本次记录的身份与范围。设原有 B、本次普通追加 C、收尾总数 E，则 E=B+C，输出 skip=B=E−C，curves=C；E−B 是新增数量，不能把 E 直接写入 skip。

一条非注释任务行作为一个完整逻辑记录：任务语义的修改按整条新记录处理，执行中不接受一半旧参数、一半新参数。它并不意味着操作系统对文本的一行写入天然原子。程序应在短编辑锁内读取最新文件、验证票据并提交完整新文件；执行期间只持有 worker 消费者所有权，不长期独占队列编辑。

现有 .edit.lock 是协作锁，普通文本编辑器不会自动遵守。原子替换保证发布一个完整文件，不能单独避免覆盖同时发生的外部保存；mtime 或散列的提交前复查也不是原子的内容比较并替换。要对并发编辑提供严格保证，GUI、工具和程序必须共同遵守编辑协议。任意外部编辑器只能做冲突检测和尽力保护，不能承诺绝不丢失更新。任务间 live edit 与多写者同时提交须分别说明。

4. CUDA workflow 与 checkpoint：推荐 A

方案优点缺点及适用条件
A：保留两条显式 workflow，统一阶段合同与必要的共用操作run_mont_stage1 和 run_edwards_stage1 均能线性阅读；顺序、错误和寿命一致；不同曲线、恢复布局和算法依赖仍清楚；不需要增加通用执行层。少量流程骨架会重复；共用政策变动时仍需核对两个入口，应靠相同的阶段合同和回归矩阵约束。
B：一个通用 workflow，曲线提供策略/回调真正完全相同的流程政策可以只实现一次；有多个形状相同的执行实现时，新增实现成本较低。需要证明阶段与前置条件确实相同；否则容易产生大量可选钩子、曲线条件和类型擦除，理解实际调用顺序反而更难，并与单任务编排重复。

建议形态：以共同词汇说明准备、恢复候选检查、布局选择、接纳恢复/构造新批次、设备执行、结果转换的前置条件与产物；每条 workflow 显式写出其顺序。采用3B后，最终 save/结果发布属于 task，不再留在 workflow；中途 checkpoint 仍在安全点参与。

checkpoint 子方案：复用现有批次容器与持久提交器，统一 encode/decode/restore/save 的职责与返回约定，载荷和几何校验仍由曲线 codec 拥有。decode 解释单份载荷，restore 处理读档、候选与接纳，save 完成已定义的编码/提交。无需把两种曲线强行改成同一种内部载荷，或为统一名字新增一层转发。

推荐依赖顺序：1B 与2B先收口入口；明确3B的结果和发布归属后，再按4A整理两条 CUDA workflow。可以分批迁移后端，但每批都须有一个明确的执行与发布责任人，不能让新旧路径同时提交同一批次。各轮继续沿用此前默认/优先级、队列匹配、保存区间、停止恢复和交接语义，性能改善以实际测量为准。

构造身份、执行算法、实际布局分开

  • 构造身份：Montgomery/Edwards；Montgomery的param0/2/3；显式sigma或待解析的sigma策略，以及N、B1、标量约定等。param在归一化结束时确定，执行中不改；一条任务和一个GPU批次使用一种构造。
  • 算法要求：ladder、resident、PRAC等属于执行选择，不能通过切换param满足要求。现有CUDA代码的resident/PRAC还受编译能力约束，并限制param0；可判定的非法组合应尽早给出明确错误。
  • 实际执行布局：设备、容器位宽、TPI、缓冲区和内核实例在后端准备/恢复接纳时确定。它必须兼容已固定的构造与有效checkpoint；不能以换param或丢弃进度作静默回退。

未指定sigma时，归一化保存的是策略，不应提前生成随机值并覆盖恢复种子。有效checkpoint的sigma先接纳；只有新批次才调用生成器。显式sigma须与恢复状态一致。算法/布局的用户要求、checkpoint记录和设备能力分别核对，沿用现有显式冲突拒绝及恢复语义。

一个 Mont workflow，param 贯穿必要阶段

保持公开的 run_mont_stage1 一个入口。param0/2/3分别提供有差异的构造、内核能力、布局描述及编码规则，不再各建完整的任务执行链。普通输入解析也不应把param当作执行后期的内核开关。
