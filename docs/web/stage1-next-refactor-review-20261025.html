  • 消除新流程对旧任务状态的依赖。
  • 失败与停止优先级在实际发生处表达。
  • 沿用现有task与发布测试Interface。

代价与边界

  • 必须逐个核对采样、设备故障、checkpoint写失败和最后一片停止。
  • Mont数组适配确有必要，不能为了去Legacy而改变内核布局。
  • 不改task/队列发布归属，不新增Runner或通用工作流。

验收：点/因子/sigma与0.53.1逐项一致；全无点与部分无点正确；显式失败优先；最后一片完成后正常收尾；失败保留完成材料；CUDA workflow不再创建LegacyExecutionResult。新增窄测试须走同一个计算Interface，而非另一套测试执行链。

方向：让任务作用域实际拥有批次状态、pending候选与文件锁，后端明确借用；容器负责候选和持久提交，曲线层负责数学/布局资格。这个Module拥有真实资源，增加Depth，而不是给全局函数再套一个类名。

优点与 Leverage

  • 寿命、清理责任和调用约束可见。
  • 顺序任务之间的状态隔离更易测试。
  • 候选接纳职责更集中。

代价与边界

  • 三项中范围最大，涉及CPU/OpenCL/CUDA多处调用。
  • 仍保持同进程单活跃任务，不顺带增加并发执行。
  • 锁内validator当前有明确限制；不能只为减少持锁而直接移出锁。

验收：主档损坏回退、无关有效主档拒绝、seed-only、恢复sigma、不可用布局、旧GPU导入、已完成恢复不重算；完成checkpoint保留至队列提交；两个顺序任务不残留状态。不同曲线载荷继续分别编码。
