本轮已验证的问题与待核实项

发现证据／影响建议
位宽输入解释不一致直接运行真实生成函数：384,1024生成8个实例；384, 1024只生成384对应的4个。生成器未trim，而根CMake后续的宏生成执行STRIP。先归一并校验，再供生成、宏、分派及身份使用。本轮未做完整链接失败复现，不扩大为已证实的运行损坏。
未知档位未在生成阶段拒绝999生成0个实例而函数成功退出；仅留下3个runtime／registry TU。错误指出键、值及可用档位；重复档位归一去重，未知档位提前拒绝。空串仍代表全档，分隔后的空片段需明确诊断，规则一处定义。
功能过滤晚于排布生成器枚举param0/2/3及全部行；dev限制和NO_PARAM2主要交给预处理，可能生成空工厂。正式脚本通常full build且PARAM2开启，因此不能称默认完整构建错误。有效实例集合提前应用编译功能选择；缺失功能继续明确不可用。
寄存器覆盖项随布局不同SMALL／SUYAMA仍给旧grouped路径设置属性；isolated另在生成器处理旧CUDA固定上限。明确当前默认、显式覆盖及工具链回退的优先级，不能静默忽略用户覆盖，也不能顺手改变已验证默认。
生成依赖与成员枚举还可收口当前生成器依赖正则和文件路径；新增档位时还要保证CMake重新配置。此处为源码检查，未运行自动重配置故障复现。将清单／模板纳入显式配置依赖；输出当前实际模块目录，不从旧生成目录glob成员。

生成试验含全档、三档、两档、空格输入和未知档位五种配置；各重复一次，已有文件内容和mtime均保持。证据：data/experiments/stage1_instance_layout_20261026/inventory.json及同目录生成物。没有新NVCC编译或GPU运行。

实施时要保护的真实Seam

  1. 旧CUDA寄存器控制：NVCC<12.6会移除__maxnreg__；普通Mont isolated由生成器按位宽补56／128／255的TU级上限。PRAC不同mode的168／128／255不能在旧工具链中靠同一个TU上限同时表达，需明确现有限制及进一步拆分政策。
  2. 实际可用性：理论档位、已编译实例和设备occupancy是三件事。声明可以读取完整类型表，可执行集合以真实工厂为准；纯元数据枚举继续不初始化设备。此前已列出的受限位宽查询／执行差异仍作为独立正确性候选，不因删除双布局而顺手改变选档规则。既有checkpoint按保存的BITS／TPI验证，不借重排改变恢复布局。
  3. 增量与身份：稳定命名和内容写入；完整记录模板、生成器、生成入口、编译命令、头依赖和对象。正常主机修改仍不触发设备重编；候选头仅影响相应family。缓存、配置、原产物不通过改写manifest伪装兼容。
  4. 打包：package_release.py直接识别生成目录和edwards_<bits>／montN_<bits>名字，并核对曲线／param／容器。基础命名首轮可保持；PRAC／算法拆分扩展时同步模块目录和成员检查，不能只让编译通过。
  5. 独立probe：Edwards Stage1 probe无worker时直接消费旧源清单，复用worker时才识别生成入口。删除源码壳后两条路径都要接同一实例生成，不能未经确认改成必须有worker。
  6. 算术与发布：不拆散kernel及其设备辅助函数，不因减少文件引入RDC／跨对象设备调用；维持原SASS／PTX目标、架构条件宏、PRAC可用模式与磁盘格式。源码文件名会影响匿名符号，SASS对照只允许明确的身份差异，不能放宽指令／模板几何核对。

Lazy Loading仍须观察实际加载范围，不能仅凭125个源文件宣布通过；查询函数也可能提前触发加载。参见NVIDIA Lazy Loading文档。Stage2的grouped默认与隔离备选不在本轮改动范围。

已有编译记录只能帮助选验证点，不能证明新方案更快

复查上一轮0.53.5构建：sm89、384/768/1024、PRAC开启、isolated、Jobs=6、CUDA13.3.73／MSVC14.51.36231，共27个CUDA TU全部编译。编译队列墙钟146.260秒；最长单元为PRAC small，128.921秒；Edwards单档最大60.022秒。这些区间并发重叠，不能相加，也不能把移除某单元的时间当作可节省墙钟。

这支持把PRAC的小位宽聚合长尾列为验证重点；它没有提供新旧排布的受控对照。源码改动和生成策略不等于编译工作量下降：更细粒度同时增加CGBN解析、编译器进程、对象和内容核验开销。

现有历史无改动release记录另表明，逐对象内容核验本身也有成本，见构建说明。本轮没有新的耗时／内存对照，不承诺“拆得越细越快”，不修改核验规则换取数字。

建议的实施门禁与测量范围

  1. 先冻结集合：保存当前完整／受限构建的实例成员、工厂、几何、可用mode及寄存器政策。无NVCC验证全档、dev、PARAM2关闭、PRAC关闭／开启和稀疏候选；覆盖非法值、空格、重复配置稳定mtime、删除档位后的目标成员及唯一符号。
  2. 先统一基础路径：保持125模块及现有命名，只删除grouped源码壳、分派分支和重复源清单；独立probe及直接CMake一起迁移。生成器输出原样绑定模板，不解析改写算术正文。
  3. 再统一PRAC排布：标准family先按几何生成，候选family保持隔离；只列当前支持的组合。明确旧工具链的寄存器约束后再决定是否需要按mode进一步拆分，最终也由同一生成机制管理。
  4. 真实编译与资源测量：在独立忽略目录对同工具链、相同架构／宏／功能的基线与候选做冷构建、无改动复用和局部改动构建。先测384／4608／16384及Edwards17408、PRAC4608，再完成11.8／13.3发布覆盖；记录Jobs、内部线程数、CPU、RAM、功耗设置及并发负载，每个对照至少3轮并交错执行。
  5. 分开计时：configure／生成、依赖核验、NVCC队列及各phase、链接／镜像检查、整入口墙钟分别记录。采集进程树CPU与同时刻工作集总量峰值；不能把各进程各自峰值相加充当进程树峰值。
  6. 运行合同：两曲线和param0/2/3、binary／NAF、resident／PRAC逐点对照，包含受限档位选择、缺失功能、停止恢复和已完成补发布。检查发布镜像、寄存器／spill及冷／热PTX加载范围；布局变化不能只凭数学端点相同就宣称JIT资格相同。
Top recommendation

选择B：一个实例清单，一种生成排布

首轮保持当前普通路径粒度，合并配置选择和生成职责，删除28个手工分组入口及双分派；随后把PRAC的宽度分组换成同一机制生成的稀疏family／geometry。这样减少仓内机械文件和隐含规则，保留不同算法真正需要的独立编译。

暂不默认拆成每核一个模块，不合并Stage2生成器，不更改checkpoint。Edwards按算法细分、PRAC仅为性能而按mode细分，以实测编译资源／加载收益为条件。旧NVCC若必须同时兑现不同寄存器上限，按cap隔离属于实现约束；首轮冻结既有实际政策，不顺手新增旧PRAC尚未提供的保证。

与下一轮重构规划关联。本节为实施前的建议；开发草稿保留，后续由用户决定处理。
