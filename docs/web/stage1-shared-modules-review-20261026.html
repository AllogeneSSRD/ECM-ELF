文件收口之后，仍有三处值得真正简化

OpenCL旧结果模型

LegacyExecutionResult唯一生产构造在OpenCL workflow。其原始数组、重复状态字段和转换方法仍污染共同内部合同；部分typed分支只由测试人工构造。等OpenCL直接产生ComputationResult时，可删除旧模型及转换，而非把它复制到新的result_adapter文件。

take_computation_result包含状态与失败优先级，并非无意义转发。深化前保留当前Preparation/Execution/Stopped区分、direct退出码及发布失败优先级；同时验证分配失败、部分初始化、停止和真实OpenCL PARAM3恢复。

CPU进度状态的任务拥有权

cpu_runtime中的meter、最大进度、节流、完成数与widget应最终归当前任务的Stage1Progress拥有；回调借用。不要为此另建ProgressManager。这个改动涉及连续任务状态、回调并发与日志协议，独立验证，不伪装成文件重命名。

已提出的公共数学checkpoint、固定标量/NAF计划和每曲线恢复分组，继续收在现有Stage1及两条曲线目录。本页先消除preparation杂项，不新增execution_context、restore_service或第二个准备流程。之后如果由task统一生成标量计划，再单独调整backend调用时点、缓存身份及日志；本轮函数归位不预先执行该行为变更。
