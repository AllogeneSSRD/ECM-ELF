源码审计生成算法 ≠ 分配形态 ≠ 恢复规则

各后端sigma：只有两套生成器，分配与恢复规则仍然分散

生产代码有2套随机生成实现、3种随机分配策略和1种固定分配策略。CPU、CUDA、OpenCL和Android已经复用了生成函数；主要可减少的是各执行路径重复选择固定值、保存值或随机值，以及各自维护范围检查。不能把不同分布和不同批次形态直接算作重复算法。

生成器实现与状态实际值域使用约束
random_sigma_u64
本页简称R53		进程级srand/rand，首次按秒播种；MSVC x86/x64每次混入rdtsc。返回值不合格时重试。6 ≤ sigma ≤ 2⁵³−1。函数名中的u64表示存储类型，不表示全64位均匀随机；也未证明在53位范围内均匀。共享全局随机状态，当前CPU在启动工作线程前串行生成。不同平台的混合方式不同；不保证不同进程或worker不会重复。
gpu_pick_random_sigma(C)
本页简称R32(C)		每次建立并销毁GMP RNG；用time、PID、高精度时钟组合播种，再做有界抽样。不执行GPU代码。1 ≤ C < UINT32_MAX时，起点位于[1,2³²−C]；连续展开后最后一条可为UINT32_MAX。C=0或UINT32_MAX时直接返回2，是另一个需要明确的特殊合同。一次调用只生成一个起点。当前源码注释把正常上界写小1；特殊C返回值不能解释为已验证可执行批次。

同一个生成器可以形成不同的曲线集合

设C为曲线数，i从0开始。三种随机策略分别为：每条独立R53、一个R53起点后按base+i展开、一个R32(C)起点后按base+i展开。固定输入统一采用显式base+i，但已保存sigma的验证时点与覆盖行为仍有差异。

例如C=3，CPU Montgomery随机模式可能得到[a,b,c]，CUDA Montgomery PARAM0得到[a,a+1,a+2]。即使把底层随机引擎换成同一种，两者也不会自动获得相同曲线集合。曲线、param、sigma已经确定后才是相同构造身份；不能为了统一Module而改变这些输入。

CUDA Montgomery PARAM0
普通ladder		一个R53起点，base+i；1次。runtime先验证payload或取已保存起点，只有缺失时调用生成回调；检查全批连续性。base+i，最后一条≤UINT64_MAX。随机起点受R53限制，固定输入可以使用64位；后续lane不受R53生成范围约束。

CUDA resident / PRAC PARAM0
可选编译路径		复用Montgomery回调，一个R53起点，base+i；1次。不是第三套生成器。有效payload或已有起点优先，仅缺失时抽样；保持连续性。通用末条范围检查外，入口还多留一个数值位置，见下节。

binary/NAF共用		每曲线独立R53；全新C次。完整payload恢复不抽样；逐曲线先saved_sigma，仅为缺失项抽样。允许保存任意sigma数组。base+i，64位不回绕；固定输入并不被R53随机范围限制。

以下依据来自当前源码与整数条件比较，未进行真实GPU或Android设备复现。应先用最小回归固定期望行为，再修复；不得借整理文件静默改变数值范围或恢复语义。

候选问题当前证据与影响后续验证条件
OpenCL上界少1归一化、CUDA、OpenCL workflow及Android外层允许base+C≤2³²；OpenCL engine要求base+C≤2³²−1。C=1、base=UINT32_MAX时，外层接受而engine拒绝。R32(C)的最大输出也会遇到此条件。检查kernel展开所需真实范围；覆盖C=1及多曲线的最后一个合法值、越界值、固定输入与受控随机最大输出。外层/engine不能各自选不同规则。
PARAM2下界未传入生成器R32(C)允许1，set_p_2p_param2拒绝sigma0<2。当前没有抽到1再重抽的逻辑，因此随机候选不一定满足构造条件。受控生成器返回1/2，验证参数诊断与正确候选范围。不要静默改写用户固定sigma；随机范围应按构造要求明确。
Android固定sigma可能被旧存档覆盖Android仅构造Context，未调用begin；engine直接采用header.sigma。桌面则由Context begin验证固定冲突，不能把桌面保证推广到Android。相同任务下准备不同sigma的有效存档，测试随机恢复、显式匹配、显式冲突。若统一拒绝冲突，需要把“显式固定”信息带到实际验证入口。
resident早期检查多留一个值入口要求base≤UINT64_MAX−C；后续按UINT64_MAX−(C−1)检查。C=1、base=UINT64_MAX时两个条件不同。先核对设备侧是否确实需要额外数值位置，再对相邻边界运行受控测试；不可直接把入口放宽当作纯搬移。
已经恢复仍先消耗随机候选Context::sigma可以返回保存值，但函数实参先求值，无法取消已发生的random调用。CPU Ed、部分CPU Mont seed-only及OpenCL与CUDA顺序不同。以可计数的随机来源覆盖完整恢复、seed-only、部分缺失与坏payload；采用保存值时是否零抽样要作为单独行为合同。
注释、名字及诊断分散R32正常范围注释少1；random_sigma_u64没有表达53位随机范围。Prime95兼容提醒仅Mont CPU实际调用。说明按实现修正；固定64位可用范围、随机抽样范围、外部格式提醒分别验证，不能把警告改成统一拒绝。
Context::sigma只负责“已有值优先/缺失时登记”，不独自承担完整冲突校验。桌面冲突检查位于begin及延迟payload验证之后；旧候选导入也可能按既有规则跳过不匹配候选。共同Module必须使用已验证的保存值，保留“缺失、无效、不兼容”的差别。

将R53与R32集中到轻量sigma.cpp/h，删除分散归属；不更换算法、状态、调用顺序或随机分配形态。Android改为包含真实头，继续窄链接并保留C导出符号。这个范围把两个分散的实现拥有者收成一个Module，仍保留两套算法，并不声称消除后端的全部选择代码。

B. 选择与范围归一：最有价值，单独明确行为

在同一个Module集中固定连续、随机逐曲线、随机连续这几种已有策略，并统一批次溢出检查与构造范围。PARAM2下界等由构造规则决定，不能仅用“CPU/GPU”区分。checkpoint读写和数学payload验证留给现有拥有者，避免引入SigmaManager、额外注册层或对IO的反向依赖。

  1. 先完成checkpoint与数学payload验证，特别是当前CUDA的pending验证；不能为统一入口就提前生成全部sigma。
  2. 显式固定输入按既有身份校验；正常保存值与显式输入冲突时应报错。旧候选导入维持候选筛选规则，不能混同最终任务冲突。
  3. 无显式输入时采用有效保存值；只为缺失项生成。任意数组保持索引，连续批次验证完整base+i，不能重抽或重排保存值来凑连续。
  4. 先检查C>0，再按base≤最大值−(C−1)表达“末条不溢出”；若后端另有算法限制，应在同一规则中明确说明。
  5. 不引入自动去重或退化曲线重抽。因子发现、构造失败属于数学结果，不能通过替换sigma掩盖。

这一阶段可删除多处“先随机、再覆盖”的模式及重复的base+i范围条件，但会改变恢复任务对随机状态的消耗，进而改变后续随机序列；Android显式冲突校验也是可见行为调整。应单独验证和说明，不能归入纯文件迁移。

C. 单一随机引擎：可研究，不建议附带实施

可以进一步改为任务拥有的一个随机引擎，加不同有界抽样规则，替代全局rand/TSC与每次创建的GMP RNG。优点是状态寿命、可控测试和平台语义更清楚；代价是随机来源、播种、分布与序列变化。即使采用同一引擎，逐曲线随机与连续批次仍应显式保留。

当前没有随机序列跨后端相同或跨worker唯一的保证。若需要避免不同任务重复曲线，那是可持久化的曲线分配规则，单独换随机引擎不能提供这种保证。

预计收益与计时限制

可以减少规则分散、无效候选抽样和边界漂移。R32初始化成本只出现在每次起点抽样；全新C条任务中CPU Mont抽C次、CUDA Mont只抽1次，但这不是两者Stage1总耗时的可比数据。本轮没有计时或设备测试，不承诺可感知提速，也不能据此解释此前约30秒的结果发布延迟。

推荐次序：为上节差异补最小确定性回归，单独修复确认的缺陷；随后完成A；再按B统一选择规则。C留待确有随机来源或可复现需求时评估。A和B均可收在既有sigma文件对，不再增加后端通用包装文件。

OpenCL旧结果模型

LegacyExecutionResult唯一生产构造在OpenCL workflow。其原始数组、重复状态字段和转换方法仍污染共同内部合同；部分typed分支只由测试人工构造。等OpenCL直接产生ComputationResult时，可删除旧模型及转换，而非把它复制到新的result_adapter文件。

take_computation_result包含状态与失败优先级，并非无意义转发。深化前保留当前Preparation/Execution/Stopped区分、direct退出码及发布失败优先级；同时验证分配失败、部分初始化、停止和真实OpenCL PARAM3恢复。

CPU进度状态的任务拥有权

cpu_runtime中的meter、最大进度、节流、完成数与widget应最终归当前任务的Stage1Progress拥有；回调借用。不要为此另建ProgressManager。这个改动涉及连续任务状态、回调并发与日志协议，独立验证，不伪装成文件重命名。

已提出的公共数学checkpoint、固定标量/NAF计划和每曲线恢复分组，继续收在现有Stage1及两条曲线目录。本页先消除preparation杂项，不新增execution_context、restore_service或第二个准备流程。之后如果由task统一生成标量计划，再单独调整backend调用时点、缓存身份及日志；本轮函数归位不预先执行该行为变更。
