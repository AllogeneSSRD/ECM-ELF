## 1. 已确认的事实（不重复推导，只列结论与出处）

1. **靶子**：Prime95 的 stage 2 吞吐 28.6 s/曲线（B2≈4.4e11），参数由它自选：M5261 → `D=1411410, poly_size=132480, stage2-fft=320`（`DEV_STAGE2_SELFHOST_FEASIBILITY.md` §2）。
2. **stage 2 的两种实现**（用户观察正确）：`ECM_STAGE2_PAIRING(0)` 与 `ECM_STAGE2_POLYMULT(1)`（`ecm.cpp:1464-1471`），`numvals ≥ 200` 时 Prime95 选 polymult（`ecm.cpp:6010-6012`）。
3. **两者的算术量级差**：pairing 每个候选素数 ≈ **1 次模乘**，候选数 ≈ `(B2−B1)/ln B2` ≈ **1.6e10 次/曲线**（B2=4.4e11）；polymult 通过乘积树/余式树把它压到 **≈1/10**（`ECM_Montgomery_STAGE1.md` §16.3-16.4 + 本文 §2.2）。
4. **旧判定（CPU 视角）**：`ECM_Montgomery_STAGE1.md` §16.5 —— 移植 polymult ✗（等于重写 GWNUM FFT），pairing ⚠（只在 B2/B1 ≲ 100 划算）。**该结论的算术前提是"我们只有 IFMA schoolbook"**；GPU 平台改变了这个前提（§2.3）。
5. **本次新增实测（关键，且它改变了本规划的结论）**：CGBN `mont_mul` 的**独立吞吐**（`instances=1e6`、值常驻寄存器、每 instance 一条依赖链，故这是满占用下的吞吐而非访存下界）随档位变化（RTX 4060 Laptop，`cgbn_op_probe.exe`，`XMP_WMAD`；`instances=8` 时是纯延迟，如 `<16,4096>` 为 1039 ns/op）：

| tier | CGBN 档位 | 独立吞吐 | ns/op | 备注 |
|---|---|---|---|---|
| 0 | `<4,512>` | **1780.9 Mops/s** | 0.56 | 512 位级（非本议题） |
| 1 | `<8,1024>` | 475.4 Mops/s | 2.10 | |
| 2 | `<8,2048>` | 141.1 Mops/s | 7.09 | |
| 3 | `<16,3072>` | 60.6 Mops/s | 16.50 | |
| 4 | `<16,4096>` | **35.7 Mops/s** | 28.05 | **M3571–M4096 档** |
| 5 | `<16,8192>` | **9.8 Mops/s** | 102.37 | M5153–M8273 档 |

   * 复现：`nvcc -O3 -arch=sm_89 -DXMP_WMAD … tools/bench/cgbn_op_probe.cu`（recipe 见 `docs/ECM_CGBN_OPTIMIZATION.md:763`），再跑 `probe_wmad.exe <tier> 1000000 200 1`（device=1）。
   * 相邻档位的成本比与 **n² 学步**吻合（`<8,1024>→<8,2048>` 实测 3.4×，理论 4×；`<16,3072>→<16,4096>` 实测 1.70×，理论 1.78×）⇒ 速率由"每次乘法的真实工作量"决定，而不是被某个访存/占用瓶颈卡住。
   * 对照 CPU：我们 AVX512-IFMA batched-8 一次批模乘 2020 ns（`ECM_Montgomery_STAGE1.md` §11，n52=58 ≈ 3584 位）⇒ 每核 3.96 Mops/s，24 线程 ≈ **95 Mops/s**。
   * ⇒ **在我们真正需要的 4096/8192 档，GPU 的 bignum 模乘比 24 线程 IFMA CPU 慢 2.7–10×**（`35.7` 与 `9.8` vs `95`）。这是本规划最重要的定量事实：**凡是"每次运算 = 一次系数模乘"的算法（pairing 正是如此），搬到 GPU 上不会变快，只会变慢。** GPU 的优势必须来自**把模乘换成浮点 FFT**（见 §2.2）。

## 2. 两条 CUDA 路线与定量模型

### 2.1 Route A：BSGS / pairing（简单，先做）

**算法**（经典标准延续，Prime95 的退路实现我们也照抄其结构）：

1. **Baby 表**：`x([j]Q)`，`j` 遍历 `[1, D/2]` 中与 D 互素者（`|Rs| ≈ 0.2·D` 个点），常驻显存；
2. **Giant steps**：`[iD]Q`，`i = 1 .. (B2−B1)/D`，每步 ~10 次域乘；
3. **配对累加**：对每个候选素数 `p = iD ± r`，把 `(x_p − x_r)` 乘进累加器 ⇒ **每个候选素数 1 次模乘 + 1 次减法 + 1 次查表**；
4. 每曲线结束 1 次 GCD（host 端 GMP）。

**工作量与时间**（B2 = 4.4e11，单曲线）：

| 项 | 值 | 出处/推导 |
|---|---|---|
| 候选素数 | ≈ 1.6e10 | `(B2−B1)/ln B2` |
| giant step 开销 | `(B2/D)·10` ≈ 3.1e6 域乘（D=1.41e6） | 可忽略 |
| 总配对 op | ≈ **1.6e10** | 每 op = 1 模乘 + 1 减 + 1 查表 |
| @ 4060 实测吞吐 35.7 Mops/s（`<16,4096>`） | **448 s/曲线** ✗ | 比 Prime95 慢 15× |
| @ 4070 Ti（SMs 60 vs 24，约 2.5×） | ≈ 180 s/曲线 ✗ | 仍慢 6× |
| @ 24 线程 IFMA CPU（95 Mops/s） | ≈ 168 s/曲线 ✗ | 与 `ECM_Montgomery_STAGE1.md` §16.4 的 600–1200 s 同量级（该表含额外开销） |
| 要在 6 s/曲线内跑完，需要 | **≥ 2.7e9 ops/s** | = 28× 整机 CPU 的模乘速率 |

* **内存**：`D` 只是旋钮 —— **配对总数与 D 几乎无关**（`0.2·(B2−B1)/ln B2`，D 被消掉，`ECM_Montgomery_STAGE1.md:1548`）。D = 1e6、4096 位容器 ⇒ baby 表 ≈ 2 × 448 B × 2e5 ≈ **180 MB**，8 GB 显存绰绰有余；D 取 1e5 只需 18 MB。
* **GPU 适配性**：规则、无发散、可完全批量化；唯一不友好的是**每个 prime 一次随机查表**（可按 `i` 分块排序、或把 baby 表按 DRAM 行组织来缓解）。累加是串行链 ⇒ 拆成每曲线 8–64 个部分累加器再合并。
* **判定（据本次实测修正）：把 pairing 放在 GPU 上做性能没有出路。** 它需要 2.7e9 ops/s 才能达到 6 s/曲线，而 GPU 的模乘速率只有 3.6e7（4060）/ ~9e7（4070 Ti）——**比它需要的低 30–75×**，比 24 线程 CPU 还慢 2.7–10×。CGBN 的 TPI 布局（每线程 4 个 limb 却要多次 `__syncthreads`）与 GPU 缺少 52 位 IFMA 是根本原因；即便自研线程级 modmul kernel 把效率提 5 倍，也只到 CPU 水平。
* **Route A 的新定位**：① **正确性沙箱**（用最简单算法打通 save → stage 2 → GCD → results 全链路，建立对拍 oracle）；② **无 Prime95 环境的兜底**，但应在 **CPU 的 IFMA batched-8 上做**（那才是我们最快的模乘），而不是 GPU；③ 只在小 B2（B2/B1 ≲ 100）有意义。

### 2.2 Route B：polymult-class（Bernstein 乘积树 + 余式树）

**算法**：与 Prime95 同构（`DEV_STAGE2_SELFHOST_FEASIBILITY.md` §1.1）——`F(X) = Π(X − Q^{r_i})` 乘积树 → `1/F` Newton → 每个 outer loop 生成 `G(X)` 并做 `H = G·H mod F`（3 次全尺寸多项式乘法）→ scaled remainder tree 下降 → 累加 → 每曲线 1 次 GCD。

**每曲线算术量**（M5261 参数 D=1411410、P=132480、num_polyG≈11）：≈ **30 次 `P×P` 多项式乘法** + `O(P·log P)` 量级的小多项式乘 + ~1.5e6 次点加法。

**与 §16.4 旧判定的关键差异（这是本次规划的核心新增）**：
旧判定把"多项式乘法"当成**一次 D×4000 bit ≈ 4e9 bit 的大整数乘法**，然后论证 schoolbook/Karatsuba/Toom 都不行 ⇒ "必须用 FFT ⇒ 即 GWNUM ⇒ 不做"。
在 GPU 上还有第三条路：**Kronecker 代入 + cuFFT 的浮点 FFT 大整数乘法**（把多项式按 `B = 2^(每系数位数)` 打包成一个 ~6.7e8 bit 的大整数，一次 FFT 卷积即得整个多项式乘积）。纸面估算（P=1.3e5、N=5153 位、单次 polymult）：

| 步骤 | 数据量 | 估算 |
|---|---|---|
| 打包（Kronecker） | 6.7e8 bit ≈ 84 MB | 1 遍遍历，~0.2 ms @ 400 GB/s |
| cuFFT（15-bit 分块，双精度） | 变换长度 ~9e7 复数 ≈ 720 MB/缓冲 | 约 4–5 遍全量访存 ≈ 12–15 ms |
| 点乘 + 逆变换 | 同上 | 再 ~10 ms |
| 系数回流 + 逐系数 `mod N` | P 个 2N 位值 ≈ 335 MB | ~1–3 ms（GPU）|
| **一次 polymult 合计** | | **≈ 25–40 ms**（纸面，**未实测**） |
| ⇒ 每曲线（×30） | | ~~0.8–1.2 s ⇒ 快 24–35×~~ **已被实测否掉：真值 53–65 s/曲线（慢 ~2×），见 §10** |

* **为什么 GPU 偏偏在这里有优势（与 Route A 的对比就是全部答案）**：Route B 把 `1.6e10` 次"系数模乘"**换成**了 `~1e9–1e10` 次**浮点 FFT 蝶形**。模乘我们 CPU 的 IFMA 比 GPU 快 2.7–10×（§1.5 实测），而**浮点吞吐 GPU 比 CPU 快 ~100×**（4060 vs 24 线程 AVX-512 的 FLOPS 之比）。Route A 用 GPU 的最弱项，Route B 用 GPU 的最强项 —— 这就是规划的选择依据。
* 若成立：960 曲线 ≈ **13–20 min**（现在 7.6 h）；单卡 4060 即可（GPU0 仍全力跑 stage 1）。
* **风险（高）**：① 浮点 FFT 的误差控制（15-bit 分块 + 双精度的经典界限需要自证，且要**每次乘法做可验证检查**，因为 stage 2 的结果是 GCD，错一位就可能漏因子）；② 显存带宽与容量（三个 720 MB 缓冲 = 2.2 GB，4060 8 GB/4070 Ti 12 GB 都放得下，但要在 8 GB 内保留多曲线批量的空间）；③ 树/下降阶段的**小多项式**（log2 P ≈ 17 层，尺寸减半）用同一个大 FFT 不经济 ⇒ 需要**混合实现**（小尺寸走 batched schoolbook/NTT）；④ 编排复杂度（Bernstein scaled remainder tree，约 1000 行量级的等价逻辑）。
* **优势**：**完全不需要 gwnum/polymult**（规避了 `DEV_STAGE2_SELFHOST_FEASIBILITY.md` §3.1 记录的"polymult 不是独立可用库、会挂死"问题），也没有许可问题。

### 2.3 两条路线的关系与选择

```
Route A (pairing)  ：1.6e10 次系数模乘/曲线   ← 简单、无 FFT；但 GPU 模乘比 CPU 慢 ⇒ 只做沙箱/CPU 兜底
Route B (polymult) ：~30 次 FFT 大整数乘法 + ~1.6e9 次系数模乘 ← 用 GPU 的浮点强项，唯一能达成 ≥5× 的路线
```
* **Route B 是本规划的主线**；Route A 降级为"CPU 侧的正确性沙箱 + 兜底"。
* 决策只看 M0 的第 2 项（cuFFT Kronecker 单次乘法时间）：**≤ 200 ms ⇒ Route B 可达成 ≥10×，全力推进**；200–600 ms ⇒ 仍有 2–5×，值得做但收益有限；> 600 ms ⇒ 回到"维持交接 Prime95"，并把精力转向交接/流水线优化（`ECM_Montgomery_STAGE1.md` §16.6）。
* 若 M0 还发现"自研 GPU modmul kernel 能把 4096 档做到 ≥3e8 ops/s"（比 CGBN 快 8×，需线程级布局 + 无屏障 + 可能用 32 位 limb 的 Comba/Montgomery），则 Route A 重新具备 parity~2× 的价值，可作为无 FFT 的低风险退路。

### 3.2 数据流

```
stage 1 (GPU0, 现有)  →  m{p}_{b1}.save（每曲线一行：SIGMA/B1/N/X）
                       ↓
stage 2 planner (host, 便宜)  →  选 (D, P, B2)  ——  用 GPU 成本模型，不再用 Prime95 的 CPU 模型
                       ↓
CUDA stage 2 (GPU1)   →  每曲线一个累加器 gg  →  host GMP 做 1 次 gcd
                       ↓
factor → results 双文件 + GUI 通知；无因子 → 记 `no factor`（与 Prime95 语义一致）
```

**批量维度**：同一任务的 960 条曲线**参数完全相同**（同 N、同 B1、同 D/P）⇒ 一次上 B 条曲线（B 由显存预算定）。两条路线都能利用这一点：
* A：B 条曲线的 giant step / 配对累加彼此独立 ⇒ `blockIdx.y = 曲线`；
* B：**同一层的多项式乘法形状完全一致** ⇒ 可把 B 条曲线的同层乘法拼成一个大 batch（这是"利用大显存做批量算法"的真正含义）。

### 3.3 显存预算（决定 `stage2_curves_batch`）

| 路线 | 单曲线常驻 | 8 GB（4060）可容纳 | 12 GB（4070 Ti） |
|---|---|---|---|
| A（pairing，D=1e6，4096 位容器） | baby 表 ≈ 180 MB（**D 可调**，D=1e5 ⇒ 18 MB）+ 每曲线累加 ~10 KB | 8–40 条（取决于 D） | 更多 |
| B（polymult-class，P=1.3e5，5153 位） | F/G/H/R 四个多项式 ≈ 4 × 84 MB ≈ 340 MB + FFT 缓冲 ~1.4 GB（**按单次乘法峰值算，可跨曲线复用**） | 1–4 条 | 2–6 条 |

⇒ B 路线建议**串行少量曲线 + 复用 FFT 缓冲**，A 路线可以开大 batch。

### 3.4 正确性与验证策略（这一层不能省）

1. **单元**：多项式乘法 vs GMP（随机多项式逐系数比对，含 `mod N` 归约）；配对累加 vs CPU 参考实现。
2. **端到端已知因子**：用带已知小因子的合成 N（例如 60–80 位判据）验证"能找出来"；再对本仓库 `m12123_110e6.save` 这类真实存档与 Prime95 结果对拍（同样 B2 下命中集合一致）。
3. **数值安全**（Route B 专属）：每次大整数乘法后做**可验证检查**（例如随机取几个系数用 mpz 复算；或整式取模 x=B 的一致性检查 —— Kronecker 打包天然提供 `X=B` 处的值），失败则**回退到更大分块/重新计算**，绝不静默出错。
4. **幂等/可重复**：同一 save + 同一参数必须给出同一结论（累加顺序不影响 GCD 结论，但为了可复现，累加器拆分方式固定）。
5. **检查点**：stage 2 的检查点 = "已完成的曲线集合 + 未完成曲线的树状态"；沿用 `src/core/ecm_checkpoint.cpp` 的风格（二进制、带版本号），并与 GUI 的"退出前写检查点"流程对接。
6. **回归**：新增 `tools/test/test_stage2_cuda.ps1`（单测 + 端到端 + 对拍 + 显存上限）并入 `tools/test/test_gui_all.ps1` 的 `exe='driver'` 组；**默认 `stage2_engine = p95`，保证既有 20/20 套件与生产行为不变**。

## 4. 里程碑（含 go/no-go 门槛）

| # | 里程碑 | 交付物 | 验收（量化） | 主要风险 |
|---|---|---|---|---|
| **M0** | **速率与工作量标定（1–2 天）**（**已完成**，见 §8） | 两个微基准：① 寄存器驻留的独立 modmul 吞吐（4096/8192 容器，两卡）；② cuFFT Kronecker 大整数乘法（6.7e8 bit 规模）+ ③ **stage-2 原语**（`poly`：P 个 S 位系数的多项式乘法） | ① ≥ 3e8 ops/s ⇒ Route A 有价值；≥ 1e9 ⇒ A 可独立达成 ≥4× <br> ② ≤ 200 ms/次 polymult ⇒ Route B 可达 ≥10× | 纸面估算可能过于乐观（**这是全计划的第一个 go/no-go**） |

## 7. 进展（2026-09-30）：M1 的 CPU 参考实现已落地并验证

用户指示"**算法与正确性优先，性能后置**"，因此先做参考实现而不是 cuFFT 微基准。

### 7.1 交付物

| 项 | 位置 |
|---|---|
| 参考实现（两种独立算法 + 自检） | `tools/bench/stage2_ref.cpp`（CMake 目标 `stage2_ref`，链仓库自带 GMP） |
| 验收测试 | `tools/test/test_stage2_ref.ps1`（已登记进 `test_gui_all.ps1`，`stage2-ref` 项，**34 项检查**，约 6 s，无需 GPU） |

实现的两种 stage-2 算法（互为对照）：

* **brute**：对 (B1,B2] 内每个素数用 x-only ladder 算 `[p]Q` 并 `gcd(Z,N)`。显然正确，代价 O(π(B2))，只适合小 B2 —— 正是 oracle 需要的性质。
* **pairing**（经典 BSGS/标准延续）：baby 表 `x([j]Q)`（j ≤ D/2）+ giant steps `x([iD]Q)`；对每个素数 p > D/2 取 `r = p mod D`、`j = min(r, D-r)`、`i = (p ± j)/D`，累加 `X_i·Z_j − X_j·Z_i`；按块做 gcd 定位，再在块内逐素数 gcd 指名。候选集 `{iD ± j} ∩ (B1,B2]` 是素数的超集（合数只增加覆盖、不会产生错因子）⇒ **brute 的命中必须是 pairing 命中的子集**，这就是两侧一致的判据。

### 7.2 已验证的事实（34/34 通过）

1. **曲线运算对拍仿射算术**（素数域 M61）：`xDBL` 对拍仿射加倍、`xADD` 对拍仿射加法、ladder 对拍 k = 2,3,5,17,1000,12345；并有一条"故意用错的 a24 必须给出不同结果"的反向检查（防止测试空转）。
2. **与 stage 1 的存档约定逐位对齐**：真实驱动（`ecm_cuda.exe --method mont --exponent lcm -sigma 26 -gpucurves 1`，N = 2^128+1，B1=1000）写出的存档 `X=0x294b8e0c5e3f95b6d6c218e669c557f9`，与参考实现从 (N, σ, B1) **独立重算**的 x **完全相同** ⇒ 曲线重建（Suyama σ → a24）、ladder、归一化 x 三者与生产 stage 1 同构。
3. **已知因子端到端**：N = 2^128+1 = 59649589127497217 × 5704689200685129054721。冻结配置 **σ=26、B1=1e3、B2=1e6、D=210** ⇒ 命中 **17 位因子 59649589127497217**，命中素数 **114713**（∈(B1,B2] ✓）；**brute 与 pairing 都找到它**（σ 扫描 2..201 共 199 条曲线，仅此一条命中，因此该配置既是确定性的、又是真实的）。
4. **真实存档健全性**：对真实 M677 存档跑 stage 2 ⇒ 解析出曲线、无任何"不整除 N 的因子"、且 brute ⊆ pairing。
5. CLI 卫生：算法选择只输出对应行；缺 `--n` 非零退出。

### 7.3 参考实现暴露出的两个真 bug（正是"先做 oracle"的价值）

| bug | 现象 | 根因 |
|---|---|---|
| `xADD` 别名 | ladder 对 k ≥ 3 全错、k = 2 对 | ladder 以 `xadd(r0, r0, r1, P)` 调用：写出 `r.X` 后 `p.X` 已被覆盖，`Z3` 用了脏值。改为先把两个坐标算进临时量、最后一次性写回 |
| 存档 `X` 解析 | 存档驱动的 stage 2 一条因子都找不到，而**同一曲线**的合成模式能找到 | 解析 `X=0x…` 时保留了 `0x` 前缀，而 `mpz_set_str(..., 16)` 不接受前缀 ⇒ 点静默变成 0。现在跳过 4 个字符，且解析失败会显式报错 |

两者都是"静默出错"型：第 1 个只能靠独立 oracle 抓，第 2 个只能靠"同一曲线两条输入路径必须给同一结论"抓 ⇒ **这两条对照已固化为测试**。

## 8. M0 的第一批实测结果（2026-09-30）

### 8.1 cuFFT + Kronecker 大整数乘法（`tools/bench/cufft_kron_probe.cu`）

目标尺寸：**6.7e8 位/操作数**（P/2 ≈ 65 000 个系数 × 10323 位槽位，即 stage-2 乘积树里顶层乘法的一半规模；
Prime95 在 M5261 上选的 P = 132480，其一层的操作数是这个的 2 倍）。显卡用**空闲的 4060 Laptop**（device 1）。

```
cufft_kron_probe bench 671088000 12 1
  fft=111974400  chunk_bits=12  卷积系数 ~2^49.7（双精度尾数 53 位，OK）  设备缓冲 ~2.5 GB
  kron: ok=1 t_fwd=0.304 t_inv=0.130 t_carry=0.293 t_total=0.727
```

* **正确性 ✓**：`check` 模式在 1200 / 1e6 / 1e8 / 6.7e8 位上与 GMP **逐位一致**（把 base-2^12 的 chunk 按 2 chunk ↔ 3 字节精确还原成整数再与 `mpz_mul` 比较）。
* **速度：0.73 s 一次乘法**（正向两个 FFT 0.30 s + 逆变换 0.13 s + carry 0.29 s）。
* 按每曲线 ~30 次该规模乘法估算 ⇒ **≈22 s/曲线**，而 Prime95 实测 28.6 s/曲线 ⇒ **只是打平，不是纸面估的 10×**。
* 原因与改进点（都已定量）：
  1. **消费级 Ada 的 fp64 只有 fp32 的 1/64**，而 cuFFT 双精度正吃这个 ⇒ 换**整数 NTT**（单 62 位素数即可覆盖 2^49.7 的系数界）可能快 3–5×；
  2. **carry 占 40%**（0.29 s）：目前是"提取商 → 移位相加"的朴素多趟（约 6 趟 × 2 kernel）。改成**分块顺序 carry**（块内串行 + 块间一次修正）应降到 ~0.05 s；
  3. 更大的卡（4070 Ti ≈ 2.5× 4060）但**它正被 stage 1 占满**，不能动。
  结论：这条路"可行但不是碾压"，达到 ≥5× 需要 NTT + carry 优化 + 更大显存/带宽，属于 M2 的工程量而不是一次测量。
* 过程中的两个真 bug（都已修，值得记）：**cuFFT 不归一化**（`Z2D(D2Z(x)) = N·x`，漏除 N 直接全错）、**carry 竞态**（同趟内线程 i 写 `c[i+1]` 而线程 i+1 同时在改写它 ⇒ 进位丢失，现象是"前 33 个 chunk 对、中间 8 个错"）。

### 8.2 `--go` 支持 param 0，并直接给出"最小 B1/B2"（`docs/DEV_ECM_GUI.md` 无关，属驱动侧）

* 原来 `--go` 的群阶函数是 **硬编码 param 3** 的，而我们的 `--method mont`／`--gpu-param 0` 用的是 Suyama（**param 0**）⇒ 报的是**另一条曲线**的群阶。现在按运行的实际参数化选择脚本（0/1/2/3 四个公式照 `FindGroupOrder()` 原样实现），并额外返回 gp 对该群阶的**精确分解**。
* 新增输出（每个命中因子一行）：
  `go_min_bounds[i]: param=0 largest_prime=114713 min_b1_stage1=114713 min_b1_stage2=599 min_b2_stage2=114713 largest_exponent=1`
  * `min_b1_stage1`：只用 stage 1 就要覆盖群阶的最大素幂；
  * `min_b1_stage2` / `min_b2_stage2`：让 **stage 2** 收尾所需的界（stage 1 覆盖"去掉一个最大素因子之后的全部"，B2 达到那个最大素因子）。
  ⇒ 这就是**为指定因子构造确定性测试向量**的方法，不再靠扫 sigma 碰运气。
* **交叉验证（与独立实现互相印证）**：对 N = 2^128+1、σ=26，gp 给出
  `#E = 2^3·3·7·67·233·331·599·114713` ⇒ 最大素因子 **114713**，而我们的参考 stage 2（`tools/bench/stage2_ref.cpp`）在 B1=1000/B2=1e6 下命中时报告的命中素数**正是 114713** ✓。
* **界的紧性也已验证**：用参考 stage 2 在 `B1=599, B2=114713`（推导出的界）下**能**找到该因子；把 B2 降到 114000（差一个素数）就**找不到** ✓。整套断言固化在 `tools/test/test_go_group_order.ps1`（12 项，gp 缺失时自动跳过）。

### 8.3 把成本归结成一个可跟踪的品质因子：**ns / 操作数 bit**

尺寸扫描（`cufft_kron_probe bench <bits> 12 1`，device 1 = 空闲 4060）：

| 操作数位宽 | fft 长度 | 设备显存 | t_total | **ns/bit** | 其中 carry |
|---|---|---|---|---|---|
| 1.0e6 | 168 750 | 4 MB | 0.002 s | 2.00 | — |
| 1.0e7 | 1 679 616 | 38 MB | 0.009 s | 0.90 | 0.004 |
| 1.0e8 | 16 777 216 | 384 MB | 0.093 s | 0.93 | 0.042 |
| 3.36e8 | 55 987 200 | 1.28 GB | 0.354 s | 1.055 | 0.147 |
| 6.71e8 | 111 974 400 | 2.56 GB | 0.728 s | **1.085** | 0.293 |

三个结论（都由这张表直接读出，不是估的）：

1. **成本与数据量成正比、与 log 因子几乎无关**：从 1e7 到 6.7e8 bit（67×）每 bit 成本只变了 1.2× ⇒ 这是**纯带宽受限**的算法。直接推论：把 P 选小到"多项式装进 cache"**并不会**让每 bit 变便宜（38 MB 那行只比 2.5 GB 那行快 4%）—— 这条设想被实测否掉。
2. 因此 stage 2 的总时间 ≈ **（每曲线搬运的 operand-bits）×（ns/bit）**，而每曲线的 operand-bits 由 (B2, D, P) 决定、与 P 近似无关（`calls × cost ∝ (B2/(D·P)) × P = B2/D`）⇒ **唯一能同时降两端的旋钮是 D**（更大 D ⇒ 更少 D-section），它的代价是 baby 表（D/2 个点）。
3. **carry 占 40%**（6.7e8 那行 0.293 s / 0.728 s），是独立的一项优化，与 FFT 无关。

**品质因子对照**（这是 M0 真正要给出的东西）：

| 实现 | ns / operand-bit | 推算每曲线 | 相对 Prime95（28.6 s/曲线） |
|---|---|---|---|
| 本原型 · 通用大整数（fp64 cuFFT + 12 位 chunk + 未融合 + 朴素 carry） | **1.09** | ≈ 5–7 分钟 | **慢 ~7×** |
| 本原型 · **stage-2 原语**（`poly`，无全局 carry，见 §8.4） | **0.28–0.34** | ≈ 55–65 s | **慢 ~2×** |
| Prime95 的 CPU（由它的参数与 28.6 s/曲线反推） | ≈ **0.15** | 28.6 s | 1.0 |
| 优化后的 GPU 目标（整数 NTT 或融合 FFT + 15 位 chunk + 无填充浪费 + 分块 carry） | 0.05–0.1 | **10–19 s** | **1.5–3× 更快**（4070 Ti 上 3–6×） |

⇒ **结论：这条路是"值得做但必须真做优化"的项目**，不是把原型接到 stage 2 上就能赢。但**关键是 §8.4 把差距从 7× 缩到了 2×**——只要 stage 2 不用"通用大整数乘法"而是用它真正需要的"多项式乘法"（进位不跨槽、carry 消失），原型立刻进入 Prime95 的同一个数量级，剩下的 2× 全在下方清单里（且清单里的大头都是**降流量**，不是换算法）。可量化的优化清单（按预期收益）：

| 优化 | 依据 | 预期 |
|---|---|---|
| 整数 NTT 取代 fp64 cuFFT | 消费级 Ada 的 fp64 只有 fp32 的 1/64；系数界 2^49.7 < 2^62 ⇒ **单个 62 位素数即可**，无需 CRT | 算术项（非带宽项）大幅下降；若瓶颈转为带宽则收益有限 |
| 提高基数 / 阶段融合（radix-8、共享内存内多阶段） | 实测每次变换≈18 遍全量访存；radix-8 只需 ~9 遍 | 1.5–2.5×（降的是**流量**，才是这条路的真瓶颈） |
| 15 位 chunk 替代 12 位 | 系数界 2^55.4 仍 < 2^62（NTT 下） | 数组长度 −20% |
| 消除 `next_smooth` 填充浪费 | 需要 2n−1 而我们开到 1.12e8（N 比需求大 25%） | ~1.2× |
| 分块顺序 carry | carry 现占 40%，且是 6 趟 × 2 kernel 的朴素实现 | ~1.3× 总体 |
| 换到带宽更大的卡 | 4060 Laptop ~256 GB/s，4070 Ti ~504 GB/s | ~2×（但 4070 Ti 被 stage 1 占满，不能动） |

**决策点（需要你定）**：优化到 0.05–0.1 ns/bit 需要的是"GPU 上的大整数 FFT/NTT 引擎"（阶段融合、共享内存、Goldilocks/ Montgomery 归约、分块 carry），量级是**数周工程量**，回报是 **1.5–3×**（4060）到 **3–6×**（若能用上 4070 Ti）。相比之下，维持现状（stage 2 交 Prime95）的代价是：每任务 7.6 h CPU 时间 + 需要人工启动 Prime95 + 无法并行。两条路都合理，取舍取决于你要的是"更快的 stage 2"还是"自主可控 + 与 stage 1 并行"。

### 8.4 `poly` 模式：真正的 stage-2 原语，比通用大整数版本快 3–4×

`cufft_kron_probe poly <P> <S>` 测的是**stage 2 真正需要的东西**：两个各含 P 个 S 位系数的多项式相乘（槽宽 `2S + ceil(log2 P)`，因此**进位不会跨槽** ⇒ 全局 carry 消失，改为"槽内归一化 + 逐槽组装"，一趟访存）。校验方式：把每个系数按 32 位素数 4294967291 做模投影，与 GMP 教科书乘法**逐系数**比对（任意 S 都适用，因为 10323 位的系数装不进 uint64）。

| S（模数） | P | fft | 设备显存 | t_total | ns/系数 | **ns/操作数位** | 校验 |
|---|---|---|---|---|---|---|---|
| 5153 | 1024 | 1 769 472 | 54 MB | 0.006 s | 5 622 | **0.284** | ✓ |
| 5153 | 8 192 | 14 155 776 | 432 MB | 0.047 s | 5 752 | **0.278** | ✓ |
| 5153 | 16 384 | 28 311 552 | 864 MB | 0.100 s | 6 104 | **0.296** | ✓ |
| 5153 | 32 768 | 56 623 104 | 1.7 GB | 0.207 s | 6 318 | **0.306** | ✓ |
| 5153 | 65 536 | 113 246 208 | 3.4 GB | 0.417 s | 6 357 | **0.308** | ✓ |
| 3571 | 8 192 | — | — | 0.037 s | 4 531 | **0.316** | ✓ |
| 3571 | 65 000 | — | — | 0.286 s | 4 403 | **0.308** | 未校验 |

**补测与一处纠正（2026-09-30，第二轮）**：

* **cuFFT 的 plan + 显存分配不是成本**：P=16384/32768 的"墙钟 − t_total"实测 0.7 / 0.6 s，只占 12 % / 3 %。
* **3.4 GB 的形状能跑**：`poly 65536 5153`（fft = 1.13e8、3456 MB）实测 **墙钟 1.5 s、t_total 0.417 s、ok=1、0.308 ns/操作数位**。
* ⚠ **上一轮我据此写下的"大形状反复超时 ⇒ 显存是限制"是错的**，已撤回：那次 >10 min 无结果的真因是**设备争用** —— 同一时刻另一个进程正在同一张卡（device 1）上做基准。由此得到一条操作规则：**本机 GPU 基准必须串行跑**（跑之前确认 device 1 上没有别人的 kernel；本仓库此前也有同类记录：`--gpu-info` 要用空闲卡）。这条错误的代价是"一整轮的结论被自己的重测推翻"，所以写在这里而不是删掉。
* **ns/操作数位对 P 依旧平坦**：1024→65536 为 0.284 / 0.278 / 0.296 / 0.306 / 0.308（P 涨 64 倍，每 bit 只涨 8 %）⇒ §10.6"取小 P 只有好处"成立。

**三个结论**：

1. **把全局 carry 换掉值 3.2–3.9×**：通用大整数模式 1.09 ns/bit → poly 模式 0.28–0.34 ns/bit。这也印证了 §8.3 的"carry 占 40%"读数。
2. **ns/系数 与 ns/位在整个 P 范围基本恒定**（P 从 1024 到 65000，每系数 5.6→7.0 µs）⇒ 依旧是带宽受限，但**P 可以自由选**（例如按显存上限选 P，而不牺牲每 bit 成本）——初测 P=65000 在 4060 上要 3.4 GB 显存，12 GB 的卡可以取 P≈132480。
3. **与 Prime95 的 CPU 基线（≈0.15 ns/位）相比，原型现在只慢 ~2×**（不再是 7×）。按 §8.3 的优化清单（阶段融合/更高基数、15 位 chunk、消除填充浪费、更大带宽的卡）目标 **0.05–0.1 ns/位 ⇒ 每曲线 10–19 s ⇒ 1.5–6× 快于 Prime95**。
4. 过程中修掉的两个真 bug（都属"静默算错"型，值得记）：
   * **槽内必须先归一化**：原始卷积系数可达 `chunks×2^24 ≈ 2^34`，不是 12 位数字 ⇒ 直接按 12 位组装会全错；
   * **位域抽取越界**：槽（144 位）比系数（64 位）宽，朴素的扁平读取会把**下一个系数的位**读进高位 chunk ⇒ 全部 127 个槽都错。现在 `bit_range` 明确"系数宽度之外的位是 0"。

**算法**：与 CPU 参考（`stage2_ref.cpp --algorithm pairing`）逐项一致 —— baby[j] = [j]Q（j ≤ D/2）、giant[i] = [iD]Q（i ≤ B2/D+2）、素数 p ∈ (B1, B2] 按 `j = min(p mod D, D − p mod D)`、`i = (p ∓ j)/D` 配对，累乘 `X_i Z_j − X_j Z_i`；**p ≤ D/2 的素数不需要算术**：baby[p] = [p]Q 已在表里，累乘 `baby[p].Z` 即可（与参考的"直接 gcd R.Z"等价）。最后宿主机把每曲线各段的累加子乘起来做一次 gcd。

### 9.1 两个内核（这一版刻意选的结构）

| 内核 | 实例划分 | 做什么 |
|---|---|---|
| `kernel_s2_tables` | 每曲线 1 个实例 | ①（可选）在设备上跑 stage 1 的 ladder 得到 Q；②链式造 baby 表；③一次 ladder 得 [D]Q 后链式造 giant 表 |
| `kernel_s2_pair` | 每 (曲线, 段) 1 个实例 | 段内素数跨步遍历，累乘配对值（small 素数段单独一轮循环）；每实例写一个剩余类 |

**为什么用链不用 ladder 造表**：CGBN 的算术是**实例内的集合操作**（TPI 个线程协作），同一 warp 里不同实例若走不同分支就会被串行化（正确但慢），而 ladder 的行程数取决于标量 —— baby 表的 10 万个个例标量各不相同，必然是发散。改用 xADD 串链 `v[j] = xADD(v[j-1], v[1], v[j-2])`：每个表项**一次差分加法**（8 乘 vs ladder 的 ~8·log2 j），而且所有实例行程数与分支**完全一致** ⇒ 零发散。ladder 只用在"所有曲线同一标量"的地方（stage-1 的 s、以及 giant 表的 D），那里均匀性是精确的。

**并发度**：`segs` 把一条曲线的素数表切成若干段，每段一个累加器实例（表是只读共享，代价只有多几个剩余类），宿主机再把各段乘回去 —— 所以"曲线数少"时也能填满 GPU。

### 9.2 域（domain）的推导 —— 这次最容易"静默算错"的地方

CGBN 的 `mont_mul` 返回 `a·b·R⁻¹`（R = 2^BITS），xDBL 里 `Z2 = K·(BB + a24·K)` 需要两项**同域**：`K = AA − BB` 与 `BB` 都是 `R⁻¹` 量级，因此 **a24 必须先 `cgbn_bn2mont` 转换**，否则算出来的是另一条曲线，而症状只是"找不到因子"（stage-1 的 Suyama 路径同理，这也是 stage-1 里 `double_add_v2_suyama` 用全宽 `mont_mul` 而不是 32 位 `special_mult_ui32` 的原因）。

反过来，**投影缩放与每次 mont_mul 的 R⁻¹ 都不重要**：`X_i Z_j − X_j Z_i` 对每个点是 2 次齐次的，两项带**相同的**因子，在差里约掉；宿主 gcd 只问"是否 ≡ 0 mod p"。⇒ stage 2 里任何地方都不需要求逆、也不需要域转换，**存档里的仿射 x 可以直接当 (x : 1) 喂进去**（§9.3 第 4 项就是这么测的）。

### 9.5 已知边界（本阶段刻意不做的）

* **B2 的实用上限**：显存 = 曲线数 × (D/2 + B2/D) × 2 × BITS/8 ⇒ 配对路线只适合 B2 ≲ 1e9（也正是 §4 的 M1 验收条件）。B2 ≥ 1e11 的规模必须走 Route B（多项式树），不是把这一版接上去就行。
* **性能未优化**：每素数 2 次 mont_mul + 1 次减法 + 累乘，是"规则批量"的朴素形态；Route A 的吞吐判据（§2.1）说明它不可能成为 ≥5× 的路子，它的价值是**正确性基线 + 脱依赖兜底**。
* **未接入驱动**：目前是独立探针；接入 = 后端 seam 加 `ecm_backend_stage2` 钩子 + `stage2_engine`/`stage2_b2` 等 ini 键 + `--stage2 self` 开关（§3 已设计，未实现）。

## 10. Route B 的定量修正：改用"吞吐"口径（2026-09-30）

§2.2 那张表是**纸面估算**（当时就标了"未实测"），实测之后它错了近 50×，这里把它改成可验证的口径，免得后面的验收门槛建在错数字上。

### 10.1 纸面估算错在哪

| 项 | §2.2 纸面 | 实测（§8.1/§8.4） | 差 |
|---|---|---|---|
| 一次 polymult | 25–40 ms | `poly P=8192 S=5153` 实测 0.047 s（规模小 16× 的形状） | — |
| 每操作数位成本 | 隐含 ≈0.005 ns（30 × 30 ms / 2e10 bit） | **0.278–0.340 ns** | **~60×** |
| 每曲线 | 0.8–1.2 s | 按 Prime95 的每曲线位数（1.9e11）折算 **53–65 s** | **~50×** |

根因不是"FFT 慢"，而是**纸面模型漏了访存**：它按"4–5 遍 720 MB"估 ≈12–15 ms，而实测每次变换≈18 遍全量访存（cuFFT 未融合 + 12 位分块的 4× 浪费 + `next_smooth` 填充 25% + 全局 carry 6 趟）。**这条算法是带宽受限的**（§8.3 第 1 条：1e7→6.7e8 位，每 bit 成本只变 1.2×），所以"算术量估算"从一开始就不是正确的模型。

### 10.2 唯一稳健的对照：每秒搬多少操作数位

时间对照会被"每曲线到底要搬多少位"污染（那个数目前是从 Prime95 的耗时**反推**的，1.9e11 = 28.6 s ÷ 0.15 ns，有循环论证风险）。**吞吐**不会：

| 实现 | 操作数位吞吐 | 说明 |
|---|---|---|
| ~~Prime95 的 CPU（反推）~~ | ~~6.6e9 bit/s~~ **作废，见 §10.5** | 该口径不成立：两套实现搬的是不同种类的位 |
| 本原型 · 通用大整数（cuFFT） | 0.92e9 bit/s | 1.09 ns/bit |
| 本原型 · **stage-2 原语**（`poly`，无全局 carry） | **2.9–3.6e9 bit/s** | 0.278–0.340 ns/bit |
| 目标（NTT + 融合 + 无填充 + 分块 carry） | 10–20e9 bit/s | 0.05–0.1 ns/bit |

⇒ **离 parity 差 1.8×，离 M3 的"每曲线 ≤6 s"差约 9×**（按每曲线 1.9e11 位）。
⚠ **2026-09-30 第三轮修正**：把树结构写成代码后（§10.5），每曲线位数更可能是 **3.75e11** ⇒ Prime95 的吞吐应为 13.1e9 位/秒、差距是 **3.6–4.5×**、"≤6 s"需要 ~15×。两个数之间的 2× 取决于"Prime95 的 polymult 到底搬多少位"这个**未决问题**（§10.5 末段），已派子代理查源码。所以本节的绝对值按 1.9e11 读会偏乐观约 2×，**结论方向不变**。

### 10.3 9× 从哪来（每一项都在 §8.3 的清单里，现在补上 gpuowl 的实测密度依据）

| 杠杆 | 依据 | 预期 |
|---|---|---|
| **整数 NTT 取代 fp64 cuFFT** | gpuowl/PRPLL 的实测 bpw 表（`src/fftbpw.h`，见 `DEV_GPUOWL_NTT_NOTES.md` §5）：`FFT64`(fp64, 8 B/word) ≈ 16.7–19.6 位、`FFT61`(GF(M61²), 8 B/word) ≈ 22.4–25.0、`FFT3161`(GF31+GF61, **12 B/word**) ≈ 37.1–40.5、`FFT323161`(16 B/word) ≈ 50.0 ⇒ 按**每字节承载位**算：2.1–2.45 → 2.80–3.13 → 3.09–3.38 → 3.13 | **1.3–1.4×**（不是我上一版写的 1.3–2.2×：40 位是 **12 字节**的密度，不是 8 字节） |
| **阶段融合**（radix-8/16 + 共享内存，把 ~18 遍访存压到 ~6–9 遍） | §8.3 实测：每次变换≈18 遍全量访存，这是**真瓶颈** | 1.5–2.5× |
| 15 位 chunk（NTT 下系数界 2^55.4 仍 < 2^61） | 数组长度 −20% | ~1.2× |
| 消除 `next_smooth` 填充浪费（需要 2n−1 却开到 N 大 25%） | §8.3 | ~1.2× |
| 分块顺序 carry（现占 40%，且是 6 趟 × 2 kernel） | §8.3 | ~1.3× |
| 换带宽更大的卡（4060 Laptop ~256 GB/s → 4070 Ti ~504 GB/s） | — | ~2×（但 4070 Ti 被 stage 1 占满） |

连乘 5–15× ⇒ **0.05–0.1 ns/bit**，正好落在 parity 到 3× 之间。

### 10.4 对 M3 验收门槛的修正建议

* 原门槛"B2 ≥ 1e11 时每曲线 ≤ 6 s（≥5×）"是在**纸面 24–35×** 的前提下定的；按实测口径，**4060 上的现实目标是 10–20 s/曲线（1.4–3×）**，≤6 s 需要 4070 Ti（或在 4060 上再拿到额外 2–3×）。
* 另一半仍待独立验证：**每曲线真正要搬的操作数位数**。M3 落地时必须从树结构自己算一遍（F 树 + Newton + 余式树 + ~30 次顶层 `P×P`），而不是继续用反推值 —— 这是下一轮的第一件事。
* 无论最终倍数是多少，"自主可控 + 与 stage 1 并行 + 无人工启动 Prime95"这三个收益不依赖这个倍数，Route B 的价值下限仍在。

### 10.5 每曲线操作数位：**手推是错的**，改用可重算的模型脚本（2026-09-30 第三轮修正）

上一版这里写的是手推表，并宣称"两条独立路径（反推 1.9e11 与正推）互相印证、差 <5%"。**该结论已撤回**：把手推写成代码（`tools/bench/stage2_shape_model.py`）并用 Prime95 自己的参数自检之后，发现手推有两处错：

| 手推的毛病 | 真相 |
|---|---|
| **漏了 G 树**：把每轮 outer loop 的代价只算成"3 次全尺寸乘法" | `DEV_STAGE2_SELFHOST_FEASIBILITY.md` §1 明写每轮 outer loop 是"**G 树** + 3 次 `P×P`"，即 **10 轮各建一棵度 P 的积树** —— 这是最大的一项（59 %） |
| **F 树公式多一个 2×**：写成 `2P·Σ(2S+k)` | 每层有 `P/2^k` 次乘法、每次操作数是 `2^(k-1)` 个系数 ⇒ 每层 = `P·(2S+k-1)`，即 `P·Σ`，不是 `2P·Σ` |
| "两条独立路径互相印证" | 反推锚点 1.9e11 里的 0.15 ns/位**本身就是为了让两个数对上而选的** ⇒ 不是独立验证，是循环论证 |

**可重算的模型**（`python tools/bench/stage2_shape_model.py --b2 1.94e12 --bits 5261 --d 1411410`）：

| 分量 | 操作数位 | 占比 |
|---|---|---|
| F 树（baby 点积树，一次） | 2.22e10 | 5.9 % |
| **G 树（每轮 outer loop 一棵）** | **2.22e11** | **59.2 %** |
| fold（`H = G·H mod F`，10 × 3 次全尺寸） | 8.38e10 | 22.3 % |
| descent（scaled remainder 下降，一次） | 4.44e10 | 11.8 % |
| small（叶层小系数乘） | 2.79e9 | 0.7 % |
| **合计** | **3.75e11** | 100 % |

**自检（脚本里的第 1 项，已通过）**：`poly_size(D) = φ(D)/2` 精确复现 Prime95 公布的三个 `poly_size`（D=1771770→167040、D=1411410→132480、D=510510→46080）⇒ **"baby 集 = 小于 D/2 且与 D 互素的个数"这个形状模型是对的**，模型输入可信。

**2× 分歧已定论（2026-09-30，查了 Prime95 源码）：不是笔误，是结构不同，而且"操作数位"这个口径本身不成立。**

事实（子代理逐条给出 `file:line`）：

* **`polymult` 乘的是"系数数组"**：`void polymult(pmhandle*, gwnum *invec1, uint64_t invec1_size, gwnum *invec2, uint64_t invec2_size, ...)`（`polymult.h:86-97`）—— 每个系数是一个**完整的模 N gwnum**（全宽），不是小整数。
* **它是两层方案**：外层对 `~2·poly_size` 个元素做复 FFT（元素就是那些模 N 残数），内层用**每个系数自己的 gwnum FFT**（长度 320）承担模算术；`polymult.c:1229-1262 prep_line`、`:4107`、`:4113` 就是按"line"把每个系数的 FFT 空间数据搬出来做外层变换。
* **`stage2-fft-length` 是内层那个 FFT 的长度**（`ecm.cpp:9940/10062` 写的是 `gwfftlen(&ecmdata.gwdata)`，即每个系数的 FFTLEN），**与多项式度无关**。合法性的位预算来自 `EXTRA_BITS/2 ≥ polymult_safety_margin = log2(P)/2`（`polymult.c:393-407`）—— 内层 320 words 之所以够，正是因为它只需要额外 `log2(P)/2` 位的余量来吸收 P 项之和。
* ⇒ **我原来的"把度 132480 的多项式 Kronecker 打包成一次 1.4e9 位变换"在这个位置上不成立**：真实结构有 ~2P 个"槽"，每个槽装一个全宽残数，而不是一个槽装 2S 位。

**由此得到的两个修正（都比数字本身重要）**：

1. **"每曲线操作数位"不能用来和 Prime95 对比**：两套实现搬的是**不同种类**的位（我们：Kronecker 打包的 2S+log P 位槽；它：每系数 320 words 的 FFT 空间）。§10.2 里"Prime95 吞吐 6.6e9 或 13.1e9 位/秒"这种说法**作废**。唯一诚实的对比是**同一 (B2, D) 参数下的墙钟时间**：Prime95 = 28.6 s/曲线（它自己报的），我们的预测来自自己的模型。
2. **本节的模型仍然有用，但它预测的是"我们自己引擎的代价"**，不是 Prime95 的：3.75e11 位 × 0.278 ns/位 = **104 s/曲线**（M5261 的 D=1411410 形状）⇒ 对 Prime95 的 28.6 s 是 **3.6×**。这与 §10.2 独立给出的"3.6–4.5×"一致 —— 两条路径现在通过**预测时间 vs 实际时间**对齐，不再依赖那个不成立的操作数位口径。

**留给后面的一条真设计选择**：既然 Prime95 用两层（外层 2P 复 FFT + 每系数内层 FFT），而我们原计划用单层 Kronecker —— 两者的**显存与流量结构不同**（我们的：一个 1.4e9 位变换，2–4 GB 缓冲；两层：每个系数在 FFT 空间占 ~2.5 KB，P=132480 时约 339 MB/多项式）。哪条在 GPU 上更优，需要用 §12 的融合 NTT 探针各测一版**才能定**，不能靠推理。已记入 §12.5。
### 10.6 ~~GPU 上应当重选 D（取小 P）~~ → **已推翻：总工作量 ∝ 1/D，因此要取"内存装得下的最大 D"**（2026-09-30 第三轮修正）

上一版这一节写的是"总工作量与 D 几乎无关，只剩对数项，所以 GPU 上应取小 P（≈8192）来省内存"。**该结论已撤回**，它把 **Route A（配对）的 D 无关性**错套到了 Route B（树）上：配对路线的候选素数个数 `0.2·(B2−B1)/ln B2` 确实与 D 无关（§2.1），但**树的代价不是**。

**正确的推导**（`tools/bench/stage2_shape_model.py` 逐点算出来的）：每轮 outer loop 处理 `P ≈ 0.2D` 个 giant 点，轮数 `num_polyG = ⌈(B2/D)/P⌉`，每轮建一棵度 P 的 G 树 + 3 次全尺寸乘法 ⇒

```
每曲线 ≈ num_polyG · [tree(P) + 3·mul(P)]
       ≈ (B2/(D·P)) · [P·2S·log2 P + 6P·(2S+log2 P)]
       ≈ (B2/D) · 2S · (log2 P + 6)          ← 对 D 是 1/D，不是 log
```

⇒ **D 越大越快**（轮数按 `1/D²` 掉，而每轮的量只按 `D·log D` 涨）。模型给的曲线（B2=1.94e12、S=5261、0.278 ns/位）：

| D | P | 每曲线位数 | 每曲线时间 | 最大变换 |
|---|---|---|---|---|
| 120 120 | 11 520 | 2.94e12 | 817 s | 128 MB |
| 510 510 | 46 080 | 7.87e11 | 219 s | 512 MB |
| **1 021 020** | **92 160** | **4.37e11** | **121 s** | **1024 MB** |
| 1 531 530 | 138 240 | 3.56e11 | 99 s | 2048 MB（2 缓冲超 2 GB 上限） |

**新的设计定律**：内存上限 `M` 决定 `D_max ∝ M`，而时间 `∝ B2/D_max ∝ B2/M` ⇒
**每曲线时间 ∝ 1/可用显存（乘一个 log 修正）**。所以 GPU 版的正确策略是"**在显存装得下的前提下取最大的 D**"，而不是取小 D。4060（8 GB，留 2 GB 给两个变换缓冲）对应 D ≈ 1e6、P ≈ 9.2e4。

**顺带一个重要的并行性结论**：P 取大之后，一条曲线的表要 1 GB 级，**不可能靠"多曲线批量"填 GPU**；但树版的并行度来自**单次 P×P 乘法内部的 1.4e9 位变换**本身 ⇒ 这与 Route A（必须靠多曲线填满）截然不同，是树版在 GPU 上的结构性优势。代价是"每曲线独占显存"，因此**显存容量直接就是吞吐上限**。

### 10.7 §10.5/§10.6 的修正对"是否值得做"的影响

* 每曲线位数从 1.9e11 上调到 **3.75e11**（§10.5），差距从 1.8× 变成 **3.6–4.5×**（待 §10.5 末段的未决问题定论，可能回落）。
* 但"取最大 D"这条新定律是**免费的收益**（模型：D 从 120120 提到 1021020，每曲线从 817 s 降到 121 s，6.7×），且与原型的 0.278 ns/位无关。
* 组合起来：0.278 ns/位 × 121 s/曲线（D=1e6）⇒ 若融合把每位数压到 ~0.08 ns，则 **~35 s/曲线**（≈ parity）；再叠加 NTT 密度 1.3–1.4× ⇒ **~25 s/曲线**（1.15×）。**≤6 s 在 4060 上不现实；要在 4070 Ti（带宽×2、显存 12 GB ⇒ D 可再大 50%）上才可能接近。**
* 因此 M3 的门槛维持 §10.4 的修正版（**4060 上 10–20 s 需要更强的融合/密度收益**，而按本节的新数字 25–35 s 更现实）—— 真正的结论是：**这份工作的价值主张不应建立在"≤6 s"上**，而应建立在"自主可控 + 与 stage 1 并行 + 无人工启动 Prime95 + 显存越大越快"上。
## 11. 从 gpuowl/PRPLL 的 NTT 引擎学到什么（2026-09-30）

规格已完整提取到 `docs/DEV_GPUOWL_NTT_NOTES.md`（169 行，逐条带 `file:line`）。这里只记**对我们设计的影响**。

### 11.1 它的引擎比"一个 NTT"重得多

| 它有 | 是什么 | 我们要不要 |
|---|---|---|
| **3-D 分解**（`WIDTH × MIDDLE × SMALL_HEIGHT`）+ 转置，radix 4/8 | 不是一维 Stockham 循环；`fftMiddleIn/Out` 做转置，中间级每线程一个 2/4/8/16 蝶形 | **要的是这个形态**：融合级数就是靠它做到的（我们的流量瓶颈） |
| **GF(M61²)** 上的"复数" NTT | M61 = 2⁶¹−1 的 v₂(p−1) = 1 撑不起 2^k 长度；扩域后单位根阶达 **2⁶²**；元素 = `ulong2`，cmul 用 Karatsuba = 3 次宽乘，csq = 2 次 | **要**（这是"怎么在 Mersenne 素数上做长 NTT"的标准答案）；也可选 Goldilocks 2⁶⁴−2³²+1（v₂ = 32） |
| **IBDWT 权重**（2 是 Z₆₁ 里的 61 次单位根，权重实现为 `mod 61` 的循环移位） | Crandall–Fagin 权重，用于 Mersenne 数 PRP | **不要**：我们的系数不是全 1，权重要按 `2^(i·w)` 另算（stage 2 里由 Kronecker 槽宽决定） |
| **中间积（tail / middle product）** 取代逐点乘 | 平方时省一半（`pairSq` 等） | **部分要**：stage 2 的下降树正是 Prime95 的 `polymult_several(CIRCULAR\|MULHI)` —— 也是中间积 |
| **CRT 在进位时融合**（`n61·M31 + n31`）、融合进位核（`fftW+carryA+carryB+premul`，有 stairway forwarding） | 引擎级技巧 | **不要**：我们的 Kronecker 槽宽保证**进位不跨槽**，slot 内部自己收尾（§8.4 已实测：去掉全局 carry 值 3.2–3.9×） |
| 惰性约减（结果落在 [0, 2p+ε]，不规范化） | 省一次条件减 | **要**（每个蝶形省一条指令） |

### 11.2 两条会改变优先级的结论

1. **整数 NTT 的密度优势只有 1.3–1.4×，不是数量级**（§10.3 已按"每字节承载位"改正：fp64 2.1–2.45、GF(M61²) 2.80–3.13、M31+M61 3.09–3.38）。⇒ **换模数不是那 9× 的来源；融合层数才是**。所以顺序应当是"**先把融合做出来（fp64 或整数都要自己写核），再谈换域**" —— 因为 cuFFT 是闭源的，融合这一项**无论如何都得自己写 FFT/NTT**。
2. **换成整数 NTT 还有一个正确性红利**（这条比速度更值钱）：fp64 FFT 的 §2.2 风险①"浮点误差控制 + 每次乘法做可验证检查"是**定理级的不确定性**；整数 NTT 下 `N·(2^bpw)² < p` 是**规划期就能证明并在代码里断言**的（探针已实现该判据），运行时**不需要**任何误差检查或回退路径 ⇒ M2 的验收从"1000 次随机对拍零误差 + 每次都事后验算"降级为"一次算对就永远对"。

## 12. 融合 NTT 的设计规格（第一优先级优化的落地形态）

§11.2 的结论是"**融合层数才是那 9× 的来源**"，这里把它写成可实现的形式。

### 12.1 要压掉的是什么

朴素实现（每级一趟 kernel）在 N = 2^k 上要 **k 趟**读写，每趟 2 次全量访存（读+写）：

| N | 朴素趟数 | 每元素字节数（uint64，3 次变换：2 前向 + 1 逆） | 每元素载荷位（bpw≈24） | 每操作数位字节数 |
|---|---|---|---|---|
| 2^24（P=8192） | 24 | 24×2×8×3 = 1152 B | 24 bit | **48 B/bit** |
| 2^28（P=132480） | 28 | 28×2×8×3 = 1344 B | 24 bit | **56 B/bit** |

对照：cuFFT 的 fp64 路径实测每次变换≈18 遍（§8.3），而它的每元素载荷≈18.5 位 ⇒ ~0.43 B/bit；**朴素 NTT 在流量上比它差 100 倍以上**，所以首版 NTT 探针的数字一定会难看（这是预期，不是失败）。

### 12.2 目标形态：三维分解 + 共享内存内多级

把 N = N1 × N2 × N3（各为 2 的幂）**（gpuowl 用的就是这种分解 + 转置，§11.1）**，每个 pass 内部把连续的一段搬进共享内存、在共享内存里做完该维的全部级、再写出：

| pass | 覆盖 | 访存趟数 |
|---|---|---|
| 1 | N1 维（共享内存内 log2 N1 级） | 2 |
| 转置/重排 | 无算术（可与下一 pass 融合） | 0–2 |
| 2 | N2 维 | 2 |
| 3 | N3 维 | 2 |
| 合计 | | **≈ 6–8 趟**（而非 24–28） |

共享内存预算（sm_89 每 block 最多 ~100 KB）：一个 tile 装 8192 个 uint64 = 64 KB，或 4096 个 = 32 KB。取 N1 = N2 = 2^12、N3 = 2^k 的分解，pass 1/2 的 twiddle 表可以整表常驻。

**预期收益**：趟数 24→7 ⇒ 流量降到 ~1/3.4；再叠加"15 位 chunk 使数组短 20%"与"消除填充"，就是 §10.3 里那 1.5–2.5× + 1.2× 两项的来源。**这一项与"fp64 还是整数"无关**（cuFFT 闭源无法融合，所以无论如何都要自己写核）。

### 12.3 验收（可测、可复现）

| 项 | 门槛 | 依据 |
|---|---|---|
| 正确性 | `poly 64 64 / 128 257 / 512 1024 / 1024 2048` 全部 `ok=1`（逐系数对拍 GMP 模投影） | `tools/test/test_ntt_poly.ps1` |
| 精确性 | 代码内断言 `N·(2^bpw)² < p`（规划期可证，运行期零误差检查） | §11.2 的正确性红利 |
| 性能（M2 更新版） | **两个形状都要测**：`poly 8192 5153`（小形状，便于正确性与回归）与 **`poly 92160 5261`（真实形状：§10.6 修正后 GPU 应取"内存装得下的最大 D"⇒ D≈1e6、P≈9.2e4，模型给的每曲线 121 s 就是以它算的）**；门槛 **≤ 0.10 ns/操作数位**（优于 fp64 cuFFT 的 0.278 至少 2.7×） | §10.3 与 §10.6（已修正） |
| 每趟访存 | 打印"每元素字节数"与 pass 数，pass 数必须 ≤ 8（否则融合没生效） | §12.1 |
| 稳定性 | 同一形状连测两次，偏差 ≤ 3 %（设备空闲；见 §8.4 的争用教训） | 本轮新增规则 |

### 12.4 与 Route A 的 stage-2 内核的关系

留给后面：融合 NTT 只解决**乘法**。树版 stage 2 还需要多项式除法/余式（Newton，用同一套乘法实现）与多点求值（余式树）。CPU 侧参考正在实现（`tools/bench/stage2_tree_ref.cpp`），它会给出**每个层次真实的乘法尺寸与次数**，那才是把 §10.5 的 1.9e11 换成"我们自己的代码算出来的数"的依据，也是融合 NTT 该按哪些尺寸调优的依据。

### 12.5 待测的真设计选择：单层 Kronecker vs 两层（外层多项式 FFT + 每系数内层 FFT）

Prime95 走的是两层（§10.5 已由源码定论），我们原计划走单层 Kronecker。两者的显存与流量结构不同，**必须各测一版**才能定，不能靠推理：

| | 单层 Kronecker（现探针） | 两层（Prime95 式） |
|---|---|---|
| 变换对象 | 一个 `P·(2S+log2 P)` 位的数 | 外层 `~2P` 个元素（每个是全宽残数）× 每系数内层 FFT |
| 变换长度 | ~2.1e8 words（P=132480 时 ~2 GB/缓冲） | 外层只有 `2P ≈ 265k`，但要做 320 "line" 次 |
| 每系数表示 | 2S+log2 P 位（≈10540） | 内层 320 words ≈ 20480 位（DWT 余量占大头） |
| 显存（P=132480） | 2–4 GB | ~339 MB/多项式 |
| 复杂度 | 一个 FFT + 槽内收尾（无全局 carry） | 需要外层/内层两级编排 + 行调度 |

**测法（都对拍 GMP 逐系数）**：
1. 现有探针（单层）在大形状上的 ns/操作数位与 pass 数；
2. 加一个 `--two-level` 模式：把系数按"每个占 320（或 512）words 的 DWT 槽"布局，外层 FFT 长度取 `2P`，内层复用同一套融合 NTT 核做 320 个 line —— 等价于把"1 个大变换"换成"320 个小变换"（这正是 gpuowl 那种 3-D 分解的自然用法：外层维度 = 320 line，内层维度 = 2P 元素）；
3. 比较两者的**墙钟**（不是操作数位，§10.5 已说明该口径不可比）与显存峰值。

### 14.1 NTT 探针失败的真因（读代码定位，2026-09-30 第六轮）

`bad_slots=127`（= 2P−1 全错）不是边界情形，是**每级索引分解写错**。以它自己的参数为例（N=1024、stage 0，调用处 `half = N>>(stage+2) = 256`、`stride = N>>(stage+1) = 512`）：

```
blk = tid/256 ∈ {0,1} ; off = tid%256 ; j = blk % stride = blk ; base = 0
i0 = blk + off ∈ [0,257) ; i1 = i0 + 512
```

⇒ 这一级只做了蝶形 **(0..256) ↔ (512..768)**，而 radix-2 DIF 的 stage 0 需要**全部** `(j, j+512)`、`j ∈ [0,512)`、扭因子 `w^j`。三个后果同时存在：① 索引 257..511 与 769..1023 **从未被处理**；② `i0 ∈ 1..256` 被两个线程组**重复写（竞态）**；③ 扭因子用的是 `w^{blk}`（只有 0 或 1）而不是 `w^j`。任何一条都足以让所有槽出错，合起来就是"每次改一处 `got` 值就变一次"的现象。

**正确分解**（蝶形数 = n/2，一趟一级）：

```
tid = block * stride + j,  j ∈ [0,stride),  block ∈ [0, n/(2*stride))
base = block * 2 * stride ;  i0 = base + j ;  i1 = i0 + stride ;  tw = w^{j * exp_step}
```

即调用时应传 `half = stride`（不是 `n>>(stage+2)`），内核里取 `block = tid/stride`、`j = tid%stride`。验证：N=1024、stage 0 ⇒ 1 个 block、j 遍历 [0,512)、`exp_step=1` ⇒ 正好是 `(j, j+512)` 配 `w^j` ✓；stage 1 ⇒ 2 个 block、base ∈ {0,512}、j ∈ [0,256)、`exp_step=2` ⇒ `w^{2j}` ✓。

**另一处需要一并检查**：逆向调用的是**同一个 DIF 形状的内核体**（`a[i1] = (u−v)·tw`）却按 `stride = 2^s` 递增、`exp_step = N/stride`（注释里写的是"DIT stage"，但内核体是 DIF）—— DIF 网络的匹配逆向是 DIT 网络（`a[i0] = u + v·w`、`a[i1] = u − v·w`），这两者不能共用同一个体而不加证明。

**流程上的教训（比这个 bug 更重要）**：探针里本来就有 `dft_direct_kernel`（O(n²) 直接 DFT，与索引代数无共享），但**没有被接进自检**，所以变换本身的错误只能以"所有槽都错"的形式暴露。正确的自检顺序应当是：① 前向 NTT 对拍直接 DFT（n=8/16）；② `inverse(forward(x)) == x` 逐位相等（定位归一化与 DIF/DIT 配对）；③ 再做完整流水线。**先有单元级的 oracle，再谈端到端** —— 这条与 §7.3 记录的两个"静默出错"教训是同一类。

| 位反转约定 | `bitrev_kernel` 是 `dst[i] = src[bitrev(i)]` ✓（DIT 位反转输入所需的那一种） |
| 点乘里的"对齐扭因子"过期 | `pointwise_twiddle_kernel(..., exp_scale = 0)` ⇒ 实际就是逐点乘，没有残留技巧 |
| 级内索引分解 | 已按 §14.1 修正（`g=tid/half`、`j=tid%half`、`i0=g·stride+j`、`i1=i0+half`）|

⇒ **范围缩到最后一环：进位（carry）与槽组装（slot assembly）** —— 逆变换输出的每个 word 是多达 344 项 25 位乘积之和（可达 ~58 位），必须先按 `bpw` 进位；组装时的位偏移必须与打包时的 `i·slot_bits` 一致（该实现自己的注释也点出了这条约定）。已给出能一次定位的极小实验：**P=1 且 S 很小**（N 只有 2 或 4，每一步都能手算：pack → 前向 → 点乘 → 逆向 → 进位 → 组装，期望值就是 `a0·b0`），再做 P=2/P=4（一个是回卷/进位的分界）。

**注**：这一节记录的是"证据链"而不是结论 —— 三次读代码诊断（约减公式、级索引、本节的排除）都是先给算术、再看对方一次改对，这个节奏比"让它自己猜"快得多。

### 14.3 NTT 探针：找到两处一行 bug（读代码确定，2026-09-30 第九轮）

范围收敛到"进位 + 组装"之后，进一步定位到**两处各自一行的错误**，且都能解释此前观察到的现象：

| bug | 代码 | 后果与现象 |
|---|---|---|
| **① 前向变换的位反转自我别名** | `ntt_forward` 里 `(void)scratch;` 之后直接 `bitrev_kernel(src, dst)`，而调用处是 `ntt_forward(dA, dA, …)` ⇒ **src == dst**，而内核写的是 `dst[i] = src[bitrev(i)]` | 原地位反转**只能**用交换实现（`if (i < r) swap(a[i], a[r])`）；用"按位反转读、顺序写"在 dst 与 src 同一块时是读后写竞态 ⇒ 结果未定义。**这解释了"每次改代码 `got` 就变"** |
| **② 槽组装读错缓冲** | 进位三步都是对 `dA` 做（`carry_extract(dA,…)` → `carry_scan` → `carry_add(dA,…)`），但 `slot_assemble_kernel` 传的是 **`dC`** | 逆变换的结果在 **`dA`**（`ntt_inverse` 是 bitrev `d→scratch`、再 `memcpy scratch→d`、再在 `d` 上做级与缩放），`dC` 只是它的位反转临时区 ⇒ 组装的是无关数据。**这解释了 `got` 变成精确的 0**（该缓冲在这些形状上基本是 0）|

两处修好后，按 §14.2 的 P=1/P=2 手算用例应当直接通过，再跑 `poly 64 64 / 128 257 / 512 1024` 即可拿到第一个 `ok=1` 与真实的 `ns_per_operand_bit`。

**方法论小结（三轮连续应验）**：这一路三个 bug（约减公式丢 `hi·(2³²−1)`、级内索引分解、本节的别名与读错缓冲）**都是靠"读代码 + 手算期望值"定位的，而不是靠试**。对 GPU 代码尤其如此：一次运行只给"全错"这种整体信号，把信号拆成"哪个缓冲、哪个偏移、哪个约定"只有靠读代码与算术。这条已经写进本节的记录里。

### 14.6 变换对的规范形式（接手者直接用这个，不要再试排序）

子代理最终定位到：**算术全对**（约减 200 000 例、twiddle、bitrev 内核、O(n²) 直接 DFT oracle 全部 0 错，`P=1` 也给 `ok=1`），错的是**前向/逆向这对网络的排序**，而它在反复试验中把 17:25 那个可用状态覆盖掉了。结论：**不要再靠试排序代数**，用下面这个规范配对，它**不需要任何位反转内核**（这正是它的价值：所有可能的置换 bug 都来自 bitrev 那一环）：

```
前向 = DIF (Gentleman-Sande)，half 递减，输出为"位反转的频率序"：
  for (half = n/2; half >= 1; half >>= 1) {
      stride = 2*half;  exp_step = n/(2*half);
      for g in [0, n/stride): for j in [0, half):
          i0 = g*stride + j;  i1 = i0 + half;
          u = a[i0]; v = a[i1];
          a[i0] = u + v;                       // 先加
          a[i1] = (u - v) * omega^(j*exp_step); // 后乘
  }

逆向 = DIT (Cooley-Tukey)，half 递增，输入为"位反转的频率序"，输出自然序：
  for (half = 1; half < n; half <<= 1) {
      stride = 2*half;  exp_step = n/(2*half);
      for g in [0, n/stride): for j in [0, half):
          i0 = g*stride + j;  i1 = i0 + half;
          u = a[i0]; v = a[i1] * omega_inv^(j*exp_step);  // 先乘
          a[i0] = u + v;                                 // 后加/减
          a[i1] = u - v;
  }
  最后每个元素乘 n^{-1} mod p
```

三处差异（就这么点）：① half 循环方向相反；② DIF 先减后乘、DIT 先乘后加减；③ 根用 ω 与 ω⁻¹。两者的 `stride`/`exp_step` **完全相同**。位反转序由前向产生、被逆向消费，逐点乘夹在中间 ⇒ **全程不需要显式置换**，`ntt_forward`/`ntt_inverse` 里的 bitrev 调用（以及随之而来的那次整块 `cudaMemcpy`）应当删掉。

**n=4 的手算校验**（ω² = −1）：前向 half=2 得 `a=[x0+x2, x1+x3, x0−x2, (x1−x3)ω]`，half=1 得 `b=[X0, X2, X1, X3]` —— 即 `b[i] == X[bitrev(i)]`；所以 `nttcheck` 必须**按这个顺序**比对直接 DFT，而不是比 `b[i] == X[i]`（这大概是它一直"forward-vs-directDFT bad=3/4"的原因之一）。

**另外两条待办（子代理自己报告的）**：
* `carry_scan_kernel` 是**分块前缀和、没有块间偏移进位** ⇒ 仅当进位链从不跨块时才对。`P=1024/S=5153` 时 N = 2^21 words = 8192 块，必须**用测试**（而不是推理）确认；静默的进位错误正是后面会变成"找不到因子"的那类 bug。
* `slot_assemble_kernel` 必须读**逆变换写入的 `dA`**（它说刚改对）—— 这一条加上上面的配对，正是 17:25 那次 `ok=1` 的配方。

3. 门禁顺序：`poly 4 64 1 1`（可手算）→ `poly 64 64 1 1` / `128 257` / `512 1024` → 再测 `poly 1024/8192/65000 5153` 两次（device 1 已空闲）。

**性能数字的口径**：`ok=0` 时打印的 `ns_per_operand_bit` 无意义，测不了。唯一有效的 M2 基线仍是我在 §14.5 记录的、**几何相同**的那一次：`P=1024/S=5153`（bpw=20、slot_bits=10316）**2.2246 ns/操作数位**，对同形状 fp64 cuFFT 的 0.2839 ⇒ **慢 7.8×** —— 这是"未融合、每级一趟"首版的合理基线，杠杆在融合层数（§12）。

### 14.8 我接手修了组装内核的两处真 bug；仍剩一处（2026-09-30，子代理已结束）

子代理到预算上限后我接手（它已结束 ⇒ 无并发编辑风险）。读 `slot_assemble_kernel` 发现**两处确定的错误**并修掉：

| bug | 原代码 | 为什么错 |
|---|---|---|
| **Horner 步不是 `v·2^bpw`** | `v = ((v << d) - v + x) % SLOT_MOD`，`d = 64 - bpw` | `(v<<d) - v = v·(2^(64−bpw) − 1)`，**与 `v·2^bpw` 无关**；而且 `v << (64−bpw)` 在多数 bpw 下溢出 64 位。正确：`v = ((v << bpw) + x) % SLOT_MOD`（`v < SLOT_MOD < 2^32`、`bpw ≤ 31` ⇒ 不会溢出）|
| **窗口多读一个字并全按 bpw 掩码** | 循环跑 `words_per_slot + 1` 次，每个字都 `& (2^bpw − 1)` | 最高字里**超过本槽的位属于下一个槽**，被当成高位喂进本槽 ⇒ 相邻槽互相污染。正确：循环 `words_per_slot` 次，且最高字按本槽在其中的实际位数 `top_bits = slot_bits − (words_per_slot−1)·bpw` 裁剪 |

两处都已改、构建通过、`poly 1 8` 仍 `ok=1`（无回归），`P=4/64` 的 `got` 值随之改变，但**仍未 `ok=1`** ⇒ 抽取路径上还至少剩一处。

**我犯的一个方法错误（记下来）**：我用"`poly 4 64` 的手算例"验证修复，前提是子代理描述的"A=1、B=x^1 ⇒ 只有 slot 1 为 1"。但实测 `want=791451053 ≠ 0` ⇒ **输入根本不是 1 与 x**，那个手算前提是假的。**教训**：手算校验必须先**打印实际输入系数**再造期望值，不能采信对输入的转述 —— 这与 §14.4"测试先干跑"是同一类问题（**先确认你验证的是你以为的那个东西**）。

**下一步（唯一剩下的路）**：在极小形状上把**输入系数、打包后的字数组、逆变换输出字数组、进位后字数组、组装结果**一次性全部打印（同一缓冲、同一路径），用真实输入手算期望乘积，然后只盯抽取逻辑（`shift`/`top_bits`/`x |= nxt << (64−shift)` 的组合以及掩码与移位的先后）。现状：变换已由独立 O(n²) 直接 DFT 对拍证明正确，**问题只在最后一个内核算术**。

### 14.9 抽取已修对（模型验证）；剩下的是上游数字数组（2026-09-30，我接手后）

**新增工具** `tools/bench/slot_extract_model.py`：**把"抽取"从 NTT 里完全隔离出来** —— 用 Python 大整数算出精确乘积，按其 **bpw 位数字数组**（探针 `c[]` 的布局：每个 64 位容器只放 bpw 位）跑一遍当前抽取逻辑，与真实系数比对。这样"抽取错"与"上游数字数组错"被彻底分开，且不需要 GPU。

**它抓到了第三处真 bug**：跨数字拼接用的是 `x |= nxt << (64 - shift)`，但 `c[]` 元素是 **bpw 位数字**（不是 64 位字）⇒ 必须左移 **`bpw - shift`**。改前：`P=4/64/128/512` 分别 `bad=6/121/244/511`（**只有 slot 0 对，因为 slot 0 的 `shift == 0` 不需要这一步**）；改后：**四档全部 `bad=0`**（7/127/255/1023 个槽全对）✓

**同一处已改进内核**（`slot_assemble_kernel`，注释里写了隔离过程与依据），构建通过；但设备端 `poly 4 64` / `64 64` / `128 257` 仍 `ok=0`，且 **`bad_slots` 计数未下降**（P=64 仍是 127）⇒ **不是抽取的问题了**。

**由此得到的确定结论**：`c[]`（逆变换 + 进位之后的数字数组）**本身不是精确乘积的数字数组**。因为：
* 抽取逻辑已由独立模型证明正确（给定正确数字 ⇒ `bad=0`）；
* 报告里的 `got` 取自 `hOut[first_bad_slot]`，而 `first_bad_slot=0` 且 slot 0 的 `shift==0` ⇒ 若上游数字正确，slot 0 必然正确（模型如此），现在它错 ⇒ 上游错。

**下一步（唯一且明确的一步）**：在**极小形状**上把三个数组同路径打印出来对比 —— ① 主机端按**同一批系数**算出的精确乘积数字数组；② 设备端**逆变换后、进位前**的数字数组；③ 设备端**进位后**的数字数组。差异范围直接指认病因：
* 只有低位数字错 ⇒ 进位；
* 全部数字错 ⇒ 前向/逆向的配对或点乘；
* 高半区是垃圾 ⇒ 零填充/回卷；
* 只有高于某个下标的部分错 ⇒ 进位扫描的块间传播（该处刚改过，值得优先看）。
为此探针需要一个"打印输入系数 + 打印中间数组"的调试入口（现有 `dbg` 只打了 24 个数字且是单个缓冲），并**必须先打印真实输入**再谈手算期望值（§14.8 的教训）。

### 14.10 NTT 验证完成：根因是两个上游缺陷，四个形状全部 ok=1（2026-09-30）

**我自己复测（device 1，18:40 构建）**：

```
poly: P=4   S=64   slot_bits=130  bpw=27 nwords=64     ok=1
poly: P=64  S=64   slot_bits=134  bpw=25 nwords=1024   ok=1
poly: P=128 S=257  slot_bits=521  bpw=24 nwords=8192   ok=1
poly: P=512 S=1024 slot_bits=2057 bpw=22 nwords=131072 ok=1
```
（`ok=1` = **每一个系数**都与 GMP 教科书乘法的模投影相等；行内无 `detail=` 即无坏槽。）

#### 根因 1（关键）：打包破坏了精确性判据 —— 而判据本身还在说 OK

打包被改成"紧凑"布局（系数 i 放在 bit `i*slot_bits`，而 `slot_bits = 2S+log2 P` **不是 bpw 的整数倍**），于是写入用了
`h[bit/bpw] |= v << (bit%bpw)` —— 这会让每个数字（digit）**溢出到下一个 digit 的低位**，一个 digit 实际可容纳到 `2^(2bpw−1)`，而不是 `2^bpw`。真实卷积界因此变成 `N·(2^(2bpw−1))²`（P=4/S=64 时 ~2^112；P=1024/S=5153 时 ~2^99），**远大于 p** ⇒ **每个乘积系数都模 p 回绕** ⇒ `bad_slots = 2P−1`（连 slot 0 也错）、几何与耗时完全不变 —— 这正是 §14.5 记录的那次"同几何回归"的真身。

**最值得记的一点**：代码里那条 `N·(2^bpw)² < p` 的检查**一直打印 OK**，因为它检查的是**设计意图**而不是**实际数据**。修法两步：① 打包与组装统一改用**按字对齐的槽距** `slot_stride = ceil(slot_bits/bpw)*bpw`；② 增加**硬断言**：每个操作数 digit 必须 `< 2^bpw`（在 `run_poly` 里）。**教训：精确性判据必须由实际数组的值算出，不能由设计假设推出** —— 否则判据会替 bug 背书。

#### 根因 2：进位数学本身错

`carry_add` 把"i 之前所有商的**前缀和**"加到 `c[i]` 上，但正确的进位权重是 `2^(bpw·(j+1−i))`，不是 1 ⇒ 它**超额累加且不保值**（`c=[2^bpw, 2^bpw]` 会变成 `2^bpw + 2·2^(2bpw)` 而不是 `2^bpw + 2^(2bpw)`）。已换成**精确的 ripple**（`q[i]=c[i]>>bpw`、掩码、`c[i]+=q[i−1]`，重复约 `(k+2bpw)/bpw+2` 轮），并加了**设备端收敛断言**（残余 digit 必须全部 `< 2^bpw`，实测为 0）。顺带删掉了 `carry_scan_blocks_kernel` —— 它用 `j` 索引 256 项共享数组而上界是 `nb−1`，`N ≥ 65536` 时越界。

#### 一个 Windows/GMP 陷阱（值得全局记住）

`mpz_add_ui` 在 Windows 上按 `unsigned long`（32 位）截断 —— 它一度"证明"一个正确的变换是错的，改用 `mpz_import` 才恢复正常。

#### 现在的状态与下一步

* **乘法层（§17.2 门禁 1）**：`P=4/64/128/512` 全 `ok=1` ✓；`1024 2048` 正在跑；随后按 §17.4 的纪律测 `P=1024/8192/65536 × S=5153` 的 `ns_per_operand_bit`（device 1、两次取中位数、`ok=0` 的数字不报）。
* 新增调试入口 `pipedump <P> <S> <dev>`：同时打印 ① 主机 GMP 算的精确乘积数字数组 ② 设备逆变换后 ③ 进位后，并给出首个差异下标 —— 正是 §14.9 要求的那件工具，留着给后面所有流水线问题用。

### 11.4 gpuowl 的 CUDA 实现与九种路径的差别（详见 `docs/DEV_GPUOWL_CUDA_FFT_PATHS.md`）

完整规格 250 行、逐条 `file:line`，写在 `docs/DEV_GPUOWL_CUDA_FFT_PATHS.md`。这里只留**影响我们设计**的结论：

| 事实 | 对我们的意义 |
|---|---|
| **它没有独立的 CUDA 内核**：`.cl` 源在构建期嵌入二进制（`genbundle.sh` → `src/bundle.cpp`），**运行时由 NVRTC 编译**；`src/cuda/clwrap_cuda.cpp` 用 cu* 驱动 API 重新实现 cl* API，`opencl_compat.cuh` + 一个**文本级预处理器**把 `__kernel`→`extern "C" __global__`、`reqd_work_group_size`→`__launch_bounds__`、`local T x[`→`__shared__` 等 | 好处是可复用它的 `.cl`，代价是**动态共享内存恒为 0、work-item dim≠0 不支持、原子序/作用域被丢弃、且没有 FP64 能力查询**（`hasFP64()` 无条件返回真 ⇒ 在 fp64 只有 1/64 速率的消费卡上 FFT64 照样编译）。我们**不需要**这套 shim：我们自己写 CUDA 内核即可 |

| **精确 vs 近似**：`FFT61`（模 M61）、`FFT3161`/`FFT323161`（进位时 CRT）是**精确**的；`FFT64`/`FFT32` 是**近似**，靠 ROE 判据 | 我们用整数 NTT 的"精确性红利"（§11.2）与它的精确路径同类 |
| bpw 表是**实测经验值、不是保证**：表里记着一次硬失败 —— *"LL of 100028317 failed (ROEmax=0.294…). Lowering bpw from 23.94 to 23.84."* | 位宽必须**按实际数据断言**（正是 §14.10 根因 1 的教训：判据不能由设计意图推出）|
| **对我们形状的建议（它的推导，已标注）**：~20–30 位 Kronecker 数字应取 **M31+M61 这一对**（92 位窗口 ⇒ `log2 L + 2d < 92`）；M61 单独在短 L 下只到 ~24 位（`d < (61 − log2 L)/2`）；**绝不要 M31 单独**（bpw 在 `50:4K:16:1K` 上崩到 7.05）| 我们的探针用**单个 Goldilocks**（容量 64 位 ⇒ `2d + log2 L < 64`）⇒ L=2²¹ 时 d ≈ 21，与实测选择的 `bpw=20` 一致 ✓。换成 M31+M61 可把每字节载荷从 ~2.5 提到 ~3.38（**1.35×**，付出两次变换 + CRT 重组的代价）⇒ 记为 §12.5 融合轮的**候选** |
| **该抄 / 不该抄**：抄**分解形态**（width×middle×height，只有转置阶段碰全局内存；一般乘积用 `tailMul`/`pairMul`）；**不要** IBDWT（只对 `2^E−1` 形态成立，非 Mersenne 模数用不上）、**不要** `n61·M31+n31` 的 CRT 进位（我们的 Kronecker 槽宽本来就不让进位跨槽）| 直接指导 §12 的融合设计与 §12.5 的对比实验 |

### 14.11 M2 的第一个可用数据点（ok=1 下测得，2026-09-30）

四个形状 `ok=1` 之后（§14.10），NTT 探针的计时**才有意义**。我自己在 device 1 上各测两次：

| 形状 | bpw | ok | ns/操作数位（两次） | 同形状 fp64 cuFFT | 比值 |
|---|---|---|---|---|---|
| P=1024, S=5153（slot=10316） | 20 | 1 | **2.1773 / 2.1773** | 0.2839 | 慢 7.7× |
| P=8192, S=5153（slot=10319） | 18 | 1 | **2.7918 / 2.7977** | 0.278 | 慢 10.0× |

**怎么读这两个数**（避免误判）：

* 它们**不是**"整数 NTT 比 fp64 慢 8–10×"的证据，而是"**每级一趟 kernel 的未融合实现**比 cuFFT（自带 ~18 趟融合 + 但吃 12 位分块的 4× 浪费）慢 8–10×"的证据。§12.1 早就算过：朴素实现每元素要搬 1152–1344 字节而只承载 ~20 位载荷（~48–56 字节/操作数位），而 cuFFT 路径是 ~0.43 字节/操作数位 —— **差两个数量级**，实测只差 8–10× 说明 NTT 的算术密度确实帮忙抵消了一部分。
* 因此 §12.3 的 `≤0.10 ns/操作数位` 门槛**不是**靠换模数能到的（§10.3/§11.4：整数化只值 1.3–1.4×），必须靠**融合**（把 24–28 趟压到 6–8 趟）拿到 3–4×，再叠加 15 位 chunk 与消除填充各 ~1.2×。
* `bpw` 随 P 从 20 降到 18（P 越大打包位数越多、N 越大 ⇒ `2d + log2 L < 64` 的余量变小）✓ 与 §11.4 里 gpuowl 的规则同构（它用 92 位窗口 ⇒ 可以到 ~30 位）。
* 两次测量偏差 ≤0.2 % ⇒ 设备干净、数字可信（§17.4 的纪律）。

**至此目标 (1) 完成**：逐系数对拍 GMP 的多形状 `ok=1`（§14.10 + 本节）＋ `ns/操作数位` 实测并与 cuFFT/门槛对照（本节）。剩下的是 §12 的融合（把 2.18 → ≤0.10）与目标 (3) 的真实参数 GPU 验证（§17，需 GPU 树版引擎）。

### 14.13 崩溃根因（GMP use-after-free）+ 融合首次跨过 cuFFT（2026-09-30）

#### 崩溃根因：对已 `mpz_clear` 的 `mpz_t` 写入

用户报告的现象是 Windows 访问违例弹窗（"引用了 0xFFFF… 内存不能为 read"），子代理也独立观察到"**~5–7 % 的调用无任何输出地猝死**（`0xC0000005` 访问违例 / `0xC0000374` **堆损坏**），且死在**第一条输出之前**"。根因是我在读启动期 selftest 时定位到的：

```c
mpz_clears(p, a, b, z, want, got, nullptr);   /* 这里清掉了 want */
...
mpz_mod(want, hi2, p2);                        /* ✗ 又用 want */
```

`mpz_clear` **只释放 `_mp_d` 而不把结构体置零**，所以 `mpz_mod` 会向**已释放的堆块**写入 ⇒ 堆损坏 / 访问违例。这解释了全部特征：**间歇**（取决于分配器是否复用或解映射了那块内存）、**~5 %**、**死在第一次 `printf` 之前**（该块在第一条输出之前）、偶尔挂死、连私有副本也 1/30。修法：在该块内改用局部 `w2`（已加注释说明原因）。

**验证**：改后连跑 **100 次 `poly 64 64 1 0`：无输出猝死 0 次、`ok=1` 100 次**。若猝死率仍是 5 %，100 次全过的概率只有 0.6 % ⇒ **根因确认**。

**教训**：`mpz_clear` 之后再次使用同一个 `mpz_t` 是**未定义行为且不会报错**；这与 §14.10 那条"`mpz_add_ui` 在 Windows 上按 32 位截断"同属一类 —— **GMP 的静默陷阱**。凡是"函数返回前 `mpz_clears`、之后又复用同名变量"的地方都要查（本文件的 device selftest 段已修）。

#### 融合首次见效：从"比 cuFFT 慢 8–12×"到"比 cuFFT 快 1.2×"

### 14.14 融合完成：13 趟、12–17× 提速、并给出"为何还差 2.4×"的实测解释（2026-09-30）

**做了什么**（单文件 `tools/bench/ntt_poly_probe.cu`，CLI/字段不变，新增 `passes=`；**一趟 = 整数组的一次读 + 一次写**，已写进文件注释）：

1. **外层寄存器级融合 radix-16**（`NTT_FUSE_M=4`）：间距最大的 4 级在寄存器里做完，一次遍历覆盖 4 级；twiddle 用增量生成（每组 1 次粗表读 + 若干平方）替代逐元素"平方乘"。前向 3 趟、逆向 3 趟。
2. **TILE 趟**（`t=12`）：最窄的 12 级在 **一个 32 KB 共享内存 tile** 内一次做完（radix-4 融合块）；**逆向 tile 趟顺带吸收了点乘与 1/N 缩放**（又省 2 趟）。
3. **一趟进位**：ripple 轮次展开成寄存器锥（与逐轮递推位相同）。它**读 `c`、写另一个缓冲** —— 原地版有竞态（P=512 错 2 槽、P=1024 错 8 槽、非确定），即使 `fusecheck` 是干净的。
4. ⇒ **总共 13 趟**（原 ~88：`3k` + 点乘 + 缩放 + 12 进位 + 组装）。

**实测（device 1 空闲、各测两次、`ok=1`、偏差 ≤1 %）**：

#### 为什么 0.10 没到（**实测**，不是估计）

* **带宽下界**：device 1 实测可达拷贝带宽 **200 GB/s** ⇒ **一趟 = 1.34 ms**。13 趟 + 组装 0.56 ⇒ **18.2 ms 下界 = 0.108 ns/位** ⇒ **即使零计算，当前趟数也到不了 0.10**。
* 逐核计时（P=8192）：外层趟 1.5–2.4 ms（下界 1.34）、tile 趟 3.4/3.8 ms（下界 1.34）、进位+组装 3 ms。
* TILE 趟是**模乘依赖链的延迟受限**：只删掉它的 twiddle 乘法（用 scratch 拷贝代替）就从 3.4 → 1.5 ms，而每元素算术量不变。
* radix-32/64 外层趟**溢出**（128 寄存器不溢，radix-64 用 255 寄存器 + 384 B/线程）**并且更慢**：M=4 → 0.167（13 趟）、M=5 → 0.181（13 趟）、M=6 → 0.224（10 趟）。

#### 最大的剩余杠杆（它没动，因为我当时说"精确性判据不许改"——**我那条指令过于保守**）

判据 `N·(2^bpw)² < p` 里的 `N` 是**保守**的：卷积系数的真实项数上界是 **`L = P·slot_words`（非零数字个数）**而不是 `N`。用 `L` 之后，`P=8192/S=5153` 可允许 **bpw=21**（`slot_words=492`、`L=4.03e6`、`2L=8.06e6 ≤ 2^23`）⇒ **N 从 2^24 减半到 2^23 ⇒ 全部流量与遍数下界减半 ⇒ ~0.108 → ~0.055 ns/位**，**一举跨过 0.10 门槛约 2×**。

注意这是**收紧**（用真实项数）而不是放宽：判据必须 ≥ 实际最大卷积系数，而实际系数是 `L·(2^bpw−1)²`；并且按 §14.10 的教训，**断言必须由实际数组的值算出**（已有的"每个操作数 digit < 2^bpw"断言正是为此）。这件事值得单独一轮并配自己的 GMP 验证。

其他未取的小项：(d) 无分支展开的 `gl_reduce`（4 次无条件折叠在 `hi==0` 后是可证明的恒等），实测 **+3 %** —— 它当时没动也是因为我要求"约减不动"，同样属于我指令过严；有 200k 例 GMP 自检在，性能改动是安全的。

### 14.15 **M2 门槛达成**：判据由 N 收紧到 L，N 减半（2026-09-30）

#### 做了什么

精确性判据从 `N·(2^bpw)² < p` 改为 **`L·(2^bpw−1)² < p`，其中 `L = P·slot_words`**（每个操作数**非零**数字的个数；每个系数独占一个按字对齐的槽，载荷之外全为 0）。

**这是收紧而不是放宽**，且被**证明 + 独立实测**（不是假设）：

* 推导：`c_k = Σ_{i+j≡k} hA[i]·hB[j]`，两个操作数各最多 `L` 个非零数字 ⇒ 固定 k 最多 `L` 对非零乘积；加上"每个 digit < 2^bpw"这条**按实际数组值**算的硬断言，得 `c_k ≤ L·(2^bpw−1)²`。`L` 由 P 与 slot_words 算出并在 GMP 精确算术里与 p 比较（旧的 N 形式仍打印出来作对照）。
* **独立实测**：`A = Σ hA[j]·2^(64j)`、`B` 同理 ⇒ `C = A·B` 的**第 k 个 limb 就是 `c_k`**（只要 `c_k < 2^64` 就不会有跨 limb 进位），所以当 `L ≤ 8M limbs` 时 **2L−1 个系数的真实最大值是被"测量"出来的，不是抽样**：
  * `P=8192/S=5153`：`L=4 030 464`，界 `2^63.943 = 0.9609·p`（余量 1.041×）✓；实测 `max c_k = 2.2078e18 = 0.1197·p = 界的 0.1246`（**界内还有 8 倍余量**）。
  * 其他形状实测 `max c_k / p`：0.0215(4/64)、0.0294(64/64)、0.0674(128/257)、0.0820(512/1024)、0.0862(1024/2048)、0.0570(1024/5153) —— 全部远在各自**已证明**的界内。
  * `bpw=22` 在 P=8192 上需要 `6.77e19 = 3.67·p` ⇒ **不可证明**，所以 **bpw=21 是上限**。这条"证明而不是调参"的纪律正是 §14.10 根因 1 换来的。

#### 结果（device 1 空闲、各测两次、`ok=1`，无 `ok=0` 数字）

| 形状 | bpw | N | 趟数 | **ns/操作数位** | 之前 |
|---|---|---|---|---|---|
| P=1024, S=5153 | 22 | 2²⁰ | 10 | **0.0858 / 0.0879** | 0.1776 |
| **P=8192, S=5153** | 21 | 2²³ | 13 | **0.0843 / 0.0845** | 0.1676 |
| P=65536, S=5153 | 19 | 2²⁷ | 16 | 0.1803 / 0.1826 | 0.1854 |
| **P=92160, S=5261（§17 的 P2 真实形状）** | 19 | 2²⁷ | 16 | **0.1275 / 0.1278**（4097 MB，11 系数 GMP 抽样 bad=0） | 首次融合版测量 |

⇒ **`P=8192/S=5153` = 0.0843 ns/操作数位 ≤ 0.10 ⇒ §12.3 的 M2 门槛达成，余量 2.0×。**

**换算成 §17 的语言**：0.0843 ns/位 × 4.3e11 位/曲线（§15.1 的 P1 口径）≈ **36 s/曲线**，对 Prime95 的 28.6 s 是 **1.27×**（首次进入"同量级"）；对同一个 fp64 cuFFT 原型（0.278）是 **3.3×**。

## 18. GPU 树版引擎（M3 的 GPU 侧）：分片计划与 oracle

乘法层（§14.15：0.0843 ns/操作数位、M2 门槛达成）已经是一块可用的积木。剩下的是**树**。为了不让"整块未验证"重演，按**每片都有独立 oracle** 切：

| 片 | 内容 | oracle（必须是逐系数/逐项可比的） | 状态 |
|---|---|---|---|
| **S1** | 系数向量 mod N 的表示 + 多项式加减乘（**乘法复用 NTT 而非复制**）+ **baby 点积树** `F(X)=Π_j(X−x_j) mod N` | 给 `stage2_tree_ref.cpp` 加 `--dump-F`，与 GPU 的 F **逐系数相同（mod N）**；两个形状（D=210 ⇒ P=24；D=2310 ⇒ P=240） | **已完成** ✓ 见 §18.1 |
| S2 | Bernstein **余式树**（F 在 giant 点的多点求值）+ 累乘 + gcd | 冻结向量必须给出 `factors=59649589127497217` 且 `hit_primes=114713`（与配对参考、与 CPU 树版参考**两者**相同） | **已完成**（主机编排版）✓ 见 §18.1 |
| S3 | **分批结构**（F 树一次 + 每轮 G 树 + 3 次 `H=G·H mod F` + 一次下降）—— §13.1 实测它比简单版便宜 ~6×（冻结形状）/~2.7×（M5261 形状） | 与 S2 的输出**逐字段相同**（因子集与 `hit_primes`），且逐层与 CPU 的 `--cost` 口径对齐 | **已完成** ✓ 见 §18.2 |
| S4 | 真实参数（§17 的 P2：D 取显存允许的最大值、P≈92160、S=5261）+ 每曲线墙钟 | §17 的三道门禁；墙钟与 §17.3 的预期带（30–45 s/曲线）对照 | 待 S3 |

**几条先定下来的工程约束**（避免后面返工）：

1. **乘法只能有一份实现**：GPU 树必须调用 `ntt_poly_probe.cu` 里那套（已由四个 oracle 保护的）乘法，而不是把它抄一遍 —— 否则两处会漂移（§14.8 那条"镜像与实现各自漂移"的教训）。
2. **系数表示要显式记录**（bpw 位数字数组 / N 的 limb 数组？）—— S2/S3 的内存布局与显存预算都依赖它；且 NTT 的精确性判据 `L·(2^bpw−1)² < p` 要按**新的 P** 重新证明并断言（§14.15）。
3. **baby 点必须与 CPU 参考同源**：`x_j = x([j]Q)`，`Q = [s]P`，`s = torsion·lcm(1..B1)`，`torsion=1`。最稳的做法是让两边的 Q 由同一个入口给出（命令行传入），而不是各自重算。
4. **S1/S2 的形状都小**（P=24/240、S=129），所以**先不谈性能**：S1/S2 只证明正确性；性能在 S3/S4 才谈，且那时才需要显存预算器。
5. 显存现实（§10.6）：P 决定内存而总工作量 ∝1/D ⇒ 真实形状要取"**显存装得下的最大 D**"；S4 必须跑一次显存预算（P=92160/S=5261 时 NTT 缓冲 4097 MB，见 §14.15）。

## 20. 工具崩溃把命令行挂住：三层防御（2026-09-30）

探针崩溃时 Windows 的"该内存不能为 read"对话框会把进程挂住 ⇒ 父 `cmd` 永不返回 ⇒ 测试/子代理命令行等几十分钟。
三层防御见 `docs/DEV_WINDOWS_CRASH_HANDLING.md`，**每层都有实测证据**：

1. **每机**：`HKCU\...\Windows Error Reporting\DontShowUI=1`（无需管理员，已在本机启用）。验证方式是用一个**必然崩溃**的小程序（`tools/diag/crash_test.c`）：改前挂住，改后 **0.3 s 返回、无弹窗**。
2. **每进程**：自己的工具在 `main` 第一行调 `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)`（三行，与注册表无关、换机有效）。**尚未逐文件落地**（写作时 `stage2_tree_gpu.cu`/`ntt_poly_probe.cu` 正被子代理编辑），由第一层先保护。
3. **每次运行**：`tools/test/run_with_timeout.ps1` —— 输出重定向到**文件**（不走管道，避免写满阻塞）、给墙钟预算、超时**杀整棵进程树**、返回 **124**。实测：5 s 预算跑 30 s 睡眠 ⇒ `exit=timeout`、6.3 s 返回、**残留 0**；30 s 预算跑 2 s ⇒ `exit=0`、2.1 s。

坑清单（都踩过）：`Start-Process -ArgumentList` 会拼坏引号（子进程根本没启动）；`cmd /c "<exe>"` 以引号开头会剥掉引号（同样立刻返回 1）；`taskkill` 在受限沙箱被拒（故用 CIM 递归兜底，且**残留子进程会占着日志文件**让下一次运行瞬间失败并显示**上一次的日志**）；`powershell -File` 会把数组参数拼成字符串；后台 job 里 `Start-Process -NoNewWindow` 被拒。

### 18.4 分批下降崩溃：根因与修复（并纠正 §18.3 的判断，2026-09-30）

**根因**（`tools/bench/stage2_tree_gpu.cu` 的 `inv_series_batch`，即每次下降除法用的批量 Newton `1/a mod X^k`）：**三处耦合的操作数/slice-stride 错误**，每一处都**声明了一个其缓冲并不具有的 slice 数**，于是 `flat_truncate` 的 `memcpy` 读到了堆外：

1. `g` 分配成 `nbatch*W`（**一个**系数），随后 `g` 的元素个数又经 `out.resize(A.size()/ma*nc)` 放大了乘法结果的规模（`:2205`）；
2. 调用 `flat_mul_batch(L, at, am, g, len, ...)` 把 `g` 作为**第一个**实参传进去，却声明 `ma = am`（一个操作数长度）—— 于是它读 `at` 的低 `len` 个与全部 `g`，返回 `3*len-1`，而代码假设是 `am+len-1`（`:2256`）；
3. `flat_truncate(ag, nbatch, am+len-1, nxt, W)` 声明每 slice `nxt` 个系数，而乘积其实有 `am+len-1`（`:2257`）。

**修法**：把 `g/gpad/ag/gn/h` 统一规范成"每 slice `nxt` 个系数"并**强制零扩展**（保值：`mod X^len` 的逆在系数 `len..nxt-1` 上是 0）；`flat_mul_batch` 增加显式契约检查（`A.size()==nbatch*ma*W`）、`flat_truncate` 拒绝过短的源、`divmod_batch` 断言逆的尺寸确实是 `k`。

**这三处也解释了"F 树能过、G 树不过"的假象**：区别只是**哪一次下降除法先碰到坏形状**。

**定位手段（值得记住）**：进程内 `AddVectoredExceptionHandler` + DbgHelp 栈解析，配合 `/Zi` + `/DEBUG` 的 PDB 构建 ⇒ 栈为
`memcpy <- flat_truncate(:2106) <- inv_series_batch(:2229) <- divmod_batch <- descent_batched <- run_batched`。
这条路径比"猜 + 二分"快得多，且**直接把 §14.9/§18.3 那种"全错/全崩"的整体信号变成了具体行号**。

**修复后的证据**：
* 门禁全绿：`test_ntt_poly` 22/22、`test_stage2_tree_ref` 62/62、`test_stage2_tree_gpu` 13/13 ✓
* 冻结向量不变：`factors=59649589127497217 hit_primes=114713`，NTT 调用 5334 / 启动 1637（与修复前 S4 相同）✓
* **真实形状 D=510510/B2=1e8 首次跑完**：`exit=0`、`factors=42089 hit_primes=3511`、`descent_divmods=91800`、NTT 361636 次调用 / 82 次启动、`gmp_check_bad=0` ✓
* **一处回退（如实记录，不掩盖）**：冻结向量的分批墙钟从文档里的 0.50/0.53 s 变成 **0.87/0.72 s**（~1.5×），原因是零扩展填充。

**仍然阻塞（且与 §18.3 的判断不同，必须更正）**：`D=570570/P=51840/B2=1.94e12` 的真实形状在 ~113 s 处 `exit=1`、**stderr 完全为空**（另两次是 4–8 s 与 ~4 min），死在 P=32768/32769 的 G 树形状自检**之后**。**它不是主机访问违例**：文件自带的 `SetUnhandledExceptionFilter` 处理器编译在内却从未打印，进程内的 vectored 处理器也从未触发；而且死亡**非确定**。因此 §18.3 里"真实形状崩在访问违例"的说法**作废**，正确描述是：**非异常型死亡**，最可能是某个 CUDA 调用报错后 `std::exit`（真实 G 树 chunk 尺寸下的 CUDA OOM）或主机 `bad_alloc`。

### 18.5 真实形状"静默死亡"的真因：**显示驱动看门狗（TDR）**（2026-10-01）

**现象与纠错**：`D=570570/P=51840/B2=1.94e12` 跑到 ~113 s 就 `exit=1` + **stderr 完全为空**、非确定（4–8 s / 113 s / ~4 min）。§18.4 我猜"CUDA OOM 后的 `std::exit` 或 `bad_alloc`" —— **错了**，而且它连"失败的 CUDA 调用"都不是（`CK()` 会打印 `CUDA error … at file:line` 并以 2 退出，而 stderr 是空的）。

**真因（有系统日志证据）**：Windows 事件日志 `Get-WinEvent System -ProviderName nvlddmkm` 里有 **id 13（error）+ id 153（device reset）**，时间戳 **2026-10-01 03:15:59**，正是那次运行死亡的时刻（它最后一行是 `batched_progress: batch=4/66 … t=90.7 s`）。**TDR 重置会拆掉 CUDA 上下文并直接杀掉宿主进程，且不抛任何异常** ⇒ 这解释了全部疑点：`SetUnhandledExceptionFilter` 与进程内 vectored 处理器**都没触发**、**WER LocalDumps 目录里 0 个 dump**、stderr 为空、并且死亡时刻看起来"莫名其妙"。

**触发条件**：`s2g_launch_ladder` 曾**按 giant 点一对一开线程** ⇒ **一次启动 207360 个线程**，每个线程跑一条串行的 `2S = 10522` 步 Montgomery ladder ⇒ **单次内核约 12 s GPU 时间**，远超系统默认的 TDR 预算（带显示器的卡默认约 2 s）。**冻结形状看不到**（那里 giant 集只有 4763 点）⇒ 这是典型的**只在真实规模才暴露**的隐患。

**修法**：ladder 内核改**grid-stride**，启动器按点分块，任何一次启动不超过 `NTT_LADDER_CAP`（默认 8192，可用环境变量覆盖）。算术与结果不变，只是把一次长启动切成有界的多段。

**验证**：改后真实形状**整轮 fold 循环跑到 batch 66/66（100%）**，耗时 **1581 s**，`arena_overflow=0`、`fuse_builds=15 / fuse_reuse=31087`、**无驱动事件**（改前连 batch 4 都过不去）。门禁仍全绿（22/22、62/62、13/13），`TRCT` 已从源码与二进制中消失。

#### 这一条带来的两条长期规则

1. **任何单次内核启动都不得超时**：在带显示器的 GPU 上按 TDR 预算（默认 ~2 s，可被 `TdrDelay` 改但需管理员+重启）切块。**"批量越大越快"在 GPU 上的上限是看门狗，不是显存**。诊断配方：死亡且**无异常、无 dump** ⇒ 先查 `Get-WinEvent System -ProviderName nvlddmkm`（找 id 13/153）再查代码。
2. **显示驱动的重置会无声杀死宿主进程** —— 因此"stderr 为空 + 非确定死亡"这一类症状在 GPU 代码里的第一嫌疑应当是 **TDR**，而不是 `std::exit`。

#### 18.5.1 更正与补充：`04:25:41` 那次不是 TDR，是**force-kill 的拆卸副作用**

我在核对日志时看到 03:15:59 之后还有一次 `nvlddmkm` id 153（`04:25:41`），当时判断"很可能就是当前这次真实形状运行在下降相位被重置"。**该判断错了**：

* **带活跃 CUDA 上下文的进程被强杀会让驱动重置设备** ⇒ 该 153 是**拆卸产物**，不是下降触发了 TDR。
* **关键证据**：`03:15:59` 与 `04:25:41` 之间**一条 `nvlddmkm` 事件都没有** ⇒ 整轮 fold 循环（66/66、1581 s）**与下降的头 33 分钟都零驱动事件** ✓

**由此补进诊断配方（与 18.5 的规则配套）**：看到 `nvlddmkm` 153 时，**先与"你自己（或你的包装脚本）在该时刻做了什么"对齐**：

| 情形 | 判据 |
|---|---|
| **真 TDR** | 事件时刻与你**没有**干预的运行死亡时刻吻合；死亡无异常、无 dump；前后有对应的 id 13 |
| **拆卸产物** | 事件时刻正好是你 `taskkill`/强杀/超时杀的那个时刻（日志通常在 `taskkill` 前最后一行停在某相位） |

**另一条自查**：该子代理还纠正了它自己早先的一个协议错误 —— 它曾用 3600 s 上限把运行杀掉，于是日志里出现了 367 s / 992 s 的"死亡"，**那些是它自己的 harness 超时，不是崩溃**，不应当作证据。现在它改为**让运行跑完**（100 分钟预算）以取得真实的下降测量。凡是"超时被杀"与"自己崩溃"混在一起，测量就不可信 —— 这与 §20 里"硬超时 + 确认残留"的纪律是同一个主题。

#### 顺带找到并搞懂的两个真 bug（都记下来，不只是打补丁）

1. 打包的操作数必须写在**槽步长** `slot_words*bpw` 上，**不是** `bpw` —— 按 `bpw` 写会溢出 `2^slot_bits` 窗口，归约会以 `slot windows have nonzero digits above slot_bits` 中止。
2. 打包内核**不能把一个 slice 整个暂存在单个 block 的共享内存里**（真实形状下那是 `P*slot_words` 个 digit ≈ 2 MB）—— 正确设计是**每系数一线程**直接 `atomicOr` 进全局 digit 缓冲，没有尺寸上限。

另外它纠正了自己第一版的一个数学错误：**商不是把 `rb` 当作自己的逆**（那只在 `k == db+1` 时成立），正确需要完整 Newton 链（`rbi = 1/rb mod X^k` 倍增，再 `qrev = ra*rbi`）。

## 25. **重大更正：所谓"分批引擎在 S=5261 上算术不成立"是假象——两次运行用的根本不是同一个 N**（2026-10-01）

§23.1、§24 与上一个子代理的整条证据链都建立在一个前提上：**GPU 在 rung 2 给出的因子不整除 N、命中数与 CPU oracle 不一致**。本轮我把这个前提本身查了一遍，**它是错的**：那两次运行（GPU 与 CPU）**用的模数不同**。

### 25.1 证据：`--n-hex` 少了开头的一个 `1`

* `5261 = 4·1315 + 1` ⇒ **2^5261−1 的十六进制是 `1` 后接 1315 个 `f`（共 1316 位）**。
* 而 `build_cuda_cmake/_t1_args.txt` 与 `_rung2_args.txt` 里的 `--n-hex` 是 **1316 个 `f`、没有开头那个 `1`** ⇒ 那个数是 **2^5264−1**（Python 实测 `int(hex,16).bit_length() = 5264`，且日志首行本来就印着 **`N_bits=5264`**）。
* CPU oracle 用的是 `--n <十进制>`（`_cpu_args.txt`），日志首行 `N_bits=5261`。
* ⇒ **CPU 在 2^5261−1 上跑，GPU 在 2^5264−1 上跑。**

### 25.3 连带作废/更正的结论

1. **§23.1 对 §22.2 的更正要撤回。** 在**同一个** N=2^5261−1 下，GPU（`_ladder_r2b.log`）给的是 `hits=1 factors=42089 hit_primes=3511`，与 CPU oracle **逐字一致**（含命中素数 3511）⇒ §22.2 原本写的"同一因子集合**且同一命中素数**"成立。（那次是旧构建；本轮正在用当前构建在**正确的 N** 上重跑，见 §26。）
2. **§24.2"263 个假命中 ⇒ 命名是长杆"不成立。** 那 263 个命中是 **2^5264−1 上的真命中**。2^5264−1 的小因子极多（5264 = 2⁴·7·47 ⇒ 2^d−1 对每个 d | 5264 都整除它），命中数本来就该很大。**命中数由 N 的因子结构决定，跨模数比较命中数是没有意义的。**
3. **§24 的 TASK 1（`SP.baby_j` 索引/索引-值混淆）并未被证明存在。** 它的全部证据（hits 不一致、因子"不整除"、`leaf_hits=64/64/64/48` 视为"退化"）都来自模数不一致；在 2^5264−1 上"每个 baby 点都能覆盖到某个小因子"是**正常现象**。最后一个子代理据此改写了 naming 的归因、做了 292→185 s 的"提速"，最后**自己回退并留绿树** —— 处置正确，但问题本身是虚的。

### 25.4 教训：**对拍之前先对拍输入**

这与 §14.10（判据不能由意图推出）同源，但更靠前一步：**"数字不同"与"数字的含义不同"是同一类错误的两面**。要断言"两个实现不一致"，第一步不是看输出，而是**证明两边读到的 N、sigma、B1、B2、D 逐项相同**。本轮的 `N_bits=` 首行**一分钟就能发现**，我却先花掉了一整轮（§24）加一个子代理去修一个不存在的行为差异。

**新增纪律（立即生效）**：

* 任何 `--n-hex` 都要**回读校验**（`int(hex,16).bit_length()` == 目标位数，并断言目标小因子整除它）；参数文件与 N 一起留档。

## 26. rung 2 正名（正确的 N）+ 命名循环的真相：**一行 100× 的启动 bug 与一处静默丢因子**（2026-10-01）

### 26.1 验收：分批引擎在**正确的 N = 2^5261−1** 上与 CPU oracle 逐项一致

```
GPU（当前构建，`--real --n-hex 1`+1315×`f` `--b2 1e7 --d 2310 --device 1`，317.28 s）
  stage2: algorithm=tree_gpu_batched curves=1 hits=1 bad_factors=0 factors=42089 hit_primes=3511
CPU（`_rung2_cpu.log`，277.90 s）
  stage2: algorithm=tree curves=1 hits=1 bad_factors=0 factors=42089 hit_primes=3511
```

**逐项一致（含 `hits` 与 `hit_primes`）** ⇒ **§23.1 对 §22.2 的更正、§24 的 TASK 1、以及那个子代理为它做的改动，全部作废**：分批引擎在 S=5261 上从来没错过，是我喂了两个不同的 N（§25）。**TASK 1 关闭，不需要任何代码改动。**

### 26.2 但这一跑暴露了一个真问题：**318 s 里的 314 s 是命名循环**

```
real_batched_split: giant=1.111 gtrees=0.910 fold=0.487 descent=0.554 inv=0.153
                    accum=314.371 name=314.313 f_tree_incl=0.631
```
⇒ **算法本体（F 树 + G 树 + fold + descent + 逆）≈ 4.2 s，命名 314.3 s（98.7%）**。§22.3 说"命名是长杆"，在**正确的 N** 上依然成立 —— 但原因与 §24.2 猜的完全不同（不是"假命中"）。

### 26.3 三个实测事实（新增 `batched_naming:` 一行把命名拆开）

```
batched_naming: hit_blocks=4 hit_leaves=240 named_searches=240 candidates_tested=664388
                unnamed=239 t_scan=4.941 t_ladder=309.231 t_name=314.313 name_max=0
```

1. **`hit_leaves=240` = 全部叶子命中。这不是 bug。** 分批引擎的叶子是 **baby 点**（H 在 x_j 上求值），而**同一个 stage-2 素数可以被多个 baby 点覆盖**，所以命中叶子数远大于 CPU 的 `hits`（CPU 的叶子是 giant 点）⇒ **`hits` 与 `hit_leaves` 是两种约定，不能逐数比较**；能比较的是**因子集合**与 `hit_primes`。§23.1 只是指出过这一点，这里补上可验证的推理与实测：rung 2 唯一因子 `q=42089` 的**剩余阶** `m=3511`（stage 1 之后 Q 的阶），命中条件 `D·i ∓ j ≡ 0 (mod 3511)`（D=2310）对**每个** baby 值 j 都有解（i 上限 4331 > 3511）⇒ 240 个叶子全命中；而 240 组里只有 `(i=1, j=1201)` 给出**素数**候选（p = 3511 = 2310+1201），所以只有 1 次归因成功 ⇒ `hits=1` ✓ 与 CPU 一致。
2. **`unnamed=239` 是一个真 bug（本轮修掉）。** 命中叶子的因子**只在候选素数被 ladder 确认时**才被 `s3_record` 记录；**不能归因的 239 个叶子一个因子都没记** ⇒ **报告出来的因子集合依赖于诊断性的命名扫描**，某个命中叶子扫不出素数时它的因子就被**静默丢掉**。修法照 CPU 参考自己的 `name_culprit`：**不能归因也照样记录叶子的 gcd**（prime=0）；这类记录进 `unnamed` 而**不进 `hits`**（新增 `s3_record(..., count_hit=false)`），以保持 `hits`/`hit_primes` 与 CPU 参考逐项可比。rung 2 修后输出**逐字不变**（`hits=1 factors=42089 hit_primes=3511`）—— 因为那 239 个叶子的 gcd 都是同一个 42089，去重后因子串不变。
3. **成本在 ladder，不在素性测试。** `t_scan=4.94 s`：664388 次素性测试 ⇒ **7.4 µs/次**（把 `mpz_probab_prime_p(z,25)` 换成"≤101 的 26 个素数试除 + 7 基确定性 MR、mulmod 走 32 位半宽"之后，比原来的 ~150 µs 快 **20×**）；`t_ladder=309.2 s`：664388 个候选点 ⇒ **465 µs/点**。

### 26.4 根因：**ladder 的启动网格总是按 cap 铺满**（一行）

`s2g_launch_ladder` 用的是

```cpp
const unsigned int bl = (unsigned int)((g_ladder_cap + th - 1) / th);   /* 128 块 = 8192 线程 */
```

**无论这一批有多少个点**；而 `s2g_mont_mul` / `s2g_ladder` 里的数组是按**运行期** `nw` 索引的（不是模板参数 `NW`）⇒ 它们**全在 local memory**，于是一次启动就要为 8192 个线程提交约 **40 MB** local memory，哪怕只需要 1 个线程。两个实测数字正好对上这个模型：

| 观测 | 点数 | 启动次数 | 耗时 | 每次启动 |
|---|---|---|---|---|
| setup 链（25 个素数幂，**单点**） | 1/次 | 25 | **12.702 s** | **0.51 s** |
| 命名 loop（240 批） | ~2768/批 | 240 | **309.2 s** | 1.29 s（其中固定部分 ≈0.5 s）|

**修法（一行）**：`bl = ceil(min(npts−p0, cap) / 64)`。thread→point 映射与 grid-stride 算术**完全不变** ⇒ 结果逐位相同，而每个点的**边际**成本不变、**固定**成本按点数摊薄。

**(a) 修法 1（持久缓冲）之后**：`ladder_chain_seconds=12.693 → 12.656`（`_rung2_name1_gpu.log`）。**没变。**
**(b) 修法 2（整条链一次启动、单线程、全程留在 Montgomery 域）之后**：`= 12.100`（`_rung2_chain_gpu.log`）。**还是没变。**

两次改动的**正确性**都验证了：Q 与改前**逐位相同**（`real_setup_Q: Q_x_hex=107c6a23ce9ad03b…`，1316 个十六进制位），冻结门禁 **13/13** ✓。而且它们确实把命名从 314.3 s 降到 235.5 s（改法 5）、把每步的 7 次小拷贝和 400 次驱动分配消掉了。

**但 12 s 一分没少 ⇒ 成本在算术本身。** 算一下：25 个素数幂的 ladder 总步数 `Σ bitlen(p^e) ≈ 175` 步，每步 `xDBL+xADD = 6+8 = 14` 次 Montgomery 乘法 ⇒ 约 **2450 次 `s2g_mont_mul`**，而它们现在是**一个线程顺序**做的（链是顺序依赖的，没有跨步并行度）⇒

```
12.1 s / 2450 = 4.9 ms  每次 83-limb Montgomery 乘法
              = 0.36 us 每个 MAC（13778 个 MAC）
              ≈ 650 周期/MAC
```

**650 周期一个乘加**只有一个解释：**这些数组根本不在寄存器里**。`s2g_mont_mul` / `s2g_addmod` / `s2g_xdbl` / `s2g_xadd` / `s2g_ladder` 全部是 `template <int NW>` 但**循环边界用运行期参数 `nw`**、数组又按 `NW`（这里是 128）声明并以指针互相传递 ⇒ 编译器只能把 `t[2*NW+2]`、`x[NW]`… 放进 **local memory**；每线程 ~5–10 KB 的帧让占用率崩掉，于是每次片内 local 访问都走 L2/DRAM，且没有 ILP 去掩盖延迟。**这是整个引擎最大的性能缺陷**，也正好解释了为什么：

| 部件 | 表现 | 说明 |
|---|---|---|
| NTT 多项式乘法 | **0.084 ns/操作数位**（M2 门禁达标）| digit 数组 + 融合 radix-16，寄存器/共享内存友好 |
| 标量 ladder（setup 链、giant 点、命名确认、S5 下降）| **~650 周期/MAC** | 上述 local-memory 问题 |
| 命名候选 ladder 的边际成本 | 每点 ~0.28 ms | 同一个原因 |

**下一个大优化因此是明确的**：把 `nw` 变成**编译期常量**（按**精确**字数的模板实例化 / dispatch），让这些数组回到寄存器。预期收益是数十倍，作用在 setup 链（每曲线 12 s → ~0.2 s）、giant 点（真实形状下是主项）、命名确认与设备下降上。**本轮不做**（改动面在 6 个互相调用的模板函数与 dispatch 上，风险不小，且要重新过全部门禁），记为下一轮第一件事。

### 27.4 要走到目标，按性价比排序的清单（每项都有本轮实测数字支撑）

1. **设备下降（S5）**：descent 79.4 s 是最大单项，而 S5 的实现**只差 §23.2 那个"读窗口由实际收到的值决定"的修法**（已写好 pack/rev_pack/eval/divmod 全套内核，只是默认关闭）。修好并打开它，目标是把 79.4 s 压到个位数。
2. **标量算术去 local memory（§26.7）**：4.9 ms/次 Montgomery 乘法是**所有**标量部件（setup 链 12.1 s、giant 43.9 s、命名确认、下降的逐系数部分）的共同乘数。把 `nw` 变成编译期常量（精确字数实例化）是**一次性投入、多处受益**的改动。
3. **giant 点改用差分加法链**：现在是"每个 i 做一次 ~41 步的独立 ladder"（≈574 次 Montgomery 乘法/点）。Montgomery 差分加法只要有差值点 `x_D`，`x_{(i+1)D} = xADD(x_{iD}, x_D, x_{(i-1)D})` 就只要 ~14 次乘法/点 ⇒ 算术量降 ~40×。代价：链是**顺序依赖**的，必须分块并行（每块用一次 ladder 播种），第 2 项修好后收益才能兑现。
4. **每次 NTT 调用的主机侧开销**（1.22 vs 0.084 ns/位的那 14.5×）：按 §14 的办法重新拆解 `batched_ntt_usecall:`，把打包/抽取/拷贝从热路径里拿掉（S5 已经演示过"操作数留在设备上"的做法）。
5. **更大的 D**：现在是 8 GB 卡上能放下的最大 D=570570；生产参数 D=1411410/P=132480 的 transform 需要约 **36 GB** 显存（`_ladder_r4.log` 的 `d_budget_choice` 行），所以要么把 transform 分块/流式化，要么换更大的卡。**工作总量 ∝ 1/D ⇒ 这一项是唯一能把总量往下压一个档次的**。
