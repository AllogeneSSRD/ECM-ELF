# Carry与F树准备优化草稿

本页记录实施与失败证据，最终现状分别归入[NTT架构](../architecture/NTT.md)和[Stage2准备成本](../performance/STAGE2_PREPARATION.md)。完成后由用户决定处理，不自动删除。

## 当前依据与候选

0.57.14同几何普通／承载G树的纯NTT均约3.012s，S4分别4.998／0.519s；承载的carry／pack等约0.95s。F树pinned预留范围累计约0.73s，oracle分配约0.50s，存在重复增长成本。数据和完整条件保留在`data/experiments/stage2_s4_auto_20261102/`。

按顺序验证：

1. 已有carry/check融合，减少一次全数组读取及单独检查提交；保持规范性、最大digit高度和已有非零计数器。
2. Oracle pinned快照容量以小量子向上取整，减少同一槽位反复free/alloc；限制host额外占用，保留精确大小失败回退，不影响样本数、签名或GMP检查。
3. 大NTT tile／outer及carry／pack的访存组织，以固定D完整曲线验收，不将kernel倍率当作整条曲线倍率。

## 构建与初步检查

证据根`data/experiments/stage2_carry_prepare_20261102/`。`screen01`确认正式生产门禁拒绝`NTT_CARRY_CHECK_FUSED=1`；该失败保留，不放宽门禁作为测试手段。独立development构建发现缺少点环境查询API定义，已在实验适配器补齐，捕获位置在默认值修改环境之前。

development适配器保留旧实验接口：不接受Edwards save和生产结构化metrics、只提供debug等级。不能将其结果冒充当前生产全流程A/B；carry融合须先由生产NTT模块探针验证，完整接入还需要显存规划及缓存条件资格。

## 已完成的实施与筛查

- 修复development适配器缺失的点后端环境API；短NTT四种length／batch组合完成输出验证。它仍不是生产Edwards全流程的替代。
- 新增生产NTT模块探针，链接经清单核验的正式对象，不包含实验实现副本。三版检查器各通过180案例、657000 words；12种carry轮数／digit位宽组合覆盖长全1进位、非32整尾、跨batch、已有非零计数及故障传播。
- 实现oracle单owner双视图和可选64／256KiB容量量子。CPU所有权夹具覆盖视图重排、OOM回退、部分分配失败、求和／取整溢出、单次释放和事件元数据保留。
- `pool_screen01`为最高位承载固定D、每设置n=2的筛查：pool＋256KiB的分配子计时约0.474→0.071s，增长28→12次，锁页峰值5872128→6291456 bytes。不能据此直接宣称完整曲线同幅加速。
- 紧凑carry汇总保持64位全局计数，局部改为32位分层shuffle，共享原子事务被消除。生产模块探针L=2²⁴、batch1的检查器均值约0.797→0.589ms；管理员NCU采集约0.812→0.629ms，全局归约写入仍为2097152 bytes。检查范围未缩减。

## 失败、保护与待验证

`matrix01`为5位宽×普通／承载、每设置一次的完整引擎持出，使用“最大值预读＋紧凑检查＋pool”。合计113.496→114.069s，回退0.50%；最大普通输入的下降明显变慢。保留所有样本，不接受默认替换。

`matrix02`移除最大值预读，同样十格独立合计115.037→114.544s，仅改善0.43%；这不足以证明通用收益。最大值预读实现已从生产源移除，原实验源和二进制仍保存在冻结证据中。

`holdout03`完成检查器单独开关的高／低位宽各三遍：最高位普通中位数32.153→32.858s（+2.19%），承载21.304→20.623s（−3.20%）。没有把十格合计的小收益当作默认资格，当前保持控制路径。

`nsys_descent0/1`重放发现下降最后25个S4请求的纯NTT、S4设备时间几乎相同，检查器累计0.127→0.109s；完整下降的差额主要随F树上传主机计时变化。`upload_seconds`包含等待、CPU打包及提交，不能据此认定PCIe变慢。增加默认关闭的Frontier细分NVTX标记，供进一步定位。

用户明确本轮只测试GPU1，GPU0以后补测。不会结束GPU0任务或改变频率。当前默认性能保护保留，两个候选均通过内部显式环境开关研究，不增加自动tune候选。

## 最终验证

`pool_holdout04`单独测试pool：最高位普通n=3中位数31.224→32.187s，承载21.666→21.403s；没有普遍端到端收益，保持默认关闭。`carry_sweep04`覆盖log₂L12～24、batch1～128，算子改善约20%～34%，不能抹去完整曲线的保护条件。扫描01～03未完成的采集器／参数错误原样保留，不纳入统计。

最终官方构建、CUDA12.6的SM60生产NTT模块编译、CPU所有权／tune／后端／边界夹具及当前模块carry门禁均通过。`release15`的普通诊断两次已通过；承载NF触发采集器错误：将原始请求32误当成实际回退0。修正采集器按未绑定规划结果识别请求，保留实际receipt／kernel严格检查；`release15b`复用同SHA普通证据并补齐承载、故障注入和最终上传剖析。没有修改生产归约逻辑来迁就测试。

最终EXE为`379753820bb47e08c734f1e7a0fdc279a338e4178b61e8237ae620ec93e9f482`；260输入／46对象核验，当前生产模块检查器事件0.810→0.589ms。新增上传标记的最高位普通诊断中，CPU打包范围0.350s、最后等待0.040s、提交0.005s；实际关联H2D事件0.051s，与CPU范围不可相加。优先继续调查冷F树打包／调度及缺页，而非据混合计时认定NTT或PCIe变慢。
