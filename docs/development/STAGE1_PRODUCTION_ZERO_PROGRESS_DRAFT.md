# Stage1 生产版 Edwards 零进度：调查草稿

## 结论与适用范围

生产目录 `ecm-win-x86_64-sm89-cuda13.3_param0` 的 Stage1 0.41.0 在 Edwards 4096-bit/TPI16 路径上重复执行零长度切片。现象可在恢复任务和全新任务上复现，属于生产二进制问题。当前源码完整重编的 0.43.0 可从同一生产存档恢复并推进。调查期间生产文件保持只读，未发布新程序或迁移生产配置。

证据指向生产二进制混用了自适应切片改动前的 CUDA 对象：提交 `16145a9` 将主机调用的 `chunk` 从 256 改为 0，0 表示自适应；同次改动把 CUDA 主机循环的固定 `min(chunk, remaining)` 改为 `EcmEdwardsSlice`。新调用端配上旧循环会得到 `end == done`，与零推进、极短 GPU 调用、大量 launches 的实测一致。当前相关计算源码与 0.41.0 的算法没有后续变化，完整重编后现象消失。生产 Stage1 缺少能追溯到各 CUDA 对象的来源清单，尚不能确认具体哪个构建步骤复用了旧对象。

## 复现与验证

生产 Stage1 二进制 SHA256 为 `01f809153f2df21f34ea175436703ae3f717590817f20e240d54b29f015246b9`；完整重编版为 `4372d8d30b2f516c15b9cc91846e1fd82882d6db16dcf5ad09a0e873748e7825`。测试 GPU 为 RTX 4070 Ti（device 0）。以下是诊断样本，未固定功耗或时钟，不作为性能基准。

- 生产日志约 7 小时保持在 NAF 第 120224000 列，`+0 columns`，停止时记录 4583212 次 launches。GPU 同步和停止处理仍能完成。
- 将生产任务、检查点、指数缓存和程序复制到忽略目录：B1=260000000、960 曲线、实际余因子 3968 bit、容器 4096 bit/TPI16、NAF window=10、doubling=4。生产版在约 3 秒观察期内仍保持 120224000，778 次 launches；重编版推进到 120258403，32 次 launches。两者均通过继承的停止事件结束，输出写入各自隔离目录。
- 同一原始存档副本在生产版空转前后 SHA256 完全一致。重编版保留了推进后的存档；此结果支持继续使用已保存状态，无需删除存档。
- 无存档的小任务（M3989、B1=1000、2 曲线、同一 4096-bit/TPI16 容器）同样复现：生产版在第 0 列空转，约一秒内 5856 次 launches；重编版正常完成 1439 列，4 次 launches。由此排除了该生产存档损坏或恢复解析作为此次停滞的必要条件。
- 更新已有 `tools/test/test_edwards_live_progress.py` 的 TOML 测试配置，并要求打印的完成位置严格递增，切片推进量为 1…4096。4096 是现有自适应调度上限，旧测试中的 256 属于固定切片时期的限制。以 M3989、B1=100000、8 曲线执行 NAF/binary、新任务/停止恢复共四条路径，全部通过；两种算法及恢复后的最终保存点完全一致。

原始日志、复制的二进制与存档、最小复现脚本、报告及回归输出位于忽略目录 `data/experiments/stage1_stall_20261020/`，不改写生产证据。

## 处理方式

生产程序需要用同一套源码、配置和全部 CUDA 对象完整重建后发布。当前可用验证程序为 `build_cuda_cmake/ecm_cuda.exe`。该版本使用 `ecm.toml` 和 `--config`，生产仍为 INI 配置，发布时须协调配置与 GUI；或从生产对应版本完整重建，避免混用配置接口及旧对象。

主机自动切片调用见 `src/core/ecm_edwards_gpu_driver.inl`；NAF 循环见 `src/cuda/stage1/edwards_runtime.inl`；切片策略见 `src/cuda/stage1/edwards_slice.h`。后续发布验收宜覆盖每个实际发布的 Edwards 容器，并核对 CUDA 对象的源文件、头文件和编译命令身份，不能只依据文件时间戳。

本草稿保留，完成后的整理或删除由用户决定。
