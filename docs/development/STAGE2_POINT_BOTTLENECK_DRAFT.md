# Stage2 点生成与同步瓶颈审查草稿

## 范围与反馈回路

先固定小档B2与已有有效Edwards保存点，不扩大矩阵。0.54.7冻结二进制、GPU1、相同D/P／算术／布局／预算，关闭运行时写入，以完整NF、闭合引擎计时、GMP检查和真实chunk路由为回执。性能计时与额外叶检查分开，保留首轮和全部样本。

入口为`tools/bench/bench_stage2_point_routes.py`，从已验收的小B2默认矩阵取得命令和精确输入；每次新建隔离目录，不消费生产队列。允许的界面PID与路径沿用用户授权，其余同卡任务拒绝。原始证据放在`data/experiments/stage2_point_routes_20261031/`。

## 排序假设

1. 7995-bit的短尾11700点退ladder。保持D180180/P17280，将容量改为6P，分成103680＋46260点；预测两块均走chain且完整时间下降。
2. `gleaves`是同步归属，不是纯CPU成本。预测时间线中的ladder／segment kernel延伸至主机叶准备的阻塞拷贝，CPU求逆仍很小。
3. 宽位chain并行度不足。保持D和chunk，只改每条链32／64／128点；预测更短链可能利用更多SM，但seed成本上升，最优点需完整引擎验证。
4. 成本模型不完整。当前原生模型已记录chunk、chain／ladder及精确ladder steps，不能称其完全忽略尾部；继续检查seed固定成本、链并行波次与主机计时归属。

## 诊断结论

默认短尾两次ladder实际3.191517 s，6P设置中消失。CPU逆仍约0.011 s；gleaves大值主要是前序设备工作在读回时等待，不能当作纯CPU成本。

宽位chain64的34个CUDA块、每块一warp，NCU实测每SM约1.43活跃warp、活跃warp占比2.98%、long-scoreboard等待65.50%；local读写请求约global的442倍。实际寄存器准入不是当前34块grid的首要限制。链长32的chain核9.694747→4.763964 s，seed核6.182539→6.138760 s。理论主核模乘反而增加约29.5%，因此只用MAC计数建模不够。

当前仅是实验方向验证，正式链长仍64，完整范围重平衡尚未实现。后续先补非单位／命中因子语义、D／预算／W128与129，再统一分块计划、内存生命周期和tune身份；不得将该19条NF视作全范围默认资格。

## 下一轮实施设计

先保持D/P、链长64、原点块容量与所有生产基线，实施完整索引区间的尾块借P调度；不是启用relocation，也不是固定使用6P预算。复用giant_chunk_take的可行性条件：只改倒数两块，均不超容量、均达到有效chain门槛，总点数／点块数／G树边界保持。独立ladder强制路径、非驻留条件及借块不可行时保留原路线。

- [ ] 用同一个纯整数chunk计划连接执行器、giant_work、GiantMemoryPlan／timeline和原生规划日志，避免执行与显存准入各算一份分块。
- [ ] 新增分块策略身份并进入Shape／样本／缓存，已有原策略记录保留原身份；不能仅凭相同C复用旧耗时。新旧策略的成本准入和默认性能保护分别核对。
- [ ] 固定D比较原策略／新策略，保持原C；先复现7995-bit的可避免短尾，再测无短尾、无法借块、W128／129、预算不足及多满块。
- [ ] 验收规范叶、非单位seed／Gamma、退化传播、gcd=N及命中因子；NF摘要一致不能替代因子语义。

然后才加入有限链长选型：先把chain_block设为独立身份；默认64常驻候选，优先仅比较32／64，16／128留给有针对性的算子筛查。按W、chunk点数、SM数量与算术类型建立小范围参考，不把D表乘上所有链长做穷举。

- [ ] 分离seed-pair、chain、段积的设备计时与主机等待；模型包含seed标量位步数、每条链有效xADD数、CUDA块取整和相对SM数量。
- [ ] 用实测吞吐校准并行波次与工作集影响；理论MAC数只提供工作量，不能直接用来排名。新区域预测不确定时保留64，实测采用正常的重复／性能保护规则。
- [ ] 链长先在固定D上验证，之后与D／布局／承载联合选型；借块后的n_c进入链长模型，避免分别最优、合起来回退。
- [ ] 扩大少量跨位宽固定D对照，再运行小档B2持出矩阵；未经这一层验收不扩大到耗时很长的大B2矩阵。
