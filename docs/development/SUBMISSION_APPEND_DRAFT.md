# 提交结果按发布顺序追加：开发草稿

## 范围与版本

用户要求新结果直接追加到提交文件末尾，已有行保持原顺序，F/NF 按实际发布顺序混排；版本按最后确认的 z+1，从 0.44.5 更新为 0.44.6。仅提交本轮文件，生产目录不在本轮修改范围。

正式使用说明维护在 `docs/usage/ECM_RESULTS.md`。本草稿保留调查、实现和验证记录，完成后由用户决定整理方式。

## 调查与实现

原导出函数把 NF 放入按散列字符串键排序的 map，随后统一输出 F，并原子替换提交文件。生产只读快照复现了新任务插入文件前部，以及先发布 F、后发布 NF 却导出为 NF/F 的问题。

共享入口 `src/core/ecm_submission_writer.h` 改为 `append_submissions`，Stage1、CPU Stage2 与 CUDA Stage2 继续共用发布流程。即时 F 和每个新封存 NF 批次都在输出独占锁内记录发布历史，再以二进制 append 写入。未完成 NF 仍不对外发布，已封存批次数量和最终 CRC 规则不变。

提交账本增加 `publication.order`，沿用已有回执格式及完整性散列保存原始输出字节。首次使用现有文件时保留其原文和原顺序；只有尚未导出的回执按回执文件时间及稳定键补到末尾。已有发布历史时，输出必须是历史的字节前缀；恢复只补齐后缀，文件缺失则按同一顺序恢复。历史损坏或文件被改成非前缀时拒绝写入。

## 验证

原始输出保留在忽略目录 `data/experiments/submission_append_fix_20261021/`。

- `red/`：在旧实现上增加 F/NF 顺序断言后，真实共享发布函数复现失败。
- `green_recovery/`：23 项结果生命周期检查通过，包括两个阶段跨任务追加、逆序时间戳下的发布顺序、F/NF 混排、CRC、重复发布、已有 CRLF 与末行无换行、部分行写入恢复、缺失文件恢复、输出被修改拒绝和历史损坏拒绝。硬链接检查确认写入保留原文件对象。
- `production_replay.json`：使用上一轮冻结的两份生产账本副本，Stage1 新结果追加为 M8387/M4283/M5167，另一份追加为 M5351/M8387；前缀字节保持，重复导出不变。没有改写生产文件或原始快照。
- CPU Stage2 完整构建通过；`cpu_export.json` 验证其真实 `--export-results` 命令入口追加新批次，并补齐被截断的追加行。CUDA Stage2 主入口使用正式构建参数在本轮目录单独编译通过；没有改写冻结构建。
- 默认 CUDA 缓存的依赖与当前源码不匹配，Stage2 `HostOnly` 正确拒绝复用，Stage1 增量入口触发全量内核编译。本轮结束了这项额外的全量编译，不将部分编译产物作为新发布包；改用正式 CMake 参数单独编译 Stage1 主入口并通过，输出在 `stage1_main_compile.log`。算术与 CUDA 调度不在修改范围。
