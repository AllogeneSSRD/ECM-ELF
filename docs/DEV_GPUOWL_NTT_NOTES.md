# GPUOWL 整数 NTT/FFT 实现说明

本文是 GPUOWL（位于 `.refactor/gpuowl`）GPU 算术路径的开发参考，重点说明
GF31/GF61 整数 NTT、共享 FFT 内核、进位重构，以及 CUDA 移植时必须保持的语义。
它不是用户使用手册；构建和运行方法见项目根目录的 `README.md`。

## 1. 实现边界

项目没有独立的 `ntt*.cl`。NTT 与浮点 FFT 共用一套 OpenCL 内核，通过主机端
宏定义选择路径：

- `src/Gpu.cpp` 的 `kernelDefines()` 设置 `FFT_TYPE`、`WordSize`、`WIDTH`、
  `SMALL_HEIGHT`、`MIDDLE`、`CARRY_LEN`、`NW`、`NH` 等参数；
- `NTT_GF31`、`NTT_GF61`、`FFT_FP32`、`FFT_FP64` 决定每个内核的算术分支；
- `src/cl/fft4.cl`、`src/cl/fft8.cl` 中的 radix butterfly 由不同类型重载共用；
- `src/FFTConfig.cpp` 将 FFT 类型映射为数据类型和字宽。

CUDA 后端也不是另一套 NTT 算法。它通过 `src/cuda/opencl_compat.cuh` 提供的
兼容层，以及 `src/cuda/clwrap_cuda.cpp` 中的 NVRTC 编译流程，复用 `.cl` 内核。
只有在脱离现有兼容层、实现纯 CUDA 内核时，才需要重新实现本文列出的算术和布局。

## 2. 域、类型与数据组合

核心模数和类型定义在 `src/cl/base.cl`、`src/cl/math.cl`：

```c
M61 = 2^61 - 1;   Z61 = ulong;   GF61 = ulong2;
M31 = 2^31 - 1;   Z31 = uint;    GF31 = uint2;
```

`Z31`/`Z61` 是素域元素；`GF31`/`GF61` 表示二次扩域中的一对元素，代码按
`a + i b` 处理，满足 `i² = -1`。长度为 2 的幂的根在扩域中生成：

- GF61 使用 `src/TrigBufCache.cpp` 中阶为 `2^62` 的根；
- GF31 使用阶为 `2^32` 的根。

主机端支持的组合包括 `FFT61`、`FFT3161`、`FFT3261`、`FFT323161`，以及
FP32/FP64 与 GF31 的混合类型。GF31 与 GF61 并非各自输出一个独立结果：
进位阶段通过 CRT 合并，基本形式为 `n61 * M31 + n31`；`FFT323161` 还利用
FP32 数据确定 `M31·M61` 的倍数。GF61 数据位于 GF31 数据之后，偏移由
`DISTGF61` 等主机参数传入内核。

## 3. 域运算约定

### 3.1 GF61

M61 约减利用：

```text
2^64 ≡ 8 (mod M61)
```

128 位乘积先折叠低 61 位和高位；乘积可能达到完整 128 位时，再折叠高端的
6 位。`weakModM61()` 和 `modM61()` 都是惰性约减，结果不保证落在严格的
`[0, M61)` 内。因此移植时必须同时保留：

1. `weakMul` 操作数为非负值的约定；
2. 调用者传入的折叠次数/上界；
3. butterfly 中每个 `modM61q(..., k)` 的人工推导上界。

加减法通过补加若干个 M61 保持中间值为正，最终再惰性约减。扩域乘法使用
Karatsuba 形式的 3 次宽乘法；扩域平方使用 2 次宽乘法。相关实现集中在
`src/cl/math.cl` 的 GF61 分支。

因为 `2^61 ≡ 1 (mod M61)`，乘以 `2^k` 实现为 61 位循环移位，而不是普通
整数乘法。`shl30`、`shl31` 是常用的专用路径。

### 3.2 GF31

GF31 使用相同的扩域结构；`modM31()` 将 64 位乘积按 31 位切分折叠。
当前代码包含多种实现，由 `MODM31` 选择。不要把 GF31 的严格范围假设套用
到 GF61：两者的惰性约减细节和可接受中间范围不同。

## 4. 变换结构与内存布局

主机端形状为 `WIDTH : MIDDLE : HEIGHT`，并定义：

```text
NWORDS = WIDTH * MIDDLE * HEIGHT * 2
ND     = NWORDS / 2
BIG_H  = SMALL_HEIGHT * MIDDLE
```

一个复数元素承载两个连续的大整数 word；因此长度为 `ND` 的复数 NTT 对应
`NWORDS` 个整数 word。`NW` 和 `NH` 通常为 4 或 8，分别控制 width/height
方向的 radix 和每个线程暂存的元素数。`MIDDLE` 为 2、4、8 或 16。

这不是单一的一维 Stockham 循环，而是带转置的分解变换：

1. `fftP`：读取整数 word，应用 IBDWT 权重并执行 width 方向变换；
2. `fftMidIn`：middle 方向 butterfly、乘 twiddle、转置；
3. `tailSquare` 或 `tailMul`：height 方向变换及中间乘法；
4. `fftMidOut`：逆向 middle 变换并转置回去；
5. `fftW` 与 carry，或融合后的 `carryFused`。

平方和乘法的主机调用链分别在 `Gpu::square()` 与乘法流程中记录。`INPLACE`
决定是否使用原地的 swizzled 布局；关闭原地模式时会使用额外 scratch buffer。
`src/cl/middle.cl` 中的 `SWIZ`、`SIZEBLK`、`SIZEW`、`SIZEM` 必须与主机端
分配和 kernel 参数保持一致。

每个线程在 width、height、middle 阶段分别持有 `NW`、`NH`、`MIDDLE` 个元素。
OpenCL 向量类型是 `ulong2`、`uint2`、`double2`、`float2`；不要在移植时擅自
改为 `float4`，因为这会改变布局和对齐。

## 5. Twiddle 表与 butterfly

twiddle 表由 `src/TrigBufCache.cpp` 生成并按 width、middle、height 区域拼接，
再由 `DISTWTRIGGF61`、`DISTMTRIGGF61`、`DISTHTRIGGF61` 绑定到 kernel。
普通 radix butterfly 的索引为：

```text
p = me & ~(f - 1)
trig[(i - 1) * WG + p]       (i = 1 .. RADIX-1)
```

因此第 `i` 个元素使用的 twiddle 指数为 `i * p`。`TABMUL_CHAIN61` 开启时，
只读取一个基准 twiddle，再通过连续乘法得到其幂；关闭时直接读取整行表项。
radix-8/radix-4 的压缩表由 `tabMul8_4a/b` 处理，不能与普通表布局混用。

## 6. IBDWT 权重与平方

权重变换用于处理 Mersenne 指数对应的非整数 bits-per-word。第 `j` 个 word
的权重为：

```text
2^(ceil(EXP*j/NWORDS) - EXP*j/NWORDS)
```

在 GF61 路径中，权重通过模 61 的循环移位实现。大小端 word 标志、分数位和
移位量由同一组 `fracBits`/`comboFracBits` 状态推进；逆变换还要应用
`log2(NWORDS) + 1` 修正，因为 NTT 输出带有 `2*NWORDS` 的比例因子。

中间阶段的平方不是逐点复数平方。`src/cl/tailsquare.cl` 的 `pairSq()` 和
`onePairSq()` 会先处理共轭配对，再按 `t_squared_type` 组合 `×1`、`×i`、
`×-1`、`×-i` 的结果。第 0 行和第 `H/2` 行是自配对行，需额外处理
`TAILTGF61`；完成中间运算后还会执行 `SWAP_XY`。这些特殊情况缺失时，结果
通常不是崩溃，而是静默错误。

## 7. bits-per-word 与精确性

`src/fftbpw.h` 提供按形状和类型索引的经验表。这里的 bpw 是每个大整数
word 的 bit 数，不是每个复数元素的 bit 数。主机端用：

```text
bitsPerWord = EXP / NWORDS
```

表中 6 个值对应不同的 middle/height 变体；形状不在表中时，
`FFTConfig::maxBpw()` 会尝试映射到已知形状并扣减余量，仍找不到时使用默认值
并记录错误。bpw 表是按长期 ROE/溢出经验标定的安全裕量，不是数学上的硬上界。

它影响三件事：是否超过形状可支持的最大指数、是否启用 long-carry，以及
kernel 中 `MAXBPW` 和 carry 快捷路径的选择。`CARRY32` 对 word 位宽有严格
限制；NTT 路径不能在超过其允许范围后强行使用 32 位 carry。

## 8. 进位与 CRT 重构

每个 word 的有效位数为：

```text
nBits = EXP / NWORDS + (isBigWord ? 1 : 0)
```

carry 从一个 word 传播到下一个 word，大小端标志必须按同一序列推进。通常路径
使用 `carryFused`：逆权重、整数重构和 carry 在一个 kernel 链中完成，并通过
`carryShuttle` 在 workgroup 之间传递进位。long-carry 路径则拆成 `carry`、
`carryB` 和后续 `fftP` 等 kernel。

移植时必须保持以下语义：

- GF31/GF61 的 CRT 合并顺序为 `n61 * M31 + n31`；
- LL 路径的初始 carry 为 `-2`；
- `WordSize` 与 `Word` 的 4/8 字节选择必须一致；
- 一个复数元素对应两个连续 word；
- carry 中使用的 64 位路径不能被 32 位临时变量截断。

## 9. CUDA 移植清单

优先按以下顺序验证，性能优化放在功能正确之后：

1. 先复现 Z31/Z61 的惰性约减、宽乘法和扩域乘/平方；
2. 复现根、twiddle 表拼接顺序和 butterfly 索引；
3. 复现 IBDWT 权重、大小端序列以及逆变换比例修正；
4. 复现 `pairSq` 的配对规则、特殊行和 `SWAP_XY`；
5. 复现数据 swizzle、padding、`WordSize` 与 buffer 偏移；
6. 最后接入 carry、CRT 和跨 workgroup 的 carry hand-off。

以下宏主要影响性能，不应成为第一阶段的移植阻塞项：`INPLACE`、
`SHUFL_BYTES_*`、`LDSPAD_*`、`LDSMUL_*`、`WMUL`、`MULTI_Q`、`L2_STRIPING`、
`ZEROHACK_*`、`UNROLL_*`、寄存器上限，以及 `TABMUL_CHAIN*` 等表读取策略。
但它们改变工作组大小、共享内存或寄存器压力时，仍必须重新检查设备限制。

## 14. 为什么"`B2 ≤ 1e9` 几乎不变、`1e10` 以后才开始变长"

两个**不同**机制叠在一起：

1. **真正 ∝ `B2` 的只有 `loop_wall`**（巨点梯子 + G 树 + fold）：`0.52 → 1.17 → 5.60 → 16.46 → 346.75 s`。
   它在 1e11 时只占 `elapsed` 的 26 %，到 1.94e12（`B2` 再 ×19.4）才变成 87 % ✓ ⇒ 拐点落在
   1e10–1e11 之间，与你观察到的现象一致 ✓。
2. **`post` 也在涨，而且不按 `B2` 线性**：`16.0 → 24.8 → 31.3 → 39.5 → 44.2 s`。这一段是**宿主 GMP**
   的 descent + 累加 gcd + 命名，descent 占大头（`12.5 → 20.8 → 26.8 → 34.0 → 31.1 s`）。
   **机制**（容易误判）：余式树的叶子数只由 `P` 决定，但**顶层被除数的长度由批内巨点数决定** ——
   批循环里 `H = T`（该批 G 树根），`deg H` 随巨点数线性增长，直到被 `mod F` 压回 `P` 以内才饱和。
   于是巨点数从 177 涨到 175265 时每次除法都变长 ⇒ `post` 跟着涨；到生产形状（3.4e6 巨点）
   `deg H` 早已饱和于 `P=51840`，`descent` 稳定在 31 s ✓。

**结论**：小 `B2` 是"**固定成本主导**"（`pre` 4–6 s + `post` 16–25 s，其中宿主 GMP 占绝大部分），
大 `B2` 才是"**批循环主导**"。别忘了 §11 那段 **≈25 s 的进程 wall 固定成本**——小 `B2` 时它比
`elapsed` 本身还大 ✓。

## 15. 内存与 `N`、`B2` 的关系

| 量 | 由谁决定 | 实测（生产形状）| 说明 |
|---|---|---|---|
| 每系数字节数 | **`N`** | `W = ceil(5261/64) = 83` 字 = **664 B** | 一切多项式内存 = 次数 × 664 B；`H`（51840 系数）≈ 34 MB |
| NTT 模数/digit 宽度 | **`N`** | `bpw=21`（绑定形状 `P=8193`，`slot_bits=10536`）| 由 `L(2^bpw−1)²<p` 定，`L=P·slot_words` |
| 变换长度 | `N` + 形状 | `max_ntt_words=65536` | 必须容下 `2L` |
| arena（设备）| 形状×批大小，受空闲显存封顶 | `arena_mb=4684.5`，`cap=6338`，`overflow=0` | `mem_budget` 自报："最大变换（fold，51841 系数）**2305 MB**；树顶（25921 系数）**1152 MB**"；放不下的形状回退到每次 `cudaMalloc`（更慢，`arena_overflow` 计数）|
| 宿主私有内存 | **`P`**（不是 `B2`）| `host private=7059 MB peak=7802 MB` | 扫描里 `B2` 涨 10⁴ 倍，host private 只在 6488–6720 MB 之间浮动 ⇒ **宿主内存是 `N` 与 `P` 的函数** ✓ |
| 设备剩余 | 被 arena 挤压 | 起跑时 `device free=1780 MB of 8188 MB` | 这正是 S5 设备下降当初 4 GB 固定池 OOM 的原因（§57）|

一句话：**`N` 定"宽度"（位数/字数、bpw、变换长度），`D` 定"叶子数"（`P=φ(D)/2`，决定 F 树、descent、
叶子内存），`B2` 定"数量"（巨点数 ⇒ G 树/fold/巨点梯子的规模）。**

## 16. GPU 占用率为什么低（GPU-Z 实测）

取你给的实时日志中 `B2=1e11` 那一次的窗口（12:29:10–12:30:36，进程 wall 86 s，采样 103 点，
两端各含几秒空闲）：

| 指标 | 实测 |
|---|---|
| GPU Load 平均 | **50.8 %**（max 100 %，min 0 %）|
| GPU Load < 5 % 的采样 | **29 / 103 ≈ 28 % 的时间几乎全闲** |
| Board Power 平均 / 最大 | 18.5 W / 57.3 W（同机空闲约 1.7 W）|
| GPU Clock 平均 | 1509 MHz（max 1800）|
| 显存占用峰值 | 6348 MB |

同一跑的阶段账：`elapsed=61.27 s` = `pre 6.33` + **`loop_wall 17.93`（仅 29 %，这才是 GPU 真正在

梯子/自检 ⇒ **86 s 里有约 70 s 是 GPU 按设计就该闲着的** ✓。

生产形状（1.94e12）好一些但同理：`loop_wall=346.75 s`（87 %）里 `giant+gtrees+fold=316.4 s` 是设备

阻塞式 `carrysplit d2h=58.45 s` —— 这些都是"GPU 等宿主"。

**结论**：本引擎**不是 GPU 吞吐受限，而是宿主/串行受限**。提高占用率不是"把内核写更快"，而是
**把宿主侧串行段搬走或并行掉**。

## 17. 优化候选（按可预期收益排序，均有实测依据）

1. **`post` 的宿主 GMP**（生产 53.8 s = 13.5 %；`B2 ≤ 1e10` 时占 60–80 %）：descent 31.1 + accum 13.1
   + name 9.6 s。S5（设备下降）方向正确，但现在**每次除法 5.0 ms vs 宿主 48 µs（§58.3）⇒ 90× 慢**，
   根因是"一个节点一次"的调度（191896 次极小 NTT launch、8125 个 level）。**先按形状把同一层的
   除法跨节点批量**（宿主 `descent_batched` 正是按 `(deg cur, deg divisor)` 分组），把每次除法压回
   48 µs 量级，再谈替换宿主下降。
2. **`gtrees`**（生产 192.9 s，最大单项）：每批一棵 G 树，形状彼此相同且都是 NTT 乘法 ⇒ 值得评估
   "跨批合并同形状乘法"（一次大批量取代多次小批量），代价是 arena 与批大小的权衡。
3. **`fold`**（72.8 s）：每批 3 次满尺寸乘法；`H` 的更新能否每 k 批合并一次以减少满尺寸乘法。
4. **NTT 内的 `t_reduce`**（GPU 事件时间约 78 s）：§35 论证的唯一数学上站得住的开口（尾部真除法）≈25 %。
5. **D2H 回读**：`carrysplit d2h=58.45 s` 是每 chunk 一次阻塞回读，可分批/异步化。
6. **小 `B2`/多曲线**：≈25 s 的初始梯子与自检是固定成本，一条命令跑多曲线可摊销，顺带拉高占用率。

### 18.4 能直接抄的三件事（按收益排序）

1. **选 `D`（我们完全没有这一步）**：他们用**更大**的 `D`（P=230400）换来**更少更胖的步**（1.7e6 步），

   所以"更少更大的步"对 GPU 更有利；他们自己的覆盖率也印证大 D 更划算（`numvals` 1413778/1524700 =
   **93 %** 对 471692/2012607 = **23 %**）✓。**下一轮应把 `D` 当搜索维度**（用我们已有的 `batched_cost`
   模型 + 实测），而不是固定 `--d`。
2. **下降不要用宿主 GMP**：他们的余式树 69.9 µs/叶子，我们 600.6 µs/叶子（8.6×）✗。这正是 S5 的目标，
   但 S5 现在每次除法 5.0 ms（§58.3）—— **先把同层除法按形状跨节点批量**，目标是把每叶子成本压到
   70 µs 量级（对应每除法 ≈48 µs，与宿主同量级）。
3. **B2 最优化器 + 成本预估**：他们有"最优 B2/B1 比"、"曲线值多少条参考曲线"、init/main transforms
   预估（预测 115.20 M vs 实测 115.31 M，误差 0.1 % ✓）、stage2/stage1 比值预估。我们只有用户给的
   `--b2`（当作 `imax = B2/D + 2` 的上限）与事后统计 ✗。把 `batched_cost` 变成**事前预测 + 搜索**
   是低风险高价值的一步。

### 18.5 不能直接比的地方（避免误读）

* **变换计数单位不同**：他们的 `transforms` 是**单次 FFT**；我们的 `ntt_calls` 是**批量调用**（一次
  覆盖很多 slice）⇒ 不能拿 `transforms/s` 互比，本节所有比值都用时间/步、时间/叶子这种可比口径 ✓。
* **算术不同**：他们是**浮点 FFT + round-off 检查**（`Round off: 0`、`avg poly_size` 是 FFT 字数），
  我们是**精确整数 NTT**（`bpw=21` 由 `L(2^bpw−1)² < p` 证明，无 round-off 概念）⇒ 我们把"精确性"
  当硬约束，代价落在 `bpw`/长度上；不能因此说我们"更保守所以更慢"，因为慢 10× 的量级差不是这一点能解释的。
* **`B1` 差 6 个数量级**（他们 `B1=2.6e8`、我们 `B1=1000`）⇒ ECM 阶段语义不可比；可比的只有 stage-2
  机器本身（同一棵 F 树/余式树/折叠结构）。
* 他们的 `B2` 是**优化后的目标**，我们的 `--b2` 是**上限**。
* 他们是 **2 个核**（主线程 + polymult helper），我们是 1 个宿主线程 + GPU。
* 日志里 `Stage 2 GCD complete. Time: 0.000 sec.` 与 `Time: 0.252 sec.` 这类量可能只是计时粒度/未计的
  结果，不要当成"他们的 gcd 是免费的"。

## 19. 第 1 项落地：把 `D` 从"装得下的最大值"换成**成本模型 + 实测校验**

### 19.1 旧规则为什么错

`--choose-d` 原来的规则是"取**装得下的最大 D**"，理由写着 *"work is proportional to 1/D, so this is the
fastest admissible shape"*。这只说对了一半：

* **主循环** ∝ `1/D`：巨步数 `imax = B2/D`，而本引擎把**批大小恰好绑成 `P`**
  （`num_poly_g = ceil(imax/P)`，第 6478 行），所以循环里每一次乘法都是"度数 P × 度数 P"，循环成本
  ∝ `imax·log2(min(P,imax))` ✓；
* **F 树 + 牛顿逆 + 余式下降 + 块累加** ∝ `P = φ(D)/2`，**随 D 增长** ✗。

所以存在**内部最优**，而"最大 D"必然不是它。

### 19.2 模型（用实测拟合，不是猜）

参考跑 = §56.1 的生产跑（`D=570570, P=51840, imax=3400110`），折成**速率**：

| 项 | 实测 | 速率 |
|---|---|---|
| 主循环（gtrees 192.920 + fold 72.836）| 265.756 s | `4.99e-6 s / (imax·log2)` |
| 树侧（pre 6.335 + descent 31.134 + accum 13.068）| 50.537 s | `974.9 µs / 叶子` |
| 巨点梯子 | 50.655 s | `14.90 µs / 巨步` |
| 宿主胶水（gleaves 20.722 + loop_host 9.617）| 30.339 s | `459.7 ms / 批` |
| 固定（`elapsed` 之外的 setup/自检）| ≈25 s | 常数 |

代回参考跑：`265.7 + 50.5 + 50.7 + 30.3 + 25.0 = 422.3 s`，实测 `397.83 + 25 = 422.8 s` ⇒ **0.1% 吻合** ✓。
它的用途是**排序**，不是精确预言（验证里绝对值偏差 8–11%）。

### 19.3 一次被实测当场否掉的错误判据（记下来）

第一版模型给每个候选加了"覆盖率 = φ(D)/D"的权重，于是把**素数幂 `D = 19⁴ = 130321`**（φ/D = 0.947）
排到远超基线（φ/D = 0.182），预测效率高 5.2×。实测：**127.00 s vs 62.93 s，慢一倍** ✗✗。

**错在哪**：一个**大于 D 且不整除 D 的素数 p，必然与 D 互素**，所以 `p mod D` **自动是单位元**；而 baby
集 `{±j : j ≤ P, gcd(j,D)=1}` **恰好就是全部单位元** ⇒ **任何 D 下，(B1,B2] 中大于 D 的素数全部被覆盖**
✓，与 φ(D)/D 无关。真正可能漏掉的只有 `(P, D]` 之间的素数，数量 `π(D)−π(P) ≈ 10⁴` 对
`π(1e11) ≈ 4×10⁹` ⇒ 比例约 **1e-5** ✓ 可以忽略。

**所以 D 的选择是纯成本问题**：最小化 `loop + tree + giant + glue` ✓。表里仍打印 `units=φ(D)/D` 与
`missed_primes`，但只作信息、不参与排序。

## 20. 第 ① 项落地：arena 驱逐缓存 ⇒ 解锁更大的 D ⇒ 生产曲线 **−31.2%**

### 20.1 为什么 arena 是共同瓶颈

§19.5 的结论是"生产 B2 上 D 只剩 ~3%，因为它被显存卡住"。量清 arena 的构成后原因很清楚
（`ntt_poly_probe.cu` 的 `NttArena`）：

| 条目 | 内容 | 大小 | 可驱逐？ |
|---|---|---|---|
| `BigEntry`（按 `(N, nbatch)` 缓存）| `dA`/`dB`/`dQ` | **3·N·nbatch 字** | 是（纯缓存）|
| `SmallEntry` | `dOut`（可增长）+ `dRes` | `out_slots·nbatch + 2·nbatch` 字 | 是 |
| `FuseEntry` 的**逐 pass 表缓存** | `passF/radF/passI/radI` | 约 **N + N/2 字** | 是（可在下次 multiply 重建）|

**三者都是缓存，而旧代码从不驱逐**：`bigs`/`smalls`/表缓存一路只增不减 ✗。于是在 `P=115200`
时出现实测的情形——

```
stage2_tree_gpu: arena refuses N=134217728 nbatch=1 (needs 3072 MB, has 5627 of 6338 MB):
                 falling back to per-call cudaMalloc
CUDA error out of memory (2) ... call: cudaMalloc(&dB, ...)
```

——arena 里 5627 MB 全是**更早形状**的大缓冲，新形状要 3072 MB 就放不下，回退到 per-call
`cudaMalloc` 然后 OOM ✗。**卡住 D 的不是表缓存（只占 1.5N），而是那 3N/形状的永久缓存。**

### 20.2 修法：`NttArena::evict_other_shapes(keep_n, keep_nbatch)`

在 `ntt_arena_bufs` **拒绝之前**先驱逐**除了当前形状之外**的一切缓存：其它 `FuseEntry` 的表缓存 +
其它 `(N, nbatch)` 的 `BigEntry`（`dA/dB/dQ`）与 `SmallEntry`，并把它们占的字数从 `ar->bytes` 里扣掉 ✓。
安全性：`ntt_arena_bufs` 在**每次 multiply 开始时**调用，返回的条目只在该次调用内使用，所以"驱逐别的形状"
不会碰到正在用的缓冲 ✓；被驱逐的形状下次需要时按需重建 ✓（表缓存由 `ntt_fuse_cache_tables` 自动重建 ✓）。

配套把可行性估计 `real_shape_words` 改成**`3N + os`**（不再计表缓存）：它必须描述**分配器真实的行为**，
否则扫描会推荐一个跑不起来的 D ✗（这正是第一次尝试时发生的事——估计放行了、分配器拒绝、进程 OOM ✗）。

## 22. 第 ② 项第二步：一次乘法内部的钱花在哪（62% 在乘法计时之外）

§21 只知道"每次除法 = 4.7 次乘法 × ~550 µs"✗。把**乘法自身的计时器**（探针的 `t_fwd/t_inv/t_slot/t_check*/t_plan/t_opcopy/t_hout`）累加进 S5 统计并打印 `s5_mul_cost` 后（D=30030、16 200 次调用、Σ=2.17 s）：

| 每次 S5 乘法 | µs | 说明 |
|---|---|---|
| `fwd` / `inv` / `slot` | **34 / 34 / 10** | 真正的变换 + carry = **78 µs** |
| `check`（其中 `d2h`=16、`kernel`=21）| **31** | **carry 收敛校验**：每调一次就阻塞回读 ✗ |
| `hopcopy` | **23** | 归约 hook 的输出搬运 |
| `hplan` | 2 | 形状规划 |
| **Σ 有归属** | **≈134** | = 2.17 s |
| **`t_generic` 折合每次调用** | **≈350** | ⇒ **≈216 µs（62%）在乘法计时之外** ✗ |

**结论与修法因此更清晰**：
* 变换本身只占 78 µs，**即使把它降到 0 也只省 22%** ✗；真正的成本是**每次调用的固定开销**（pack 内核 + memset + 归约 hook 的 launch/同步 + arena 分配 + 未归因的同步 = 216 µs ✗）。

* **一个仍未归因的口子（记下来）**：每次调用 216 µs 里，`t_pack` 只解释约 25 µs ✓，剩下的（约 190 µs）落在 `s5_mul_batch` 内、`ntt_poly_mul_batch_dev` 外或其后端未计时的部分（memset、hook 的 `s4_launch_reduce`、隐式同步、arena 分配）✗ —— 下一轮做批量重构时应当顺手把这一段也拆开量（它很可能就是"hook 被按 slice 调用"造成的每次调用一次同步 ✗）。

### 27.1 更正：**不是**分块往返的"传输量"，而是**每个分块的固定开销 ~2 ms**

上面那张表让我先写成"地板就是分块往返的搬运"，**这个解释被同一批日志里的实测数字否掉了** ✗（记录在此，
不删）：

| 指标 | 16 MB | 32 MB | 64 MB |
|---|---|---|---|
| `pack_launches`（每分块 2 次 ⇒ 分块数） | 37006（18503） | 20256（10128） | 11130（5565） |
| D2H 体积（GB） | 13.67 | 13.67 | 13.67 |
| H2D 体积（GB） | 14.29 | 14.29 | 14.29 |
| D2H 时间（s，有效 GB/s） | 4.60（2.97） | 4.99（2.74） | 4.56（3.00） |
| H2D 时间（s，有效 GB/s） | 3.22（4.44） | 2.56（5.57） | 2.15（6.64） |

| `ntt_calls`（切片总数，三次完全相同） | 1002748 | 1002748 | 1002748 |

⇒ **传输体积逐字节相同**（13.67 GB / 14.29 GB）✗，传输时间也基本不变（4.4→6.6 GB/s 的小幅变化只有
~1 s 量级）✗；变的**只有分块数** ✓。也就是说那 −24 s 全部落在 **`ntt_seconds` 内部**，而 `ntt_calls`

按"每个被消掉的分块省多少"折算：16→32 MB 消掉 8375 个分块、省 19.2 s ⇒ **≈2.3 ms/分块**；
32→64 MB 消掉 4563 个分块、省 8.5 s ⇒ **≈1.9 ms/分块** ⇒ **每个分块约 2 ms 的固定开销** ✓✓，
且这部分开销**与分块里装几个切片无关** ✗（否则总量应该不变 ✓）。

**~2 ms 的固定开销是什么**：分块越小，`m` 越小（这个形状下 16 MB 只装 ~2 个切片✗），于是每个分块
都是一次**很小的批量乘法**：NTT 趟数不变、launch 数不变、但每次之后都要**被一次阻塞式 D2H 同步抽干
流水线** ✗，加上小 grid 的 kernel 填不满 SM ✗。两者都指向同一个修法：**不要每个分块同步一次** ✓
——这正是第 ⑤ 项（D2H 回读分批/异步）与 ③ 的合流点 ✓✓：把分块的 H2D/D2H 改成 pinned 暂存 + 异步，
整个调用的所有分块只在最后同步一次，就能把 ~2 ms/分块 的抽干拿掉 ✗→✓。

## 28. 分块往返到底是什么：**每 chunk 的阻塞式回读 = 一次流水线抽干**（实测定位）

§27 把"每分块 ~2 ms 固定开销"测出来了，但**说不出它是什么** ✗。这一轮用生产日志里的计数把它定位了：

| 计数（生产命令，32 MB，22471 个分块） | 实测 |
|---|---|
| `real_batched_carrysplit ... d2h` | **36.752 s**（=1.64 ms/分块，而拷的只有 `2*nbatch` 个字 ✗） |
| `real_batched_coeffback`（分块输出回读） | 12.872 s（0.57 ms/分块，有效 2.90 GB/s ✗） |
| `real_batched_rawupload`（原始系数上传） | 6.486 s（0.29 ms/分块，有效 5.98 GB/s） |

**拷贝的字数微不足道，代价全是"等设备把之前排队的活干完"** ✓✓：一次**可分页（pageable）的 D2H
`cudaMemcpy` 在返回前必须等它在流里的前面全部完成** ✗，所以每个分块都要**抽干一次流水线** ✗。
`d2h_us_per_call=14.7` 的"per call"是按**切片**算的（1e6 量级），真实的是"每个分块 1.64 ms" ✓——这正是

⇒ **分块越大越快，不是因为少搬了数据，而是因为少抽干了流水线** ✓✓（§27.1 中"传输体积逐字节相同"有了机制解释 ✓）。

## 29. 第一项落地：**把 carry 检查推迟成"每次调用读一次"** ⇒ 生产 −17.7 s（−7.0%）

既然代价是每分块一次抽干，而 carry 检查（`dRes` 的两个计数器）**只是一次校验** ✗，就没有理由每个分块读一次 ✓。
实现（`ntt_poly_mul_batch_dev(..., bool defer_carry)` + 新的 `ntt_batch_carry_finish`）：

- **最后一个分块之外**的分块把计数器**留在设备上**（既不 `cudaMemset` 也不回读 ✗），
  由调用方在**最后一个分块之前**用 `ntt_batch_carry_finish()` **一次性**读回、求和并给出判定 ✓；
- **第一个分块必须走非推迟路径** ✓（它才是负责 `cudaMemset` 的那一次 ✗）；
- 只能在**有 arena** 时用 ✓（计数器缓冲区必须活过这次调用 ✓），主机打包路径自动关闭 ✓。

**为什么要"最后一个分块之前"读**：arena 的分块缓冲按 `(N, nbatch=m)` 建键 ✗，若最后一个分块大小与内部
分块相同，它的 `cudaMemset` 会把内部累积的计数器**擦掉** ✗ ⇒ 先读后跑 ✓。

**踩到的坑（诚实记录）**：第一版写成"除最后一个分块外全部推迟"，忘了第一个分块要负责清零 ✗ ⇒
读到了**上一次调用残留的计数器**，运行直接报 `CARRY DID NOT CONVERGE in 113 of 225 slices` ✗
（`P=3 nbatch=28800 chunk=225`）。因为"检查通过"留下的就是 0，这类残留**不会误报**，但会让那些切片
的检查**变成空检查** ✗ ⇒ 修成 `defer_this = defer_ok && !last_chunk && (s0 != 0)` ✓。

**生产命令实测（同一条，D=1231230、B2=1.94e12、`NTT_NAME_MAX=1`）**：

#### 27.3.2 但这两个因子**不是同一类东西**（独立验证过，不靠猜）
